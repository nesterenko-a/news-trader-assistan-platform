# Task → spec → implementation

Применять только в этом проекте. Перед действиями прочитать [регламент](../../../docs/16-working-process.md), прежде всего §1.1 и §3.2. Он является источником полного порядка; файлы и их жизненный цикл описаны в [архитектуре документации](../../../docs/32-docs-architecture.md).

## Определить этап

Прочитать существующую постановку и спецификацию, проверить подтверждения пользователя в текущей истории. Уточнение или исправление уже начатой задачи остаётся в её этапе и ветке, если цель и границы не меняются. Не создавать повторную постановку для каждого сообщения пользователя.

Перед новым этапом проверить `git branch --show-current`, `git status --short` и наличие предыдущего этапа в master. Если текущая ветка не master, HEAD отсоединён, изменения мешают переходу или предыдущий этап ещё не слит — сообщить состояние и согласовать действие до изменения файлов. Не выполнять автоматические stash/reset, перенос изменений или merge. При разрешённом переходе создать новую ветку от master.

## Выполнить разрешённый этап

1. **Постановка.** Сформулировать цель, контекст, границы и критерии готовности. Показать пользователю и спросить, устраивает ли постановка. До утверждения не фиксировать её в Git и не реализовывать задачу. После одобрения создать `tasks/<slug>.md` и коммит `tasks(scope): summary` в ветке постановки.
2. **Спецификация.** После слияния постановки подготовить в новой ветке от master необходимые уточнения, спецификацию и документацию. Для небольшой задачи достаточно подходящего раздела существующего документа; не придумывать неприменимые модель БД, API или UI. Показать конкретные документы и получить явное одобрение их коммита. Только затем создать коммит `docs(scope): summary` или `spec(scope): summary`.
3. **Реализация.** После одобрения, коммита и слияния спецификации создать ветку реализации от master. Выполнить согласованный объём, проверки и обновление документации. Не запрашивать заново уже полученное одобрение без изменения требований.

Отсутствие ответа не является одобрением. Одобрение постановки не разрешает реализацию. Существенное изменение целей или требований возвращает затронутую часть на согласование. Коммит, push, PR и merge различаются: не считать одобрение коммита разрешением на остальные действия. При отказе hook исправить причину; не обходить проверку и не заменять требуемый тип коммита без разрешения пользователя.

## Закрыть задачу

Сопоставить результат с критериями готовности и перечислить проверки и ограничения.

- **Полностью выполнена:** зафиксировать выполнение критериев в описании завершающего коммита/PR, удалить файл `tasks/<slug>.md` обычным Git-коммитом и устранить действующие ссылки на него. Не создавать архив или копию файла задачи: история Git достаточна. Спецификацию обработать отдельно по правилам документации.
- **Частично выполнена:** оставить файл задачи с выполненными пунктами, остатками, причинами и следующим шагом. Не объявлять полное закрытие из-за окончания сеанса. Сокращение согласованного объёма требует решения пользователя.

Не автоматизировать согласования. Не расширять область задачи и не устанавливать этот навык глобально для других проектов.

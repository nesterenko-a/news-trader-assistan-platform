# 13. Инфраструктура и эксплуатация

**Статус:** утверждено v1.51  
**Система:** NewsTrader Assistant

Практическое руководство: как запускается система, как управлять схемой БД, как работает планировщик сбора новостей и какие утилиты доступны.

## 1. Инфраструктура (Docker)

Система разворачивается с помощью Docker Compose. Файл конфигурации — `docker/docker-compose.yml`.

| Сервис | Образ | Назначение |
|---|---|---|
| `db` | postgres:13.3 | Основная БД, порт 5432, том `pgdata` (данные переживают перезапуск), healthcheck |
| `migrations` | `newstrader-liquibase:local` (собирается из `docker/liquibase.Dockerfile` на базе liquibase/liquibase:4.31) | Применение миграций схемы; ченджлоги **вшиты в образ при сборке** (`COPY liquibase/ /liquibase/changelog`) — bind-mount не используется; запускается и завершается |

**Запуск БД:**
```
docker compose -f docker/docker-compose.yml up -d db
```

## 2. Миграции (Liquibase)

Схема БД управляется миграциями. Ченджлоги лежат в `liquibase/`:
- `changelog-master.xml` — мастер-ченджлог (список файлов);
- `changelogs/001_initial_schema.xml` — начальная схема (таблицы, ограничения, индексы).

Каждый ченджсет содержит precondition `tableExists/indexExists` с `onFail="MARK_RAN"`, поэтому при применении к существующей базе изменения помечаются выполненными без потери данных.

**Автозапуск при старте приложения (реализовано):** при запуске веб-приложения (`scripts/run_app.py`, `uvicorn app.main:app`) и Telegram-бота (`scripts/run_bot.py`) автоматически вызывается `run_migrations()` (`app/db/migrations.py`): если БД — PostgreSQL, запускается `docker compose -f docker/docker-compose.yml up --build migrations` (Liquibase сам проверяет `databasechangelog` и применяет только новые миграции; контейнер БД поднимается автоматически через `depends_on`; `--build` пересобирает образ с ченджлогами — кэш слоёв делает это быстрым, когда ничего не менялось). Логи в терминале приложения: `[migrations] Проверка миграций Liquibase (PostgreSQL)...`, затем вывод Liquibase и `[migrations] Миграции проверены и применены (Liquibase: успешно)`. Если docker недоступен или миграции завершились ошибкой — печатается `[migrations] ПРЕДУПРЕЖДЕНИЕ: ...` с командой ручного запуска, приложение продолжает старт. Для SQLite (тесты, smoke) миграции пропускаются (лог «БД не PostgreSQL»).

**Применить миграции вручную:**
```
docker compose -f docker/docker-compose.yml up --build migrations
```
Применение идемпотентно: повторный запуск ничего не меняет (Run: 0). Флаг `--build` обязателен после добавления нового ченджлога в `liquibase/changelogs/` — он пересобирает образ, в который вшиты ченджлоги (bind-mount не используется: это обходит баг Docker Desktop «error while creating mount source path /run/desktop/mnt/host/...»).

**Статус и откат:**
```
docker compose -f docker/docker-compose.yml run --rm migrations status
docker compose -f docker/docker-compose.yml run --rm migrations rollback --count 1
```

**Добавление новой миграции:**
1. Создать `liquibase/changelogs/002_<описание>.xml`.
2. Включить его в `changelog-master.xml` через `<include .../>`.
3. Применить: `docker compose -f docker/docker-compose.yml up --build migrations` (пересборка образа подхватит новый ченджлог).

Флаг `AUTO_CREATE_SCHEMA` в `.env`: `true` для локальной разработки, `false` в продакшене — приложение не создаёт схему само, ею управляет только Liquibase.

## 3. Планировщик ежедневного конвейера

Сбор и обновление данных выполняются автоматически по расписанию — эквивалент cron на Windows (Task Scheduler).

- Задача: `NewsTraderBot\CollectNews`.
- Расписание: ежедневно в 09:00.
- Скрипт: `scripts/collect_news.bat` (активирует venv и запускает `scripts/daily_pipeline.py`).
- Лог: `logs/daily_pipeline.log`.

**Ежедневный конвейер (`scripts/daily_pipeline.py`) выполняет пять фаз:**
1. Сбор и анализ новостей (RSS + LLM; при `--telegram` — дополнительно из Telegram-каналов, при `--sites` — со страниц-списков сайтов компаний).
2. Синхронизация дневных свечей (MOEX ISS): **акции** и **фьючерсы** — двумя подзадачами. Фьючерсы синхронизируются по переданному `--tickers <SECID1,SECID2,...>` (список из сохранённого шаблона выбора пользователя); без `--tickers` — по всем фьючерсам справочника.
3. Генерация и сохранение стратегий **только по акциям** (фьючерсы исключены — их нет в knowledge graph; данные их OI/свечей по-прежнему учитываются движком для стратегий акций). Накапливается история вердиктов для бэктеста.
4. Генерация алертов и push в Telegram.
5. **Виртуальный портфель (paper trading)** — открытие/закрытие позиций по вердиктам.

**Повтор фаз:** параметр `--from-phase N` (1–5) запускает конвейер **с фазы N**, пропуская уже успешно завершённые (в логе: «Пропускаю фазы 1..N−1»). В админке — поле «Начать с фазы (1–5)» в карточке «Ежедневный конвейер»; на странице запуска — **виджет фаз** с кликом по красному кружку для продолжения с фазы, а в **Задачах фазы 2** — селект **«Шаблон фьючерсов»**, выбор сохраняется на пользователя и применяется при запуске с фазами 1–2 (в запуск подставляется `--tickers`). Подфазы 1b/1c (Telegram/сайты) следуют за фазой 1 и пропускаются вместе с ней.

**Ошибки:** при падении конвейера в модуль **Внимание** попадает уведомление с указанием фазы: «Скрипт «Ежедневный конвейер» завершился с ошибкой (код N) **на фазе 2/5: синхронизация свечей MOEX**» — фаза определяется по последней строке «Фаза N/5» в логе перед Traceback.

**Telegram-источник:** чтение каналов через Telethon (Telegram API). Требуется `TELEGRAM_API_ID`/`TELEGRAM_API_HASH`/`TELEGRAM_CHANNELS` в `.env` и одноразовый вход: `python -m scripts.telegram_login` (запрашивает номер телефона и код). После этого сообщения из указанных каналов попадают в конвейер как источник `telegram` (репутация 0.6), дедупликация по ссылке `t.me/<канал>/<id>`. Включение в сборе: `--telegram`.

В лог конвейера по каждой бумаге выводится результат генерации стратегии:
- `strategy <TICKER>: STORED verdict=... confidence=... net_score=...` — стратегия записана;
- `strategy <TICKER>: REJECTED (insufficient data)` — бумага отклонена за недостаточностью данных.

В конце фазы выводится сводка: `strategies stored: N (...)` и `strategies rejected (insufficient data): N (...)`.

### 3.1. Виртуальный портфель (paper trading)

Имитация торговли по вердиктам системы на виртуальный капитал (см. UC-07, FR-08-03…08-06).

**Как начать:** ничего запускать отдельно не нужно. Откройте страницу `/paper` (или вызовите `GET /v1/paper`) — виртуальный счёт (стартовый капитал 1 000 000 ₽) создастся автоматически.

**Когда торгуется:** автоматически в `daily_pipeline`, фаза 5/5 (после генерации стратегий). Правила:
- вердикт **BUY** → открыть позицию (капитал делится поровну между BUY-сигналами прогона);
- вердикт **SELL** → закрыть позицию по бумаге;
- **HOLD / INSUFFICIENT_DATA** → без изменений;
- вход/выход — по цене закрытия дня вердикта (**вариант А**): сделка исполняется на ближайшем прогоне, когда этот close уже известен (без заглядывания в будущее). Для этого нужны свечи MOEX и вердикты за предыдущие дни.

**Где смотреть:**
- веб: `/paper` — капитал, открытые позиции, история сделок, метрики (P&L, доходность, % прибыльных сделок, просадка) и бенчмарк «купил всё и держишь»;
- API: `GET /v1/paper`, `GET /v1/paper/trades`, `DELETE /v1/paper/{ticker}`, `POST /v1/paper/reset` (см. [10-api-specification.md](./10-api-specification.md) §3.6).

Если новостей нет — вердиктов нет, сделок нет. Для накопления истории нужны регулярные прогоны конвейера.

**Команды планировщика:**
```
schtasks /Query /TN "NewsTraderBot\CollectNews"     # статус
schtasks /Delete /TN "NewsTraderBot\CollectNews" /F # удалить
```

На Linux аналогичная автоматизация выполняется через cron:
```
0 9 * * * cd /path/to/NewsTraderBot && .venv/bin/python -m scripts.daily_pipeline >> logs/daily_pipeline.log 2>&1
```

## 4. Единый запуск приложения и Telegram-бот

**Единый лаунчер `scripts/run_app.py`** поднимает в одном процессе и веб-интерфейс (uvicorn), и Telegram-бота. Запуск: `python -m scripts.run_app` (или `scripts/run_app.bat` — через `pythonw`, без окна консоли).

- Если Telegram-бот **не может запуститься** (таймаут, нет сети) — приложение всё равно стартует: ошибка не фатальна, фиксируется в «Внимание» (некритичная, warning).
- Фоновый **монитор здоровья** (проверка БД, LLM, Telegram, MOEX, RSS, диск, свежесть данных и периодических скриптов) наполняет «Внимание»: недоступность БД/ИИ-анализа/MOEX — критично, Telegram/RSS/диск/устаревание — некритично, давно не запускавшиеся скрипты — информационно (см. [14-web-interface.md](./14-web-interface.md) и ТЗ [18-health-monitor.md](./18-health-monitor.md)).
- **Ошибки скриптов в «Внимание» снимаются автоматически**: уведомление «Скрипт „X" завершился с ошибкой» (`source=script_run`) деактивируется, как только в истории **«Последние запуски»** появляется более поздний успешный запуск того же скрипта (`ScriptRun.status=success`, `finished_at` позже момента уведомления). Сверка выполняется при каждом успешном завершении скрипта (см. ниже) и периодически фоновым монитором здоровья (каждые ~60 с) — это покрывает и «старые» ошибки, оставшиеся после перезапуска сервиса.
- При **недоступности БД** приложение не падает: стартует, а страницы, требующие данных, возвращают дружелюбную страницу «База данных недоступна» (503) вместо Internal Server Error; **после восстановления БД уведомление в «Внимании» автоматически снимается**.

- Автозапуск: ярлык `NewsTraderBot.lnk` в папке «Автозагрузка» Windows указывает на `scripts/run_app.bat`.
- Лог: `logs/app.log`.
- Если `TELEGRAM_BOT_TOKEN` не задан — запускается только веб-интерфейс (с предупреждением в логе).

**Telegram-бот:**
- Команды: `/start`, `/help`, либо просто тикер (AFLT, SBER, LKOH и т.д.).
- Отдельный запуск только бота: `python -m scripts.run_bot` (полезно для отладки).
- Публичный адрес веб-интерфейса для ссылок в ответах бота — `APP_URL`.

## 5. Утилиты

| Скрипт | Назначение |
|---|---|
| `scripts/seed_db.py` | Создаёт/дополняет справочники: бумаги, сущности, связи графа |
| `scripts/add_research.py` | Дополняет knowledge graph научной/аналитической ссылкой-обоснованием (FR-05-08): `--file <articles.csv>` (колонки `from,to,url[,rationale,strength,confidence,direction,kind]`; поддержка от/к/ссылка), либо одиночно `--from <сущность> --to <сущность> --url <ссылка> [--rationale …]`, либо **`--pdf <путь>`** — текст PDF извлекается (библиотека `pypdf`), LLM определяет связь «от→к», ребро добавляется с `source_ref=file://…`. Прикрепляет ссылку к существующему ребру влияния или создаёт новое ребро (недостающие сущности создаются автоматически; `created_by="curator"`). Идемпотентен — повторный запуск с той же ссылкой не дублирует (`duplicate`). Зарегистрирован в админ-панели как «Добавить научную ссылку в граф» (веб-форма `/admin/graph` позволяет несколько ссылок + загрузку PDF, см. [14-web-interface.md](./14-web-interface.md)) |
| `scripts/export_graph.py` | Выгружает весь graph (сущности `type/aliases/meta` + рёбра `from/to/direction/strength/kind/confidence/rationale/source_ref/created_by/is_approved`) в **JSONL** (`--out <файл>`; без аргумента — в stdout). Формат — строка на запись, маркер `record: "entity"` / `"influence"`, рёбра ссылаются на сущности по имени. Файл переносим между БД. |
| `scripts/import_graph.py` | Идемпотентный импорт дампа из `export_graph` (`--file <dump.jsonl>`, опция `--dry-run`). Создаёт недостающие сущности (по имени, сохраняя `type/aliases/meta`) и рёбра (по паре `<from,to,created_by>`), `source_ref` дополняется без дублей. Повторный запуск не плодит дубликаты. Оба зарегистрированы в админ-панели: «Экспорт графа (JSONL)» и «Импорт графа (JSONL)». |
| `scripts/collect_news.py` | Собирает RSS, фильтрует релевантное, анализирует через LLM, сохраняет в БД (шаг конвейера). Окно сбора: `--days N` / `--from YYYY-MM-DD`; точечный сбор по сущностям: `--entity <имя>` (повторяемый); Telegram-каналы: `--telegram`; **сайты компаний: `--sites`** (страницы-списки новостей, извлечение записей через LLM; см. [22-company-sites-source.md](./22-company-sites-source.md)) |
| `scripts/update_prices.py` | Синхронизирует дневные свечи из MOEX ISS; `--days N` — обновление за N дней; `--from YYYY-MM-DD` — полный бэкфилл истории. Акции качаются с TQBR, **фьючерсы — со срочного рынка forts** (без привязки к доске: доски разные — RFUD/FORTS и др.; свечи фьючерса берутся с его фактической доски). Устойчивость: при временных ответах MOEX 302/5xx (троттлинг) **и обрывах соединения** (`ReadError`/`ConnectError`/таймаут) запрос повторяется с паузами до 6 попыток; при недоступности MOEX тикер **пропускается с предупреждением в логе** — скрипт продолжает остальные бумаги |
| `scripts/update_oi.py` | Синхронизирует открытые позиции фьючерсов из MOEX ISS (история `iss/history/.../forts/securities/{SECID}.json`) и попутно создаёт дневные свечи фьючерса (`MarketCandle` — для сигналов «цена × OI»); `--ticker <SECID>` — код фьючерса (например W4V6, можно несколько раз), `--tickers <SECID1,SECID2,...>` — список через запятую (например, из сохранённого шаблона админки; приоритетнее `--ticker`), `--all` — по всем фьючерсам MOEX (~467 контрактов, список из ISS), `--days N` — окно (по умолчанию 30; работает и с `--ticker`, и с `--all`), `--from YYYY-MM-DD` — полная история (переопределяет `--days`). Автоматически создаёт бумагу-фьючерс, если её нет в справочнике, и проставляет **`assetcode` (код базового актива) и `lastdeldate` (дата экспирации)** из списка фьючерсов ISS — по ним строится связь «акция ↔ фьючерс» (см. [07-data-model.md](./07-data-model.md) §2.1); у существующих фьючерсов поля обновляются (backfill). Повторные запуски идемпотентны (не дублируют даты). Таймаут запуска из админки — 2 часа (env `SCRIPT_TIMEOUT_SECONDS_UPDATE_OI`) |
| `scripts/daily_pipeline.py` | Ежедневный конвейер: новости → цены → генерация стратегий. Окно сбора новостей: `--days N` / `--from YYYY-MM-DD`; Telegram-каналы: `--telegram`; сайты компаний: `--sites`; начать с фазы: `--from-phase N`; список фьючерсов фазы 2: `--tickers SECID1,SECID2,...` (из шаблона) |
| `scripts/run_app.py` | Единый запуск: веб-интерфейс (uvicorn) + Telegram-бот |
| `scripts/run_bot.py` | Запуск только Telegram-бота (polling) |
| `scripts/calibrate.py` | Анализирует распределение скоринга по всем бумагам без сохранения стратегий (для настройки порогов) |
| `scripts/calibrate_weights.py` | Пересчитывает веса факторов (news/graph) по накопленной обратной связи и создаёт новую версию весов (`factor_weights`, w1, w2…) — см. [09-strategy-engine.md](./09-strategy-engine.md) §6.1. Запускать периодически по мере накопления оценок |
| `scripts/backtest.py` | Оценивает сохранённые вердикты против фактического движения цены по дневным свечам (вход = close на дату генерации, выход = close через 5 торговых дней) |
| `scripts/backtest_asof.py` | Бэктест «на момент T»: воспроизводит вердикт на историческую дату, используя только данные, доступные в T (новости до T, без рыночных котировок), и оценивает результат через N торговых дней. Параметры: `--tickers` (по умолчанию все), `--start`/`--end YYYY-MM-DD`, `--horizon N` (торговых дней, по умолчанию 5), `--step N` (шаг по торговым дням, по умолчанию 1). Отчёт: точность по вердиктам и по месяцам, средняя доходность |
| `scripts/smoke.py` | Сквозная проверка API и веб-интерфейса на SQLite |
| `scripts/create_user.py` | Создание пользователя: `python -m scripts.create_user <username> <password>` (аналог регистрации через веб) |
| `scripts/process_alerts.py` | Генерирует алерты по значимым новостям из watchlist всех пользователей; `--days N` — окно новостей (по умолчанию 7) |
| `scripts/seed_macro.py` | Наполняет макрокалендарь на 6 месяцев вперёд: заседания ЦБ, CPI/PMI/ВВП, сезоны отчётностей и корпоративные события по тикерам (идемпотентен) |
| `scripts/telegram_login.py` | Первый вход Telethon для чтения Telegram-каналов (интерактивный: телефон + код), создаёт файл сессии |

Запуск: `.venv\Scripts\python.exe -m scripts.<имя>` из корня проекта.

**E2E-тесты веб-интерфейса (Playwright Test Runner):** сценарии в `tests/e2e/` (`*.spec.ts`) запускаются **отдельным прогоном** — `npx playwright test` (UI-режим: `npx playwright test --ui`); в `pytest -q` не входят (pytest — только unit). Быстрый запуск из корня: `scripts\run_e2e.bat`. Стенд (uvicorn + сидинг `scripts/e2e_seed.py`) поднимается автоматически, см. [21-web-e2e-tests.md](./21-web-e2e-tests.md).

**Запуск скриптов из веб-интерфейса:** администраторы (роль `admin`, см. [11-security-compliance.md](./11-security-compliance.md)) могут запускать основные скрипты через страницу `/admin` — с историей запусков и **живым логом** (вывод поступает в реальном времени, скрипты запускаются без буферизации и сообщают о ходе работы). На карточке «Обновить открытые позиции (OI)» — текстовое поле тикера, поле **«За последние N дней»** (по умолчанию 30; работает и с тикером, и с флагом `--all`) и чекбокс **«Скачать OI по всем фьючерсам (--all)»** (при установке поле тикера блокируется); страница результата запуска показывает **прогресс-бар «загружено из N, осталось»** (парсится из строк `[i/N]` в логе, обновляется при авто-обновлении страницы). Страница запуска обновляется **без перезагрузки**: пока скрипт выполняется, статус, прогресс и вывод подтягиваются через AJAX (`GET /admin/runs/{id}?partial=1`) каждые 3 секунды — открытое меню пользователя/«Внимание» не сбрасывается. **Успешное завершение скрипта снимает** из «Внимание» уведомления об ошибках этого скрипта (сверка с «Последними запусками», см. §1). Журнал хранится в таблице `script_runs`. При перезапуске сервиса запуски, оставшиеся в статусе «выполняется», автоматически помечаются как прерванные (failed).

Веб-панель запускает скрипты как `python -u -m scripts.<имя>` (флаг `-u` — «без буферизации вывода» — нужен только для потоковой записи лога) автоматически. При ручном запуске из терминала флаг `-u` не требуется — команды остаются в обычном виде `python -m scripts.<имя>`.

**Накопление данных и бэктест:**
- Исторические цены: `python -m scripts.update_prices --from 2012-01-01` (полная история) или `--days N` (обновление).
- Открытые позиции фьючерсов (индикатор OI): `python -m scripts.update_oi --ticker W4V6 --from 2026-03-01` (история OI, см. [19-market-indicators.md](./19-market-indicators.md) §8.12).
- Дополнить граф научной ссылкой: `python -m scripts.add_research --from "Нефть" --to "Нефтегазовый сектор" --url "https://…"`, пакетно из файла: `python -m scripts.add_research --file research_links.csv`, или из PDF: `python -m scripts.add_research --pdf /путь/article.pdf` (см. [09-strategy-engine.md](./09-strategy-engine.md) §3).
- Ежедневно конвейер добавляет новости, свечи и вердикты.
- Бэктест становится осмысленным после ~2–4 недель накопления (нужны вердикты, для которых прошло 5 торговых дней).
- Веб-интерфейс показывает историю цены на карточке бумаги: диапазоны 1 год / 5 лет / с 2012 года (серверный SVG-график по сохранённым свечам).

**Перенос графа между БД (экспорт/импорт):** для восстановления кураторских связей и обоснований (в т.ч. FAO/SEC из `add_research`) после пересоздания или переезда БД:
1. На старой БД выгрузить дамп: `python -m scripts.export_graph --out graph_dump.jsonl` (или без `--out` — в stdout).
2. На новой БД выполнить сидирование справочников и графа: `python -m scripts.seed_db`.
3. Импортировать дамп (идемпотентно): `python -m scripts.import_graph --file graph_dump.jsonl` (предпросмотр — с `--dry-run`).
Повторный импорт не дублирует записи: сущности дополняются по имени (type/aliases/meta), рёбра — по паре от/к/created_by, а `source_ref` мержится без повторов. Оба скрипта доступны из админ-панели («Экспорт графа (JSONL)» / «Импорт графа (JSONL)»).

## 6. Конфигурация (`.env`)

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Строка подключения к PostgreSQL (asyncpg) |
| `AUTO_CREATE_SCHEMA` | `true` — приложение создаёт схему само (dev); `false` — только Liquibase (prod) |

| `TELEGRAM_BOT_TOKEN` | Токен Telegram-бота (канал доступа) |
| `TELEGRAM_API_ID` / `TELEGRAM_API_HASH` | Данные Telegram API для чтения каналов как источника новостей (Telethon) |
| `TELEGRAM_CHANNELS` | Список каналов-источников через запятую (без `@`) |

| `MVP_TICKERS` | Список отслеживаемых тикеров |

Секреты (ключи API, токены) хранятся только в `.env` и не попадают в репозиторий.

### 6.1. Получение `TELEGRAM_API_ID` / `TELEGRAM_API_HASH`

`api_id` и `api_hash` — это ключи **приложения Telegram API** (не токен бота). Получаются бесплатно на официальном сайте [my.telegram.org](https://my.telegram.org/):

1. Откройте https://my.telegram.org/ и войдите под номером телефона, который используется в Telegram (придёт код подтверждения в мессенджер).
2. Перейдите в раздел **API development tools**.
3. Если приложение ещё не создано — нажмите **Create new application**:
   - **App title** — любое название, например `NewsTraderBot`;
   - **Short name** — короткое имя без пробелов, например `newstrader`;
   - **URL** — можно оставить пустым;
   - **Platform** — Desktop;
   - **Description** — любое описание (можно оставить пустым).
4. После создания на странице отобразятся **api_id** (число) и **api_hash** (строка). Пропишите их в `.env`:

   ```
   TELEGRAM_API_ID=12345678
   TELEGRAM_API_HASH=0123456789abcdef0123456789abcdef
   ```

5. **Важно:** `api_id`/`api_hash` привязаны к аккаунту и считаются секретами — не коммитьте их в git и не публикуйте. Один аккаунт может создать ограниченное число приложений; уточняйте лимит на [my.telegram.org](https://my.telegram.org/).

# 13. Инфраструктура и эксплуатация

**Статус:** утверждено v1.93 (запуск аналитических вопросов MCP)
**Система:** NewsTrader Assistant

## Проверка MCP Т-Инвестиций

Для вопросов после запуска приложения открыть выбранную карточку брокера, проверить MCP и выбранную пару LLM, затем отправить вопрос по [инструкции интерфейса](./14-web-interface.md#mcp-диагностика-т-инвестиций). Нужны существующее подключение брокера и ключ выбранного LLM-провайдера; новых .env-переменных, миграций и фоновых процессов нет. При перезапуске процесса повторить проверку LLM. Смена хеша MCP-инструмента требует исследования новой схемы и обновления манифеста через код; не отключать проверку и не разрешать новый инструмент по одному названию/readOnlyHint. Публичные SHA-256 схем в манифесте проверены как контрольные суммы, а не секреты; исключения сканера ограничены этими значениями.

Для разработки адаптеров владелец подключения может [скачать структуру схем MCP](./14-web-interface.md#mcp-диагностика-т-инвестиций) из того же интерфейса. Повторно вводить ключ DeepSeek или токен брокера не нужно. Экспорт использует только обнаружение tools/list, не читает портфель и не вызывает LLM. Новых переменных окружения и скриптов нет. Сверить полные хеши с исходными схемами и исследовать исключённые ключи до допуска инструмента; не считать экспорт автоматическим разрешением.

Проверка LLM использует существующие ключи, base_url и модели DeepSeek/ChatGPT из настроек приложения; новых переменных нет. Запускается отдельно явной кнопкой, допускает расходы выбранного LLM-провайдера, но не передаёт портфель или токен брокера. После перезапуска серверного процесса или смены ключей повторить проверку выбранной пары. Ошибка проверки не переключает провайдера автоматически; требуется выбрать поддерживаемую модель. Каталог может включать модели, не поддерживающие нужный протокол или вызов инструментов.

Отдельный процесс и новые переменные окружения не требуются. MCP использует сохранённое зашифрованное подключение выбранного контура и существующее доверие TLS брокера. Запустить приложение обычным способом и выполнить [проверку из настроек брокеров](./14-web-interface.md#mcp-диагностика-т-инвестиций). Сама диагностика MCP не использует ключи LLM; для отдельной кнопки проверки LLM нужны настройки выбранного провайдера. При отказе авторизации проверить контур/права собственного токена; при TLS-ошибке использовать существующее восстановление сертификата. Не отключать проверку TLS. Контракт диагностики — [API](./10-api-specification.md#mcp-диагностика).

Практическое руководство: как запускается система, как управлять схемой БД, как работает планировщик сбора новостей и какие утилиты доступны.

## 1. Инфраструктура (Docker)

Система разворачивается с помощью Docker Compose. Файл конфигурации — `docker/docker-compose.yml`.

| Сервис | Образ | Назначение |
|---|---|---|
| `db` | postgres:13.3 | Основная БД, порт 5432, том `pgdata` (данные переживают перезапуск), healthcheck |
| `migrations` | `newstrader-liquibase:local` (собирается из `docker/liquibase.Dockerfile` на базе liquibase/liquibase:4.31) | Применение миграций схемы; ченджлоги **вшиты в образ при сборке** (`COPY liquibase/ /liquibase/changelog`) — bind-mount не используется; запускается и завершается |

**Запуск БД:**
```
docker compose -f docker/docker-compose.yml up -d db
```

## 2. Миграции (Liquibase)

Схема БД управляется миграциями. Ченджлоги лежат в `liquibase/`:
- `changelog-master.xml` — мастер-ченджлог (список файлов);
- `changelogs/001_initial_schema.xml` — начальная схема (таблицы, ограничения, индексы).

Каждый ченджсет содержит precondition `tableExists/indexExists` с `onFail="MARK_RAN"`, поэтому при применении к существующей базе изменения помечаются выполненными без потери данных.

**Автозапуск при старте приложения (реализовано):** при запуске веб-приложения (`scripts/run_app.py`, `uvicorn app.main:app`) и Telegram-бота (`scripts/run_bot.py`) автоматически вызывается `run_migrations()` (`app/db/migrations.py`): если БД — PostgreSQL, запускается `docker compose -f docker/docker-compose.yml up --build migrations` (Liquibase сам проверяет `databasechangelog` и применяет только новые миграции; контейнер БД поднимается автоматически через `depends_on`; `--build` пересобирает образ с ченджлогами — кэш слоёв делает это быстрым, когда ничего не менялось). Логи в терминале приложения: `[migrations] Проверка миграций Liquibase (PostgreSQL)...`, затем вывод Liquibase и `[migrations] Миграции проверены и применены (Liquibase: успешно)`. Если docker недоступен или миграции завершились ошибкой — печатается `[migrations] ПРЕДУПРЕЖДЕНИЕ: ...` с командой ручного запуска, приложение продолжает старт. Для SQLite (тесты, smoke) миграции пропускаются (лог «БД не PostgreSQL»).

Миграция `029_user_profiles.xml` создаёт приватные профили пользователей. Для загрузки и безопасного перекодирования аватаров требуется `Pillow` из `requirements.txt`; файлы хранятся в неверсируемом каталоге `uploads/avatars/`.

**Применить миграции вручную:**
```
docker compose -f docker/docker-compose.yml up --build migrations
```
Миграция `031_graph_candidates.xml` создаёт очередь предложенных связей и их доказательства. После обычного запуска `daily_pipeline` или `collect_news` кандидаты извлекаются только для достаточно значимых новостей; ошибки дополнительного LLM-вызова не останавливают сбор. Куратор проверяет их в веб-интерфейсе `/admin/graph/candidates`: «Принять» создаёт обычную утверждённую связь, «Отклонить» сохраняет решение для аудита, «Нужно больше данных» возвращает предложение в очередь доказательств.
Применение идемпотентно: повторный запуск ничего не меняет (Run: 0). Флаг `--build` обязателен после добавления нового ченджлога в `liquibase/changelogs/` — он пересобирает образ, в который вшиты ченджлоги (bind-mount не используется: это обходит баг Docker Desktop «error while creating mount source path /run/desktop/mnt/host/...»).

**Статус и откат:**
```
docker compose -f docker/docker-compose.yml run --rm migrations status
docker compose -f docker/docker-compose.yml run --rm migrations rollback --count 1
```

**Добавление новой миграции:**
1. Создать `liquibase/changelogs/002_<описание>.xml`.
2. Включить его в `changelog-master.xml` через `<include .../>`.
3. Применить: `docker compose -f docker/docker-compose.yml up --build migrations` (пересборка образа подхватит новый ченджлог).

Флаг `AUTO_CREATE_SCHEMA` в `.env`: `true` для локальной разработки, `false` в продакшене — приложение не создаёт схему само, ею управляет только Liquibase.

## 3. Планировщик ежедневного конвейера

Сбор и обновление данных выполняются автоматически по расписанию — эквивалент cron на Windows (Task Scheduler).

- Задача: `NewsTraderBot\CollectNews`.
- Расписание: ежедневно в 09:00.
- Скрипт: `scripts/collect_news.bat` (активирует venv и запускает `scripts/daily_pipeline.py`).
- Лог: `logs/daily_pipeline.log`.

**Ежедневный конвейер (`scripts/daily_pipeline.py`) выполняет пять фаз:**
1. Сбор и анализ новостей (RSS + LLM; при `--telegram` — дополнительно из Telegram-каналов, при `--sites` — со страниц-списков сайтов компаний).
2. Синхронизация дневных свечей (MOEX ISS): **акции** и **фьючерсы** — двумя подзадачами. Фьючерсы синхронизируются по переданному `--tickers <SECID1,SECID2,...>` (список из сохранённого шаблона выбора пользователя); без `--tickers` — по всем фьючерсам справочника.
3. Генерация и сохранение стратегий **только по акциям** (фьючерсы исключены — их нет в knowledge graph; данные их OI/свечей по-прежнему учитываются движком для стратегий акций). Накапливается история вердиктов для бэктеста.
4. Генерация алертов и push в Telegram.
5. **Виртуальный портфель (paper trading)** — открытие/закрытие позиций по вердиктам.

**Повтор фаз:** параметр `--from-phase N` (1–5) запускает конвейер **с фазы N**, пропуская уже успешно завершённые (в логе: «Пропускаю фазы 1..N−1»). В админке — поле «Начать с фазы (1–5)» в карточке «Ежедневный конвейер»; на странице запуска — **виджет фаз** с кликом по красному кружку для продолжения с фазы, а в **Задачах фазы 2** — селект **«Шаблон фьючерсов»**, выбор сохраняется на пользователя и применяется при запуске с фазами 1–2 (в запуск подставляется `--tickers`). Подфазы 1b/1c (Telegram/сайты) следуют за фазой 1 и пропускаются вместе с ней.

**Ошибки:** при падении конвейера в модуль **Внимание** попадает уведомление с указанием фазы: «Скрипт «Ежедневный конвейер» завершился с ошибкой (код N) **на фазе 2/5: синхронизация свечей MOEX**» — фаза определяется по последней строке «Фаза N/5» в логе перед Traceback.

**Telegram-источник:** чтение каналов через Telethon (Telegram API). Требуется `TELEGRAM_API_ID`/`TELEGRAM_API_HASH`/`TELEGRAM_CHANNELS` в `.env` и одноразовый вход: `python -m scripts.telegram_login` (запрашивает номер телефона и код). После этого сообщения из указанных каналов попадают в конвейер как источник `telegram` (репутация 0.6), дедупликация по ссылке `t.me/<канал>/<id>`. Включение в сборе: `--telegram`.

В лог конвейера по каждой бумаге выводится результат генерации стратегии:
- `strategy <TICKER>: STORED verdict=... confidence=... net_score=...` — стратегия записана;
- `strategy <TICKER>: REJECTED (insufficient data)` — бумага отклонена за недостаточностью данных.

В конце фазы выводится сводка: `strategies stored: N (...)` и `strategies rejected (insufficient data): N (...)`.

### 3.1. Виртуальный портфель (paper trading)

Имитация торговли по вердиктам системы на виртуальный капитал (см. UC-07, FR-08-03…08-06).

**Как начать:** ничего запускать отдельно не нужно. Откройте страницу `/paper` (или вызовите `GET /v1/paper`) — виртуальный счёт (стартовый капитал 1 000 000 ₽) создастся автоматически.

**Когда торгуется:** автоматически в `daily_pipeline`, фаза 5/5 (после генерации стратегий). Правила:
- вердикт **BUY** → открыть позицию (капитал делится поровну между BUY-сигналами прогона);
- вердикт **SELL** → закрыть позицию по бумаге;
- **HOLD / INSUFFICIENT_DATA** → без изменений;
- вход/выход — по цене закрытия дня вердикта (**вариант А**): сделка исполняется на ближайшем прогоне, когда этот close уже известен (без заглядывания в будущее). Для этого нужны свечи MOEX и вердикты за предыдущие дни.

**Где смотреть:**
- веб: `/paper` — капитал, открытые позиции, история сделок, метрики (P&L, доходность, % прибыльных сделок, просадка) и бенчмарк «купил всё и держишь»;
- API: `GET /v1/paper`, `GET /v1/paper/trades`, `DELETE /v1/paper/{ticker}`, `POST /v1/paper/reset` (см. [10-api-specification.md](./10-api-specification.md) §3.6).

Если новостей нет — вердиктов нет, сделок нет. Для накопления истории нужны регулярные прогоны конвейера.

**Команды планировщика:**
```
schtasks /Query /TN "NewsTraderBot\CollectNews"     # статус
schtasks /Delete /TN "NewsTraderBot\CollectNews" /F # удалить
```

На Linux аналогичная автоматизация выполняется через cron:
```
0 9 * * * cd /path/to/NewsTraderBot && .venv/bin/python -m scripts.daily_pipeline >> logs/daily_pipeline.log 2>&1
```

### 3.2. Top-5: лучшая сделка из шаблона инструментов (Теханализ в LLM)

Свечная схема подтверждения на полном ответе теханализа появляется для новых разборов, если LLM вернул валидированный `confirmation_plans`. Чтобы получить её для бумаги, запустите новый разбор с карточки бумаги; уже сохранённые ответы не переписываются и при отсутствии плана остаются текстовыми. Отдельного скрипта, миграции или переменной окружения для схемы нет; работа с ней описана в [14-web-interface.md](./14-web-interface.md) §2.

- **Что это:** пользователь выбирает «Шаблон инструментов» типа **Акции** (`kind=stock`) или **Фьючерсы** (`kind=futures`), нажимает **«Теханализ в LLM»** на странице `/top5` — система запускает одиночный Теханализ по каждому инструменту шаблона и выводит **рейтинг до 5 лучших сделок по Expected R** (`prob×rr − (1−prob)×1`). Свежие успешные результаты переиспользуются без нового вызова LLM, каждый инструмент — обычный анализ `tech_analyses`, доступный на его карточке.
- **Где запускать:** не запускается скриптом — запускается из веб-интерфейса на странице `/top5` (нужен вход). Управление шаблонами акций и фьючерсов — в админ-панели «Шаблоны инструментов» (`/admin/futures-templates`).
- **Как отобрать сделки:** выберите шаблон, затем в блоке «Фильтр качества сделки» включите «Только подходящие» и задайте пороги R/R, риска и уверенности. По желанию включите минимум ликвидности (начальное значение 1 млн ₽/день) и требование плана подтверждения. Таблица и счётчики пересчитаются без повторного обращения к LLM; «Сбросить» вернёт исходную выдачу. Ликвидность требует не менее 10 валидных дневных свечей за последние 45 дней; при отсутствии данных бумага не проходит включённый критерий. Подробное поведение — в [14-web-interface.md](./14-web-interface.md).
- **Группы и повтор:** полный шаблон делится на последовательные группы по 10 акций по умолчанию (30 акций → 3 батча по 10 в истории). Следующая группа стартует после завершения анализов предыдущей. В «Составе батча» нажмите ▶ у ошибочной акции или фьючерса: полный анализ повторится в той же строке, с индикатором загрузки и приблизительным процентом по этапу; после успеха появится «разбор →», после ошибки — ▶. Страница не перезагружается при обновлении строк. При запуске нового шаблона свежие успешные результаты переиспользуются без переноса их из прежней истории; «Принудительно обновить» запускает новый анализ для каждой бумаги. Старые батчи из 20 акций не расширяются автоматически: для полного охвата запустите шаблон заново.
- **Конфиг:** `TOP5_FRESH_HOURS` (актуальность анализа для переиспользования), `TOP5_BATCH_SIZE` (размер одной последовательной группы; по умолчанию 10). Старый `TOP5_MAX_INSTRUMENTS` сохраняется в конфигурации для чтения прежнего `.env`, но больше не ограничивает шаблон и может быть удалён из файла.
- **Миграция:** БД получает новые колонки/таблицы миграцией `liquibase/changelogs/027_top5_trades.xml` (поле `kind` в `futures_templates`, таблица `tech_analysis_batches`, колонка `batch_id` в `tech_analyses`).

### 3.3. Реальное время (актуализация данных + live-котировки)

**Что это:** автономный демон `realtime_updater`, который периодически актуализирует рыночные данные и пишет live-котировки, по которым веб-интерфейс транслирует живые цены на карточке бумаги по **SSE** (см. [archive/24-market-realtime.md](./archive/24-market-realtime.md)).

**Как включить и запустить:**
1. Войдите как администратор → страница `/admin` → блок **«Реальное время»**: включите тумблер «Актуализация», задайте интервалы (котировки / свечи / OI фьючерсов, сек) и выберите шаблон фьючерсов → «Сохранить».
2. Запустите демон: карточка **«Актуализация рынка (демон)»** в списке скриптов `/admin` (кнопка «Запустить»).
3. Демон — долгоживущий процесс: работает, пока его не остановят (таймаут не ограничивается — `no_timeout` в `SCRIPTS`). Пока демон работает, из админки можно запустить один обычный скрипт, например обновление OI или ежедневный конвейер; второй обычный скрипт ожидает завершения первого. Повторный запуск самого демона недоступен. Команда CLI: `python -m scripts.realtime_updater [--oneshot]` (`--oneshot` — один проход для проверки).

**Состав инструментов:** акции = watchlist всех пользователей + `MVP_TICKERS`; фьючерсы = тикеры выбранного шаблона (`kind=futures`); пересчитывается на каждой итерации.

**Что обновляет демон:** live-котировки (`real_time_quotes`, LAST/OHLC/объём дня); дневные свечи акций и фьючерсов (`sync_security_prices`); OI фьючерсов шаблона, включая группы клиентов (`sync_security_oi`).

**Поведение:**
- Настройки перечитываются каждую итерацию — изменение тумблера/интервалов в админке применяется без перезапуска.
- При `enabled=false` демон сразу завершается («Realtime отключён», код 0).
- Временный сетевой сбой MOEX (`ReadError`, `ConnectError`, таймаут) повторяется до шести раз с паузой. Если данные по тикеру так и не получены, он пропускается в текущем проходе; демон продолжает работу и попробует снова на следующей итерации.
- При недоступности MOEX в «Внимание» создаётся/снимается уведомление `realtime_moex` (warning).
- Журнал запуска на странице `/admin/runs/{id}` показывает каждый проход: состав акций и фьючерсов, результат обновления котировки по каждому тикеру (LAST/объём или причина отсутствия данных), новые или актуальные дневные свечи и OI, а также общий итог и время следующего прохода.

**Где смотреть:** на карточке бумаги (`/securities/{ticker}`, акции/фьючерсы) блок котировок обновляется по SSE без перезагрузки (JS `initRealtimeQuotes` в `/static/app.js`, эндпоинт `GET /v1/realtime/stream`).

## 4. Единый запуск приложения и Telegram-бот

**Единый лаунчер `scripts/run_app.py`** поднимает в одном процессе и веб-интерфейс (uvicorn), и Telegram-бота. Запуск: `python -m scripts.run_app` (или `scripts/run_app.bat` — через `pythonw`, без окна консоли).

- Если Telegram-бот **не может запуститься** (таймаут, нет сети) — приложение всё равно стартует: ошибка не фатальна, фиксируется в «Внимание» (некритичная, warning).
- Фоновый **монитор здоровья** (проверка БД, LLM, Telegram, MOEX, RSS, диск, свежесть данных и периодических скриптов) наполняет «Внимание»: недоступность БД/ИИ-анализа/MOEX — критично, Telegram/RSS/диск/устаревание — некритично, давно не запускавшиеся скрипты — информационно (см. [14-web-interface.md](./14-web-interface.md) и ТЗ [18-health-monitor.md](./18-health-monitor.md)).
- **Ошибки скриптов в «Внимание» снимаются автоматически**: уведомление «Скрипт „X" завершился с ошибкой» (`source=script_run`) деактивируется, как только в истории **«Последние запуски»** появляется более поздний успешный запуск того же скрипта (`ScriptRun.status=success`, `finished_at` позже момента уведомления). Сверка выполняется при каждом успешном завершении скрипта (см. ниже) и периодически фоновым монитором здоровья (каждые ~60 с) — это покрывает и «старые» ошибки, оставшиеся после перезапуска сервиса.
- При **недоступности БД** приложение не падает: стартует, а страницы, требующие данных, возвращают дружелюбную страницу «База данных недоступна» (503) вместо Internal Server Error; **после восстановления БД уведомление в «Внимании» автоматически снимается**.

- Автозапуск: ярлык `NewsTraderBot.lnk` в папке «Автозагрузка» Windows указывает на `scripts/run_app.bat`.
- Лог: `logs/app.log`.
- Если `TELEGRAM_BOT_TOKEN` не задан — запускается только веб-интерфейс (с предупреждением в логе).

**Telegram-бот:**
- Команды: `/start`, `/help`, либо просто тикер (AFLT, SBER, LKOH и т.д.).
- Отдельный запуск только бота: `python -m scripts.run_bot` (полезно для отладки).
- Публичный адрес веб-интерфейса для ссылок в ответах бота — `APP_URL`.

**E2E-тесты веб-интерфейса (Playwright Test Runner):** сценарии в `tests/e2e/` (`*.spec.ts`) запускаются **отдельным прогоном** — `npx playwright test` (UI-режим: `npx playwright test --ui`); в `pytest -q` не входят (pytest — только unit). Быстрый запуск из корня: `scripts\run_e2e.bat`. Стенд (uvicorn + сидинг `scripts/e2e_seed.py`) поднимается автоматически, см. [21-web-e2e-tests.md](./21-web-e2e-tests.md).

**Запуск скриптов из веб-интерфейса:** администраторы (роль `admin`, см. [11-security-compliance.md](./11-security-compliance.md)) запускают и настраивают основные скрипты через `/admin` — с историей запусков и **живым логом**. Каждая карточка использует ON/OFF-switch: OFF запускает, ON останавливает без подтверждения. После запуска страница остаётся `/admin`, а карточка показывает ссылку «Открыть задачу →» на живой лог. Раннер останавливает процесс через `terminate`, а через 10 секунд — `kill`; уже сохранённые данные не откатываются, запуск получает `stopped`, инициатора и время остановки, notice об ошибке не создаётся. Запуск realtime-демона сначала включает его конфигурацию, поэтому процесс не завершается сразу как отключённый. В `/settings` для администратора есть только лаконичный якорный блок работающих задач с toggle остановки. Realtime запускается, останавливается и настраивается только в `/admin`; элемента realtime в шапке нет. На карточке «Обновить открытые позиции (OI)» доступны поле тикера, поле **«За последние N дней»** и режим `--all`; страница результата обновляет статус, прогресс и вывод через AJAX (`GET /admin/runs/{id}?partial=1`) каждые 3 секунды. Успешный скрипт снимает свои уведомления об ошибках. При перезапуске сервиса незавершённые запуски помечаются `failed`, потому что живой процесс доступен только в памяти текущего веб-процесса.

Операции запуска и остановки выполняются фоновым HTTP-запросом: браузер обновляет только сетку карточек задач, без перезагрузки `/admin`.

Веб-панель запускает скрипты как `python -u -m scripts.<имя>` (флаг `-u` — «без буферизации вывода» — нужен только для потоковой записи лога) автоматически. При ручном запуске из терминала флаг `-u` не требуется — команды остаются в обычном виде `python -m scripts.<имя>`.

**Накопление данных и бэктест:**
- Исторические цены: `python -m scripts.update_prices --from 2012-01-01` (полная история) или `--days N` (обновление).
- Открытые позиции фьючерсов (индикатор OI): `python -m scripts.update_oi --ticker W4V6 --from 2026-03-01` (история OI, см. [19-market-indicators.md](./19-market-indicators.md) §8.12).
- Дополнить граф научной ссылкой: `python -m scripts.add_research --from "Нефть" --to "Нефтегазовый сектор" --url "https://…"`, пакетно из файла: `python -m scripts.add_research --file research_links.csv`, или из PDF: `python -m scripts.add_research --pdf /путь/article.pdf` (см. [09-strategy-engine.md](./09-strategy-engine.md) §3).
- Ежедневно конвейер добавляет новости, свечи и вердикты.
- Бэктест становится осмысленным после ~2–4 недель накопления (нужны вердикты, для которых прошло 5 торговых дней).
- Веб-интерфейс показывает историю цены на карточке бумаги: диапазоны 1 год / 5 лет / с 2012 года (серверный SVG-график по сохранённым свечам).

**Перенос графа между БД (экспорт/импорт):** для восстановления кураторских связей и обоснований (в т.ч. FAO/SEC из `add_research`) после пересоздания или переезда БД:
1. На старой БД выгрузить дамп: `python -m scripts.export_graph --out graph_dump.jsonl` (или без `--out` — в stdout).
2. На новой БД выполнить сидирование справочников и графа: `python -m scripts.seed_db`.
3. Импортировать дамп (идемпотентно): `python -m scripts.import_graph --file graph_dump.jsonl` (предпросмотр — с `--dry-run`).
Повторный импорт не дублирует записи: сущности дополняются по имени (type/aliases/meta), рёбра — по паре от/к/created_by, а `source_ref` мержится без повторов. Дамп переносит также подсказки «что отслеживать» (`entity_watch_metrics`) для карты зависимостей. Оба инструмента доступны в веб-интерфейсе через раздел **«Перенос графа (экспорт / импорт)»** на странице `/admin` (скачать дамп / выбрать файл и импортировать).

Чтобы заполнить раздельное число лиц в лонге и шорте для уже сохранённых дат, после миграции повторно запустите штатное обновление OI для нужного фьючерса и окна дат: `.venv\Scripts\python.exe -m scripts.update_oi --ticker <SECID> --from YYYY-MM-DD`. Существующие записи обновляются, когда источник MOEX возвращает полные позиции группы. У старых дат, для которых источник больше не отдаёт число лиц, на графике остаётся прочерк. Новый график на `/indicators` читает сохранённую историю и не загружает её автоматически. Порядок работы в интерфейсе — [14-web-interface.md](./14-web-interface.md) §5.

### 6.1. Получение `TELEGRAM_API_ID` / `TELEGRAM_API_HASH`

`api_id` и `api_hash` — это ключи **приложения Telegram API** (не токен бота). Получаются бесплатно на официальном сайте [my.telegram.org](https://my.telegram.org/):

1. Откройте https://my.telegram.org/ и войдите под номером телефона, который используется в Telegram (придёт код подтверждения в мессенджер).
2. Перейдите в раздел **API development tools**.
3. Если приложение ещё не создано — нажмите **Create new application**:
   - **App title** — любое название, например `NewsTraderBot`;
   - **Short name** — короткое имя без пробелов, например `newstrader`;
   - **URL** — можно оставить пустым;
   - **Platform** — Desktop;
   - **Description** — любое описание (можно оставить пустым).
4. После создания на странице отобразятся **api_id** (число) и **api_hash** (строка). Пропишите их в `.env`:

   ```
   TELEGRAM_API_ID=12345678
   TELEGRAM_API_HASH=0123456789abcdef0123456789abcdef
   ```

5. **Важно:** `api_id`/`api_hash` привязаны к аккаунту и считаются секретами — не коммитьте их в git и не публикуйте. Один аккаунт может создать ограниченное число приложений; уточняйте лимит на [my.telegram.org](https://my.telegram.org/).

## 7. Проверки коммитов и GitHub Actions

### 7.1. Подключение на рабочем клоне

Из корня проекта, после создания `.venv`:

```powershell
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.venv\Scripts\python.exe -m pre_commit install
.venv\Scripts\python.exe -m pre_commit run --all-files
```

Установка создаёт оба hooks: `pre-commit` и `commit-msg`. Выполняется один раз на каждом клоне; hooks в `.git/hooks` не передаются через git. Первый запуск создаёт изолированные окружения инструментов и требует интернета. Версии инструментов закреплены в `requirements-dev.txt` и `.pre-commit-config.yaml`; при обновлении менять обе конфигурации согласованно.

При `git commit` проверяются добавленные в индекс файлы. Ruff использует минимальные правила корректности из `ruff.toml`, без автоматического форматирования. Проверки YAML/JSON/XML отклоняют синтаксические ошибки; `.vscode/*.json` исключены из строгого JSON-парсера, поскольку настройки VS Code допускают JSONC. Маркеры merge-конфликтов и приватные ключи проверяются в текстовых файлах. Проверка путей отклоняет `.env` и его варианты (кроме `.env.example`), виртуальные окружения, БД, Telethon-сессии и артефакты; список — `tools/git_checks.py`.

Для изменений в `app/`, `scripts/`, `tests/`, `tools/`, зависимостях и конфигурациях тестов, hooks, CI, Docker и Liquibase выполняются полный `compileall` и pytest. Точные пути — фильтр `python-checks` в `.pre-commit-config.yaml`. Python берётся из проектного `.venv`, независимо от активного окружения терминала. Отсутствие окружения или неуспешная проверка блокирует коммит. Изменения только документации не запускают тяжёлый Python-прогон. Smoke и локальный Playwright выполняются по регламенту [16-working-process.md](./16-working-process.md) §5.

Сообщение коммита должно соответствовать формату из [16-working-process.md](./16-working-process.md) §3, например `infra(git): добавить проверки коммитов`. Если hook отклонил сообщение, исправить его и повторить коммит.

### 7.2. Проверка секретов

`detect-secrets` проверяет новые токены и пароли без сетевой верификации (`--no-verify`). `.secrets.baseline` содержит хеши пяти проверенных известных значений: алфавит кодов привязки Telegram, реквизиты локальной БД в конфигурации и Docker, два пароля E2E-стенда. Это точечные исключения по файлу и значению; новые значения в тех же файлах проверяются. `package-lock.json` исключён из этой проверки из-за хешей пакетов; остальные проверки файла сохраняются.

При срабатывании удалить настоящий секрет из изменения. Ложное срабатывание разобрать вручную; не обновлять baseline автоматически ради прохождения hook. Содержимое секретов в baseline не сохраняется. Если hook обновил номера строк существующих исключений, проверить diff и добавить baseline в индекс перед повторным запуском.

### 7.3. Серверные проверки

`.github/workflows/tests.yml` запускается при push в `master`, для pull request и вручную через GitHub Actions. Задания:

- `Quality checks` — валидация конфигурации hooks и статические проверки всех отслеживаемых файлов; `python-checks` здесь пропускается, поскольку тесты запускаются отдельным заданием.
- `Unit tests` — компиляция и полный pytest на Python 3.13.
- `E2E (Playwright)` — существующий браузерный набор на Node.js 22; при ошибке сохраняются артефакты стенда.

Workflow имеет только право чтения содержимого репозитория, отменяет предыдущий прогон того же ref при новом запуске и ограничивает длительность заданий. Настройки защиты ветки не устанавливаются YAML-файлом: в GitHub для `master` следует сделать эти три проверки обязательными и запретить force push. До включения защиты ветки неуспешный CI сообщает об ошибке, но сам не запрещает merge. Реальные миграции PostgreSQL и детерминированный smoke пока не входят в этот этап.

### 7.4. Markdown и OpenAPI

Hook Markdown проверяет относительные ссылки на файлы и якоря в заголовках всех изменённых `.md`; внешние HTTP(S)-ссылки не запрашиваются, чтобы коммиты не зависели от доступности сторонних сайтов. Полный набор Markdown-файлов проверяется заданием `Quality checks` в CI.

Фактический API-контракт — `openapi/openapi.json`. Он содержит только маршруты `/v1`, не веб-страницы, и генерируется из FastAPI. После изменения API-маршрутов, моделей запроса или ответа обновите его из корня:

```powershell
.venv\Scripts\python.exe tools\export_openapi.py
```

Проверить, что снимок не устарел: `.venv\Scripts\python.exe tools\export_openapi.py --check` или `npm run check:openapi`. Hook отклонит изменения API при устаревшем контракте. `npm run lint:openapi` выполняет Redocly с минимальным набором правил, проверяющим корректность OpenAPI. Правила, требующие глобальной схемы безопасности и URL production-сервера, выключены в `redocly.yaml`: аутентификация API основана на cookie-сессии и пока не описана в OpenAPI как `securityScheme`.

Для pull request CI сравнивает `openapi/openapi.json` с `origin/<base branch>` через oasdiff и останавливает merge при ошибках совместимости. Сравнение начнёт работать после попадания первого контракта в базовую ветку; до этого GitHub job завершается успешно с пояснением. Локально эта проверка не выполняется, потому что oasdiff запускается в изолированном GitHub runner; Redocly и проверка синхронизации контракта выполняются при коммите.
## Подключение Т-Инвестиций

Установить зависимости `pip install -r requirements.txt` в `.venv`. Шаблон `.env.example` содержит `BROKER_TOKEN_KEY_ID=v1` и пустую строку `BROKER_TOKEN_KEYS=`. Перед запуском в локальном `.env` заполнить `BROKER_TOKEN_KEYS=v1:<base64 от 32 случайных байт>`. Пример генерации ключа: `.venv\Scripts\python.exe -c "import base64,os; print(base64.b64encode(os.urandom(32)).decode())"`. Хранить ключ отдельно от дампа БД; при его потере сохранённые токены не расшифруются. `.env` исключён из git. После настройки запустить миграции Liquibase обычным способом, затем приложение. В Настройках доступно подключение Т-Инвестиций, обновление портфеля выполняется вручную; фонового задания нет.

В Настройках выберите карточку рабочего подключения или Sandbox и сохраните её токен. Для рабочего контура нужен readonly-токен, для песочницы — Sandbox token. REST-адреса различаются: `https://invest-public-api.tbank.ru/rest/` и `https://sandbox-invest-public-api.tbank.ru/rest/` ([документация](https://developer.tbank.ru/invest/intro/developer/protocols/)); приложение выбирает адрес автоматически и не принимает произвольный URL. Существующие подключения после миграции остаются рабочими. Песочница подключается и без тестовых счетов; их создание и пополнение теперь доступны внутри приложения — см. [управление счетами песочницы](#управление-счетами-песочницы). Для получения календаря наличие счёта не требуется. После миграции 038 оба контура хранятся независимо; подключение или замена одного сохраняет счета и снимки другого. Новых переменных .env нет. После обновления кода примените миграции и перезапустите приложение и наблюдатель.

Клиент Т-Инвестиций проверяет TLS по системным доверенным центрам и включённому в проект корневому сертификату Минцифры из [официального источника Госуслуг](https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt). Отключать проверку сертификата для подключения не требуется. Если сертификат Минцифры будет перевыпущен, файл `app/brokers/certs/russian_trusted_root_ca.pem` и закреплённый отпечаток в `app/brokers/certificates.py` нужно обновить из официального источника и проверить перед выпуском приложения.

При ошибке подключения 502/503 любой авторизованный пользователь может запустить восстановление кнопкой в `/settings/brokers`. Администратор также может выполнить `.venv\Scripts\python.exe -m scripts.repair_t_invest_certificate` из корня проекта или задачу «Проверить сертификат Т-Инвестиций» в `/admin`. Скрипт запускается **по требованию**, не по расписанию: скачивает корневой сертификат с Госуслуг, сверяет закреплённый SHA-256 отпечаток, атомарно сохраняет копию в `.runtime/certs/` и проверяет TLS-вызов API без пользовательского токена. Папка `.runtime/` исключена из git. Доверие добавляется только этому приложению, без установки корневого сертификата в Windows или контейнер. Приложение подхватывает файл при следующем запросе без перезапуска. Успешная проверка TLS не подтверждает права или действительность токена; если ошибка сохраняется, изучите лог запуска задачи и ответ API.

## Проверка исходов Top-5

Сначала применить миграции по §1. Новые завершённые анализы батчей сохраняют снимки автоматически. Само наблюдение запускается отдельным процессом, независимо от числа веб-воркеров:

```powershell
.venv\Scripts\python.exe -m scripts.evaluate_top5
.venv\Scripts\python.exe -m scripts.evaluate_top5 --loop --interval 300 --limit 100
```

Первый вариант — один проход, второй — непрерывно каждые 5 минут. interval >= 30 секунд, limit — 1–1000 снимков за проход; после простоя обработка продолжается с сохранённого курсора. В админке карточка «Проверить исходы Top-5» содержит лимит 1–1000, интервал от 30 секунд (по умолчанию 300) и переключатель «Проверять непрерывно», по умолчанию выключенный. Без переключателя выполняется один проход, интервал не применяется. При включённом переключателе процесс повторяет проверки: интервал — пауза после окончания предыдущего прохода. Такой запуск не ограничивается общим таймаутом разовых скриптов и работает до кнопки «Остановить» или перезапуска сервиса. Он занимает отдельную очередь: не блокирует актуализацию рынка и разовые задачи, второй наблюдатель из админки одновременно не запускается. Выбранные параметры сохраняются в истории запуска; для изменения интервала остановить процесс и запустить с новыми значениями. В начале лога выводятся режим, интервал и лимит; вывод фоновой задачи сохраняется регулярно, даже когда новых строк нет. Новых переменных окружения нет.

Процесс читает завершённые часовые свечи и [машиночитаемый календарь MOEX](https://www.moex.com/files/4rkd3yjkghfhqz4h7g8rewetx4): /calendars/stock и /calendars/futures, off_days и session_schedule. При недоступном/неполном календаре автоматический исход не определяется; отсутствие ожидаемой свечи также требует проверки покрытия. Доступ к этим данным проверять из окружения запуска. При HTTP 401/403 или HTML-странице MOEX «Информация доступна только подписчикам» (в том числе с HTTP 200) причина проверки: «Календарь MOEX требует авторизации». Это ограничение доступа к календарю; повторный проход без настройки доступа его не устраняет. Прочий некорректный ответ не считается доказательством требования авторизации. Состояние сценария сохраняется, полнота и расписание остаются неподтверждёнными. Вместо ручного календаря реализован автоматический источник через подключение Т-Инвестиций, описанный ниже.

Тот же проход создаёт очередь уведомлений и доставляет веб/Telegram по включённым подпискам. Telegram использует существующие настройку бота и привязку пользователя. До 5 попыток с увеличением паузы; сетевой сбой с неопределённым результатом может привести к повторной доставке. Старые события при подписке не рассылаются, торговые поручения не создаются. Для наблюдения за исходами открытия браузера недостаточно: процесс должен работать. Интерфейс — [14-web-interface.md](./14-web-interface.md#исходы-сценариев-top-5).

При наличии подключения Т-Инвестиций у владельца исходного анализа наблюдатель автоматически запрашивает календарь через него; используется сохранённый контур, в том числе sandbox. Чужие токены не подставляются. Без подключения сохраняется путь ISS. При ошибке выбранного брокера автоматического переключения на ISS нет: причина видна в исходе, полнота остаётся неподтверждённой. Расписание загружается при проходе, отдельный скрипт и ручная недельная сверка не нужны; поддерживаемые типы сессий и ограничения — [09](./09-strategy-engine.md#наблюдение-за-сценариями-top-5). Подключение токена не запускает новый платный LLM-анализ и не исправляет старые unsupported-планы.

## Обновление внешних OpenAPI Т-Инвестиций

Назначение снимка и его отличия от API приложения — [10-api-specification.md](./10-api-specification.md#внешний-rest-контракт-песочницы-т-инвестиций). Из корня проекта проверить сохранённый YAML:

```powershell
npx --no-install redocly lint docs/openapi/t-invest-sandbox.openapi.yaml docs/openapi/t-invest-production.openapi.yaml
```

Используются закреплённые npm-зависимости проекта; если CLI отсутствует, сначала выполнить `npm ci`. Проверка структуры и ссылок не вызывает операции брокера и не требует токена. Этот внешний YAML не генерируется командой `npm run export:openapi`, которая обновляет только контракт NewsTrader.

Для обновления:

1. Получить `src/docs/swagger-ui/openapi.yaml` из официального репозитория RussianInvestments/investAPI; закрепить конкретный commit, вычислить SHA-256 полученных байтов, сохранить дату получения в `x-news-trader-source`. Плавающая ветка main не заменяет commit снимка.
2. Сверить состав REST-песочницы с официальным сравнением контуров. Применить фильтр путей из `excluded_paths` соответствующего профиля и оставить только его сервер. В sandbox исключаются недоступные методы; в production SandboxService вынесен в отдельный профиль. Потоковые сервисы не входят в оба REST-профиля. Если доступность метода изменилась, обновить фильтр и объяснение в YAML.
3. Сохранить структуры включённых операций без переписывания типов. Вычислить транзитивное замыкание `$ref` от оставшихся путей и удалить недостижимые схемы; сохранить Bearer security scheme. Обновить описания тегов, метаданные источника и атрибуцию при изменении лицензии.
4. Проверить, что все `$ref` локальны и разрешаются, operationId уникальны, сохранённые операции и схемы совпадают с исходными, сервер соответствует выбранному контуру и нет секретов. Прогнать Redocly без ошибок и предупреждений, проверить diff и поднять версии затронутых документов по правилам проекта.

Для загрузки, сборки и проверки этого снимка не нужны пользовательские токены, создание счетов или торговые запросы.

## Управление счетами песочницы

После обновления применить миграции штатной командой из §1 (нужны миграции 037 и 038), затем перезапустить приложение. Новых зависимостей, .env-переменных и фоновых скриптов нет. Подключить Sandbox token по разделу выше, раскрыть подключённую карточку Sandbox. UI и маршруты — [14](./14-web-interface.md#управление-счетами-песочницы), быстрый сценарий — [17](./17-quickstart.md#управление-тестовым-счётом).

Пополнение в MVP — только виртуальные RUB, положительная сумма до копейки (точка или запятая). Брокерские лимиты проверяет брокер; отказ сохраняется в журнале. Закрытие удаляет тестовый счёт и его данные у брокера; выбрать подтверждение и подтвердить диалог. Рабочий контур остаётся readonly. Создание и синхронизация не выбирают портфельный счёт автоматически: выбор выполняется в плашке портфеля той же страницы Настроек.

Изменяющие RPC отправляются один раз без сетевых повторов. При unknown не повторять пополнение вслепую: обновить счета и сверить остаток. Новый клик после загрузки страницы получает новый ключ и является новым действием. Гарантия exactly-once у брокера не заявляется. При sync_failed внешний успех уже зафиксирован: нажать «Обновить счета», не создавать/пополнять повторно.

Pending блокирует смену подключения, отключение, обновление портфеля и другие изменения того же подключения. Таймаут RPC — 15 секунд; страховочная аренда блокировки — 120 секунд. Если процесс прерван, после 120 секунд страница показывает результат неизвестным, а следующий успешный POST синхронизации/изменения подключения сохраняет unknown и снимает устаревшую блокировку. Не снимать её вручную во время выполняющегося запроса. Чтение календаря не блокируется. Аудит хранится отдельно от портфельных снимков — [07](./07-data-model.md#действия-песочницы).

Подключение и замена токена теперь выполняются на отдельной странице: в Настройках выбрать пункт «Брокеры и торговля». Формы возвращают туда же. Старая ссылка на секцию продолжает работать через перенаправление; описание интерфейса — [14](./14-web-interface.md#отдельная-страница-настроек-брокеров). Перенос не требует миграций и новых переменных окружения; после обновления перезапустить веб-приложение.

Управление рабочими счетами использует прежнее readonly-подключение; дополнительных миграций, ключей или фоновых задач не требуется. После обновления перезапустить приложение. Состав плашки и актуальность балансов — [14](./14-web-interface.md#управление-рабочими-счетами).

## Карточки брокеров и оформление

После обновления применить миграцию 038 штатным запуском Liquibase из §1 и перезапустить приложение; существующий токен и его снимки сохраняются. Новых .env-переменных, фоновых заданий и зависимостей нет. Обновить также процесс наблюдателя: при двух подключениях календарь использует рабочий контур владельца, иначе Sandbox. Настройка цвета и фона доступна через ✎ и сохраняется в БД; включать эту таблицу в штатные резервные копии. ## Обновление портфеля внутри карточки

После обновления кода перезапустить приложение и обновить страницу браузера. Новых зависимостей, миграций, переменных .env или фоновых задач нет. Выбор счёта и ручное обновление выполняются внутри открытой карточки; время данных берётся из серверного снимка. Сценарии ошибок и возврата к работе — [14](./14-web-interface.md#обновление-портфеля-без-перезагрузки).

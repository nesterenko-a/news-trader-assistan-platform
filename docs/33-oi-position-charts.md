# 33. Графики позиций физических и юридических лиц по OI

**Статус:** утверждено v1.2 (графики OI и раздельное число лиц в лонге/шорте)
**Система:** NewsTrader Assistant
**Очередность:** следующая задача к реализации.

## 1. Цель и обоснование

На вкладке OI страницы `/indicators` добавить наглядную динамику нетто-позиций физических и юридических лиц по образцу трёх скриншотов пользователя (общий вид и два увеличенных фрагмента одного графика). Пользователь выбирает группу и период, видит преобладание длинных или коротких позиций и изменение относительно предыдущей торговой даты.

## 2. Сценарии и интерфейс

- UC-33-01: открыть OI выбранного фьючерса и блок графика над существующими карточками позиций по датам.
- UC-33-02: переключить «Физические лица / Юридические лица»; график и показатели пересчитываются для выбранной группы. По умолчанию — физические лица.
- UC-33-03: выбрать период графика «1м / 3м / 6м / 1г / 3г / Всё» или «Свой период» через существующие поля ОТ/ДО. Быстрые периоды меняют только новый график и его карточки; прочие графики и список дат сохраняют действующий диапазон ОТ/ДО. При выборе «Свой период» новый график использует эти даты. Быстрые периоды отсчитываются от последней доступной даты выбранной группы, чтобы поддерживать архивные контракты; по умолчанию — 1г. Показывать фактический диапазон и число наблюдений.
- UC-33-04: навести на график и увидеть дату, long, short, net и скользящую среднюю; на узком экране показатели переносятся на несколько строк.

Над графиком — карточки «Шорт», «Лонг», «Нетто», «Доля шорта», «Лиц в лонге», «Лиц в шорте», «Перцентиль доли шорта». Значения относятся к последней доступной дате выбранного периода; изменения числа контрактов и лиц — к предыдущему доступному наблюдению той же группы. Число лиц брать из отдельных полей источника MOEX, а не вычислять из числа контрактов. При отсутствии значения на текущую или предыдущую дату соответствующее значение или изменение отображать прочерком.

График: фиолетовая линия net, заметная нулевая ось, зелёная заливка между положительным net и нулём, красная — между отрицательным net и нулём; пунктирная золотистая средняя с легендой «Средняя, 30 наблюдений»; последняя точка выделена. Подпись для физических лиц: «Выше нуля — физлица в лонге, ниже нуля — физлица в шорте»; для юридических лиц — аналогично «юрлица». Подсказка поясняет, что речь о нетто-позиции группы; на нуле лонг и шорт равны. Ось Y — контракты, X — даты. Карточки записей по датам и существующие графики остаются доступны.

## 3. Требования и расчёты

- FR-33-01: net = long − short; доля шорта = short / (long + short) × 100%. При нулевом знаменателе — «Нет данных».
- FR-33-02: средняя net — арифметическое среднее последних 30 доступных наблюдений включительно с текущим; до накопления 30 точек линия отсутствует. Расчёт предшествует обрезке выбранного периода.
- FR-33-03: перцентиль последней доли шорта — доля валидных наблюдений за скользящие 12 календарных месяцев по дату последнего наблюдения включительно, у которых доля шорта не выше текущей. Подсказка раскрывает формулу и фактическое число наблюдений. Для менее двух наблюдений — «Недостаточно данных». Рядом с долей шорта — медиана за то же окно. Расчёт делается по полной сохранённой истории выбранной группы до обрезки видимого периода.
- FR-33-04: отсутствующие значения группы не подменять нулями; пропуски показывать разрывом, метрики без данных — прочерком. Пустая история и единственная точка отображаются корректно.
- FR-33-05: показывать дату актуальности и пояснение, что позиции групп агрегированы по базовому активу, а не только по выбранному контракту. Период «Всё» означает доступную сохранённую историю; автоматическое скачивание многолетней истории в этот срез не входит.
- FR-33-06: хранить число лиц в лонге и шорте раздельно для физических и юридических лиц. Ноль участников отличать от отсутствующих данных. Не складывать эти показатели в число уникальных участников без подтверждённой методики источника.

## 4. Данные, API и архитектура

Использовать существующие `MarketOpenPositionClientGroup` и `client_groups_series` из `app/market/oi_data.py`: даты и physical/juridical long/short/net/participants. Источник и особенности агрегации — [19-market-indicators.md](./19-market-indicators.md) §8.14; модель — [07-data-model.md](./07-data-model.md).

Расширить существующую таблицу nullable-полями `participants_long` и `participants_short` с миграцией Liquibase и соответствующим изменением SQLAlchemy-модели. Загрузчик читает `PhysicalLong`/`PhysicalShort` и `JuridicalLong`/`JuridicalShort` из блока количества лиц (`payload[3]`) в ответе OpenOptionService, отдельно от блока контрактов (`payload[0]`). Отсутствующее поле сохраняется как NULL; достоверный ноль — как 0.

Существующее поле `participants` фактически заполняется количеством лиц в лонге. Сохранить его для совместимости; при миграции перенести положительные сохранённые значения в `participants_long`, а прежние нули без подтверждения источником оставить NULL. `participants_short` для старых записей остаётся NULL до повторной загрузки. Синхронизация должна обновлять новые поля и у существующих записей, включая достоверные нули, чтобы повторный запуск штатного `update_oi` мог заполнить доступную историю; новых скриптов не требуется. Число лиц в шорте за дату, уже недоступную в источнике, не восстанавливать расчётом из контрактов.

Загрузчик больше не подменяет отсутствующие `long` или `short` контрактов нулём: неполную группу за дату не создаёт, а существующую запись меняет только при полном ответе источника. В `client_groups_series` отсутствующая группа передаётся как отсутствие данных; прежняя подстановка `{long: 0, short: 0, net: 0}` удаляется. Существующие карточки и API должны показать прочерк вместо ложного нуля, а показатели, зависящие от двух групп, — отсутствие данных. Для старых строк с прежним искусственным нулём достоверность нельзя установить без повторной синхронизации; интерфейс не должен заявлять, что такая история проверена.

Метрики рассчитываются в чистой функции с тестами по полной сохранённой истории; отображаемый период применяется после расчёта средней и годового окна перцентиля. Веб передаёт графику выбранный ряд и показатели. Выбор группы и периода передаётся параметрами страницы `/indicators`, переключение перезагружает страницу с сохранением выбранного тикера; новые API-эндпоинты не требуются. В ответ существующего `/v1/indicators/oi?client_groups=1` добавить nullable-поля `participants_long` и `participants_short` внутри каждой имеющейся группы, сохранив прежние поля. Актуализировать API-документацию и OpenAPI-контракт в применимой части.

Использовать существующий подход проекта — серверная подготовка рядов и SVG в шаблоне — и общие стили; отдельной библиотеки графиков на текущей странице нет. Для наведения и клавиатурного фокуса сделать читаемую подсказку даты и значений; на сенсорном экране дать доступ к значениям выбранной точки. Новый внешний сервис не подключать. Фильтр графика не меняет выбранный инструмент. При переключении индикатора или инструмента график пересоздаётся вместе со страницей, без сохранения устаревшего состояния.

## 5. Приёмка и проверки

Проверить обе группы, все периоды, положительный/отрицательный net и переход через ноль, подсказки, адаптивность, пустые/неполные ряды, среднюю и перцентиль на фиксированных данных. Проверить раздельный разбор числа лиц в лонге/шорте, миграцию старых данных, повторную синхронизацию существующих записей, нули и NULL, дневные изменения и совместимость API. Добавить Python-тесты расчётов и загрузки, актуализировать Playwright-тесты OI. Выполнить pytest, compileall, smoke, Playwright и проверки OpenAPI.

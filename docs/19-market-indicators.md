Требование FR-04-02 (приоритет P0) из [04-functional-requirements.md](./04-functional-requirements.md): система должна рассчитывать технические индикаторы — RSI, MACD, скользящие средние, уровни поддержки/сопротивления, волатильность.

- единый контракт и реестр позволяют добавлять/тестировать/калибровать индикаторы независимо;
- реализация без тяжёлых внешних зависимостей (ta-lib/pandas-ta не подключаем): формулы стандартные, код свой.

## 2. Цели и не-цели

**Цели:**
- пакет `app/market/indicators/` с единым контрактом и реестром;
- 11 индикаторов по утверждённому списку;
- REST API `/api/indicators/*` и веб-страница `/indicators`;
- интеграция в движок стратегий (новые техсигналы) и бэктест.

**Не-цели (в рамках этого ТЗ):**
- не заменяем существующие `sma/rsi/volatility` — они мигрируют в пакет с сохранением интерфейса (тонкая обёртка-реэкспорт остаётся);
- индикаторы не дают «советов»: выдают только расчётные значения и сигналы по порогам;
- историю расчётов в БД не храним — расчёт on-the-fly из свечей;
- индикаторы не являются инвестиционными рекомендациями (дисклеймер как у вердиктов);
- индикаторы VWAP, Ichimoku, свечные паттерны, Williams %R, Supertrend в этот этап **не входят** (могут быть добавлены отдельным ТЗ).

- Каждый модуль — чистая функция расчёта: вход — список свечей (объекты с атрибутами `date, open, high, low, close, volume` или dict-совместимые) + параметры; выход — `IndicatorResult`.
- Расчёт только по фактическим датам свечей (MOEX не торгует в праздники) — окна строятся по имеющимся свечам, без «пустых» дней.

- Модули не ходят в БД сами: данные загружает вызывающий слой (API/web/движок) через существующий `app/market/prices.py`.

## 4. Единый контракт индикатора

```python
@dataclass
class IndicatorValue:
    date: date
    value: float | None          # None — позиция «не прогрета» (недостаточно истории)

@dataclass
class IndicatorSignal:
    date: date
    kind: str                    # машинный ключ, например "cross_up", "overbought", "breakout"
    severity: str                # "info" | "warning" | "strong"
    note: str                    # человекопонятное описание на русском

@dataclass
class IndicatorResult:
    indicator: str               # имя индикатора (ключ реестра)
    params: dict                 # фактически применённые параметры
    values: list[IndicatorValue]
    signals: list[IndicatorSignal]
    meta: dict                   # число свечей, окно дат, ограничения (например, "мало данных")
```

Правила контракта:
- параметры валидируются (период > 0, разумные диапазоны); невалидные → исключение/ошибка 422 в API;
- недостаточно данных → пустые/частичные `values`, причина в `meta` (не ошибка);
- сигналы формируются по фиксированным порогам индикатора (см. ТЗ ниже), пороги калибруются отдельно (как веса факторов).

## 5. REST API (дизайн)

Эндпоинты (полная спецификация — в [10-api-specification.md](./10-api-specification.md) на этапе реализации):

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/v1/indicators` | Список индикаторов: имя, описание, параметры по умолчанию, сложность |
| GET | `/v1/indicators/{name}` | Расчёт индикатора |

Пути указаны с учётом префикса API проекта (`/v1`, см. [10-api-specification.md](./10-api-specification.md)).

Параметры `GET /v1/indicators/{name}`:
- `ticker` или `security_id` — бумага (обязательный);
- `from`, `to` — диапазон дат (опц., по умолчанию — доступная история);
- `limit` — ограничение числа свечей (опц., защита от тяжёлых запросов);
- параметры индикатора по именам из реестра (`period`, `fast`, `slow`, `k`, …).

Ответ: JSON-представление `IndicatorResult`:

```json
{
  "indicator": "macd",
  "params": {"fast": 12, "slow": 26, "signal": 9},
  "values": [{"date": "2026-05-14", "value": 12.4}, "..."],
  "signals": [{"date": "2026-05-14", "kind": "cross_up", "severity": "warning", "note": "MACD пересекла сигнальную линию снизу вверх"}],
  "meta": {"candles": 300, "from": "...", "to": "...", "limits": []}
}
```

Ошибки: `404` — неизвестный индикатор; `422` — невалидные параметры; `400` — нет данных по бумаге/периоду. Аутентификация — по текущим правилам API (уточняется на этапе реализации).

**Особенность OI:** значения для `oi` берутся не из `MarketCandle`, а из таблицы `market_open_positions` (см. §7); цена для сигналов — из `MarketCandle` по тем же датам. Контракт ответа (`values`/`signals`) — общий.

**Список фьючерсов:** `GET /v1/indicators/futures[?q=...]` возвращает все фьючерсы срочного рынка MOEX (`secid`, `shortname`, `assetcode`, `lastdeldate`, `prevopenposition`); используется админкой для выбора тикера при загрузке OI (кэш 1 час).

## 6. Веб-интерфейс (дизайн)

- Страница `/indicators`: выбор индикатора, бумаги, диапазона и параметров; график значений (тот же JS-график, что на карточке бумаги) + таблица сигналов.
- **Правило отображения в UI (обязательное):** каждый индикатор, зарегистрированный в реестре `app/market/indicators/registry.py`, автоматически получает **вкладку на странице `/indicators`** (навигация строится из `REGISTRY` — ключ, заголовок). При добавлении нового индикатора его раздел на `/indicators` (форма параметров + график/таблица сигналов) добавляется вместе с модулем — это критерий приёмки любого нового индикатора (см. [14-web-interface.md](./14-web-interface.md), раздел «Индикаторы»).
- Опционально (фаза 6): компактный блок с ключевыми индикаторами на карточке бумаги.
- Дизайн страницы фиксируется на этапе реализации и описывается в [14-web-interface.md](./14-web-interface.md).

### 6.1. UI-требования: индикатор OI (страница `/indicators`, раздел «Открытый интерес»)

*Реализовано (см. [14-web-interface.md](./14-web-interface.md)): форма выбора фьючерса/периода/порога, график OI+цена (две линии), график изменения OI (столбцы с нулевой осью), таблица сигналов; пропуски — разрывы линии.*

- Выбор фьючерсного тикера (SECID, например W4V6), диапазон дат, параметр `oi_change_threshold_pct`.
- **График 1 — OI и цена:** линия OI (ось слева, подпись «контракты») + линия close (ось справа) на общей временной шкале — для визуального поиска дивергенций «цена × OI».
- **График 2 — изменение OI:** `oi_change_pct` (столбцы/линия) с нулевой осью.
- **График 3 — объём торгов:** столбцы объёма (абсолютные значения, от нижней линии) — визуальное подтверждение/ослабление сигналов «цена × OI» (рост объёма подтверждает, падение — «движение на излёте»).
- **Таблица сигналов:** дата, тип (Strong Bull / Strong Bear / Bearish Setup / Bullish Setup / Long Liquidation / Short Covering), важность, **объём** (значение в день сигнала, изменение в % и интерпретация «подтверждает движение» / «движение на излёте»), трактовка. Трактовки со стрелками направления: ↑ — рост, ↓ — падение, → — без изменений (например, «Цена растёт ↑, OI растёт ↑ — набор + длинных позиций»). «Важность» у Strong Bear (открытие коротких позиций) — красным, у остальных сильных сигналов — зелёным, у предупреждений — жёлтым.
- Пропуски в ряду OI (нет публикации/торгов) отображаются как пропуски, не как ноль.
- Страница общая для всех индикаторов; разделы других индикаторов добавляются по мере реализации (см. [14-web-interface.md](./14-web-interface.md)).
- **Раздел Volume Profile на `/indicators` (реализовано, см. §8.13):** форма «тикер + период» (1M/2M/3M/6M/1Y), горизонтальный профиль объёма (POC подсвечен, линии VAH/VAL), легенда POC/VAH/VAL и таблица сигналов (POC, Value Area, HVN, LVN с трактовками).

## 7. Модель данных

- Для 11 индикаторов, рассчитываемых из цен: on-the-fly из `MarketCandle` (daily, OHLCV) — новая таблица не требуется. Кэш не вводим: дневные свечи, расчёт быстрый.
- **Исключение — OI:** это внешние сырые данные (не расчёт), их нужно скачивать и хранить. Новая таблица `market_open_positions` (миграция Liquibase + модель SQLAlchemy):

  | Колонка | Тип | Назначение |
  |---|---|---|
  | id | int PK | |
  | security_id | FK → securities.id | фьючерсный контракт (по SECID) |
  | trading_date | date | дата торгов |
  | open_position | bigint | открытые позиции, контрактов (ISS `OPENPOSITION`) |
  | open_position_value | numeric | открытые позиции, руб. (ISS `OPENPOSITIONVALUE`, опц.) |
  | source | varchar | `iss` (для будущих источников) |

  Уникальный ключ (security_id, trading_date). Наполнение — `scripts/update_oi.py` (по аналогии с `update_prices`, с кэшем запросов ISS и повторными попытками).
- Параметры индикаторов передаются в вызове, в БД не хранятся.

## 8. ТЗ на индикаторы

Общие критерии приёмки для каждого индикатора:
- юнит-тесты на синтетических данных с известными эталонными значениями (ручной расчёт или сверка с pandas-ta/ta-lib в тестах-комментариях);
- детерминизм и обработка недостатка данных (None/пусто + `meta`);
- регистрация в реестре и доступность через API;
- описание и параметры в документации (10, 14, 17-quickstart) + статус в [12-roadmap.md](./12-roadmap.md).

### 8.1. EMA — экспоненциальная скользящая средняя

**Статус:** реализован (модуль `app/market/indicators/ema.py`, реестр/API `/v1/indicators/ema`, веб-вкладка; параметры `fast`/`slow`; сигналы `cross_up`/`cross_down`).

**Обоснование:** базовая СС с большим весом свежих цен; «кирпич» для MACD и Боллинджера; сейчас в проекте только SMA.

**Формула:** α = 2 / (N+1); seed: EMA первых N значений = SMA(N); далее EMAₜ = Cₜ·α + EMAₜ₋₁·(1−α).

**Параметры:** `period` = 20 (типовые 12/26/50/200).

**Сигналы:** пересечение двух EMA (`ema_fast`/`ema_slow`): `cross_up` / `cross_down` (golden/death cross).

**Сложность:** просто.

**Roadmap:** 1) модуль + тесты; 2) валидация на данных MOEX; 3) реестр/API; 4) веб; 5) интеграция в движок стратегий (EMA50/200 как техсигналы); 6) документация и статус.

### 8.2. MACD — схождение/расхождение скользящих средних

**Статус:** реализован (модуль `app/market/indicators/macd.py`, реестр/API `/v1/indicators/macd`, веб-вкладка; параметры `fast`/`slow`/`signal`; сигналы `cross_up`/`cross_down`, `hist_positive`/`hist_negative`; интеграция в движок — техсигнал направления тренда, см. [09-strategy-engine.md](./09-strategy-engine.md) §4.1).

**Обоснование:** закрывает P0 FR-04-02; классический тренд-осциллятор, используется в стратегиях как фильтр направления.

**Формула:** MACD = EMA(fast) − EMA(slow); signal = EMA(signal) от MACD; hist = MACD − signal.

**Параметры:** `fast` = 12, `slow` = 26, `signal` = 9.

**Сигналы:** `cross_up` / `cross_down` (MACD × signal); `hist_positive` / `hist_negative` (знак гистограммы). Дивергенции MACD/цены — отдельная задача (не в этом этапе).

**Сложность:** просто.

**Roadmap:** 1) модуль + тесты (включая сверку с эталоном); 2) валидация; 3) реестр/API; 4) веб; 5) интеграция в движок (направление тренда в техсигналах) — **реализовано**; 6) документация и статус — **реализовано**.

### 8.3. Полосы Боллинджера

**Статус:** реализован (модуль `app/market/indicators/bollinger.py`, реестр/API `/v1/indicators/bollinger`, веб-вкладка; интеграция в движок стратегий — зоны перекупленности/перепроданности цены относительно upper/lower как сдерживающий фактор, kind `bollinger`).

**Обоснование:** волатильность вокруг среднего + зоны перекупленности/перепроданности по цене; входит в блок «волатильность» FR-04-02.

**Формула:** middle = SMA(N); σ — стандартное отклонение (популяционное) за окно; upper = middle + k·σ; lower = middle − k·σ; %B = (C − lower) / (upper − lower); bandwidth = (upper − lower) / middle.

**Параметры:** `period` = 20, `k` = 2.

**Сигналы:** `touch_upper` / `touch_lower` (C пересекает полосу), `revert_in` (возврат внутрь полос), `squeeze` (bandwidth ниже порога — сжатие, предвестник движения; порог = 10-й процентиль bandwidth за окно).

**Сложность:** просто.

**Roadmap:** 1) модуль + тесты — **реализовано**; 2) валидация — **реализовано**; 3) реестр/API — **реализовано**; 4) веб — **реализовано**; 5) движок (зоны перекупленности как сдерживающий фактор) — **реализовано**; 6) документация и статус — **реализовано**.

### 8.4. Parabolic SAR

**Обоснование:** точки разворота тренда; удобен для стоп-уровней в бэктесте и бумажной торговле.

**Формула (итеративная):** SARₜ₊₁ = SARₜ + AF·(EP − SARₜ), где AF стартует с 0.02, растёт на 0.02 при каждом новом экстремуме EP до максимума 0.2; EP — экстремальная цена текущего тренда (максимум в аптренде, минимум в даунтренде); при пробое SAR ценой — разворот: SAR перепрыгивает на противоположную сторону, AF сбрасывается на 0.02.

**Параметры:** `af_step` = 0.02, `af_max` = 0.2.

**Сигналы:** `flip_up` / `flip_down` (разворот направления), `above` / `below` (SAR относительно цены — тренд).

**Сложность:** средне (аккуратная итеративная логика разворотов, edge-кейсы на старте).

**Roadmap:** 1) модуль + тесты (синтетика с известными разворотами); 2) валидация; 3) реестр/API; 4) веб; 5) движок/бэктест (стоп-уровни); 6) документация и статус.

### 8.5. Stochastic %K/%D

**Обоснование:** зоны перекупленности/перепроданности в боковике — дополняет RSI (RSI лучше работает в тренде).

**Формула:** %K = (C − Lₙ) / (Hₙ − Lₙ) · 100 (n = 14); %D = SMA(3) от %K.

**Параметры:** `k_period` = 14, `d_period` = 3, `smooth` = 1.

**Сигналы:** `overbought` (≥ 80), `oversold` (≤ 20), `cross_up` / `cross_down` (%K × %D).

**Сложность:** просто.

**Roadmap:** 1) модуль + тесты; 2) валидация; 3) реестр/API; 4) веб; 5) движок (осцилляторный сигнал); 6) документация и статус.

### 8.6. CCI — индекс товарного канала

**Обоснование:** циклические экстремумы и дивергенции; стандартные уровни ±100.

**Формула:** TP = (H + L + C) / 3; CCI = (TP − SMA(TP, n)) / (0.015 · MD), где MD — среднее абсолютное отклонение TP от SMA за окно.

**Параметры:** `period` = 20.

**Сигналы:** `overbought` (> +100), `oversold` (< −100), `revert` (возврат в коридор через ±100).

**Сложность:** просто.

**Roadmap:** 1) модуль + тесты; 2) валидация; 3) реестр/API; 4) веб; 5) движок (при необходимости); 6) документация и статус.

### 8.7. ROC — скорость изменения цены

**Обоснование:** простой моментум-фильтр (темп изменения за N периодов); полезен как ранний сигнал и в бэктесте.

**Формула:** ROCₜ = (Cₜ − Cₜ₋ₙ) / Cₜ₋ₙ · 100.

**Параметры:** `period` = 10.

**Сигналы:** `positive` / `negative` (знак моментума), `extreme` (выход за порог, напр. |ROC| > 10 — калибруется).

**Сложность:** просто.

**Roadmap:** 1) модуль + тесты; 2) валидация; 3) реестр/API; 4) веб; 5) движок (моментум-фильтр); 6) документация и статус.

### 8.8. ATR — средний истинный диапазон

**Статус:** реализован (модуль `app/market/indicators/atr.py`, реестр/API `/v1/indicators/atr`, веб-вкладка; интеграция в движок — информационный сигнал волатильности `atr_pct`, kind `atr`).

**Обоснование:** мера волатильности; нужен для стопов/риск-параметров (paper trading, бэктест, размер позиции). Требует high/low — они есть в `MarketCandle`.

**Формула:** TRₜ = max(Hₜ − Lₜ, |Hₜ − Cₜ₋₁|, |Lₜ − Cₜ₋₁|); ATR — сглаживание Уайлдера (n = 14): ATRₜ = (ATRₜ₋₁·(n−1) + TRₜ) / n; seed — простое среднее первых n TR.

**Параметры:** `period` = 14.

**Сигналы:** сам по себе сигналов не даёт (уровень волатильности); нормализованное значение ATR/цена используется потребителями (движок, бэктест). Опционально `atr_pct` (ATR в % от цены) для сравнения между бумагами.

**Сложность:** просто.

**Roadmap:** 1) модуль + тесты — **реализовано**; 2) валидация — **реализовано**; 3) реестр/API — **реализовано**; 4) веб — **реализовано**; 5) интеграция в бэктест/бумажную торговлю (стопы по k·ATR) — отложено, в движок интегрирован (kind `atr`); 6) документация и статус — **реализовано**.

### 8.9. OBV — балансовый объём

**Обоснование:** подтверждение тренда объёмом; объём есть в `MarketCandle`.

**Формула:** OBVₜ = OBVₜ₋₁ + Vₜ при Cₜ > Cₜ₋₁; OBVₜ = OBVₜ₋₁ − Vₜ при Cₜ < Cₜ₋₁; без изменения при равенстве.

**Параметры:** нет (опц. `smooth_period` для сглаженного OBV, напр. 20).

**Сигналы:** `divergence_bullish` / `divergence_bearish` (цена обновляет экстремум, OBV — нет: расхождение цены и объёмного баланса).

**Сложность:** просто.

**Roadmap:** 1) модуль + тесты; 2) валидация; 3) реестр/API; 4) веб; 5) движок (подтверждение/ослабление сигнала); 6) документация и статус.

### 8.10. ADX/DI — средний направленный индекс

**Статус:** реализован (модуль `app/market/indicators/adx.py`, реестр/API `/v1/indicators/adx`, веб-вкладка; интеграция в движок — фильтр силы тренда, kind `adx`).

**Обоснование:** сила и направление тренда; фильтр сигналов движка (не выдаём BUY/SELL против сильного тренда).

**Формула:** +DM = Hₜ − Hₜ₋₁ (если > 0 и > −DM), −DM = Lₜ₋₁ − Lₜ (аналогично); сглаживание Уайлдера; +DI = 100·smooth(+DM)/TR_sum, −DI = 100·smooth(−DM)/TR_sum; DX = 100·|+DI − −DI| / (+DI + −DI); ADX = сглаженное DX (n = 14).

**Параметры:** `period` = 14.

**Сигналы:** `trend` (ADX ≥ 25 — выраженный тренд), `range` (ADX < 20 — флэт), `bullish` / `bearish` (+DI > −DI / наоборот).

**Сложность:** средне (аккуратное сглаживание Уайлдера, защита от деления на ноль).

**Roadmap:** 1) модуль + тесты — **реализовано**; 2) валидация — **реализовано**; 3) реестр/API — **реализовано**; 4) веб — **реализовано**; 5) движок (фильтр силы тренда) — **реализовано**; 6) документация и статус — **реализовано**.

### 8.11. Поддержка/сопротивление

**Статус:** реализован (модуль `app/market/indicators/support_resistance.py`, реестр/API `/v1/indicators/support_resistance`, веб-вкладка на `/indicators`, интеграция в движок стратегий — уровни в «Сигналах» и сдерживающий фактор «цена у уровня»).

**Обоснование:** закрывает P0 FR-04-02. Эвристика, единого стандарта нет — открытых готовых решений мало, нужна своя реализация и валидация на истории MOEX.

**Алгоритм (реализовано):**
1. **Классические pivot points** от последней свечи окна: P = (H + L + C)/3; R1 = 2P − L; S1 = 2P − H; R2 = P + (H − L); S2 = P − (H − L).
2. **Локальные экстремумы (фракталы Уильямса):** свеча — максимум, если H выше k свечей слева и справа (k = 2); минимум — аналогично. Фильтр значимости: отклонение от соседних экстремумов ≥ k_atr·ATR (иначе уровень шума).
3. **Кластеризация:** близкие уровни (разница < 0.25·ATR) объединяются в средневзвешенный (вес = число касаний).
4. **Ранжирование:** по близости к текущей цене и числу касаний; сила уровня — weak/medium/strong.

**Выход:** список уровней: `{price, kind: support|resistance, strength, touches}`.

**Сигналы:** `bounce` (отскок от уровня — цена коснулась и развернулась), `breakout` (пробой уровня с подтверждением по закрытию за уровень).

**Параметры:** `window` = 20 (окно поиска экстремумов), `fractal_k` = 2, `min_touches` = 2, `cluster_tolerance_atr` = 0.25.

**Сложность:** сложно (эвристика, нет эталона; требует валидации и итераций).

**Roadmap:** 1) MVP алгоритма (pivot + фракталы + кластеризация) + юнит-тесты на синтетике ✅; 2) валидация на истории: 5–10 бумаг × 2 года, метрики — доля отскоков и пробоев, сравнение с наивным бенчмарком (скользящие минимумы/максимумы) ⏳; 3) итерации алгоритма по результатам валидации ⏳; 4) реестр/API ✅; 5) веб ✅; 6) движок (уровни в рисках/контраргументах, как «цена у сопротивления») ✅; 7) документация и статус ✅.

### 8.12. OI — открытый интерес (срочный рынок)

**Обоснование:** открытый интерес (число открытых контрактов) — ключевая метрика срочного рынка, недоступная из обычных свечей. Сигналы «цена × OI» показывают накопление/распределение позиций (классика анализа фьючерсов). Источник — **ISS API** (`engines/futures/markets/forts`), а не HTML-страница `moex.com/derivatives/open-positions` (она не API и парсить её не нужно).

**Данные (источник, подтверждено на 2026-08):**
- текущее значение: `securities/{SECID}.json` → блок `marketdata`: `OPENPOSITION` (контракты), `OICHANGE` (изменение к предыдущему дню); блок `securities`: `PREVOPENPOSITION`;
- история по датам: `forts/openpositions.json` (блок `history`: `TRADEDATE`, `SECID`, `CLOSE`, `VOLUME`, `OPENPOSITION`, `OPENPOSITIONVALUE`, `SETTLEPRICE`); точный способ запроса диапазона (`from`/`till`/`date`) уточняется на этапе реализации — задача «разведка ISS».

**Хранение:** таблица `market_open_positions` (см. §7) + `scripts/update_oi.py`. Скрипт из того же ответа ISS создаёт и дневные свечи фьючерса (`MarketCandle`) — без них сигналы «цена × OI» не рассчитываются.

**Расчёт (модуль `oi.py`):** вход — серия `(date, close, oi)` (цена из `MarketCandle`, OI из таблицы); выход: `values` — `oi`, `oi_change` (= oiₜ − oiₜ₋₁), `oi_change_pct` (= oi_change / oiₜ₋₁ · 100).

**Сигналы (по дневному изменению цены и OI):**

| Цена | OI | Сигнал | kind | severity | Трактовка |
|---|---|---|---|---|---|
| ↑ | ↑ | Strong Bull | `strong_bull` | strong | Цена растёт ↑, OI растёт ↑ — набор + длинных позиций (рост рынка продолжится) |
| ↓ | ↑ | Strong Bear | `strong_bear` | strong | Цена падает ↓, OI растёт ↑ — открытие − коротких позиций (падение продолжится) |
| → | ↑ | Bearish Setup | `bearish_setup` | warning | Цена без изменений →, OI растёт ↑ — рынок готовится к снижению |
| → | ↓ | Bullish Setup | `bullish_setup` | warning | Цена без изменений →, OI падает ↓ — рынок готовится к росту |
| ↓ | ↓ | Long Liquidation | `long_liquidation` | warning | Цена падает ↓, OI падает ↓ — закрытие длинных позиций (возможен разворот вверх) |
| ↑ | ↓ | Short Covering | `short_covering` | warning | Цена растёт ↑, OI падает ↓ — закрытие коротких позиций (возможен разворот вниз) |

Сигнал считается только при `|ΔOI| ≥ oi_change_threshold_pct`% (иначе — без сигнала). Комбинации с неизменным OI (→) сигналов не дают: изменение OI ниже порога. Нейтральные сигналы (цена →) добавлены по трактовкам источника (статья Т-Банка «Когда покупать фьючерсы: открытый интерес», см. [14-web-interface.md](./14-web-interface.md)); в движке стратегий они не участвуют (только в таблице сигналов веб-интерфейса).

**Объём — подтверждение сигнала.** В серию OI дополнительно подаётся объём торгов (4-й элемент: `(date, close, open_position, volume)`). Изменение объёма к предыдущему дню определяет пометку сигнала: `volume: "up"` (объём растёт — движение подтверждено «новыми деньгами», сигнал сильнее) или `"down"` (объём падает — движение «на излёте», сигнал слабее); без данных об объёме пометка отсутствует (`None`). Пометка добавляется в трактовку сигнала («· объём растёт ↑ / объём падает ↓») и в API (`volume` в signals). Значение `volume_change_pct` доступно в `values` (kind `volume_change_pct`).

**Параметры:** `oi_change_threshold_pct` = 1.0 (мин. изменение OI для сигнала), `price_change_threshold_pct` = 0.0 (мин. изменение цены; при равенстве — нет сигнала).

**Связь с акциями:** при синке (`scripts/update_oi.py`) фьючерсу проставляются `assetcode` (код базового актива) и `lastdeldate` (экспирация) — по ним строится связь «акция ↔ фьючерс» (см. [07-data-model.md](./07-data-model.md) §2.1). На карточке акции показывается блок «Фьючерсы на акцию» со ссылками на страницу OI каждого фьючерса и график OI ближайшего по экспирации фьючерса ([14-web-interface.md](./14-web-interface.md) §4). Движок стратегий учитывает OI-сигнал ближайшего фьючерса в аналитике акции: сигнал в «Сигналах», риски/контраргументы и ослабление net_score ([09-strategy-engine.md](./09-strategy-engine.md) §4.1).

**Сложность:** средне (не формула, а внешние данные: разведка эндпоинта истории, хранение, скрипт наполнения, специфика фьючерсов — тикеры и экспирации).

**Roadmap:** 1) разведка ISS: подтвердить эндпоинт истории OI, параметры диапазона и единицы; 2) миграция Liquibase `market_open_positions` + модель SQLAlchemy; 3) `scripts/update_oi.py` (загрузка с кэшем, повторными попытками; регистрация в админ-панели) + `app/market/oi_data.py`; 4) модуль `oi.py` (значения + сигналы) и юнит-тесты на синтетике; 5) валидация на реальном фьючерсе (сверка с сайтом MOEX); 6) реестр/API; 7) веб-страница; 8) движок стратегий (сигналы OI в контраргументах/рисках — **реализовано**, см. [09-strategy-engine.md](./09-strategy-engine.md) §4.1); 9) документация и статус.

**Критерии приёмки:** данные за указанный период скачиваются и строят график OI; сигналы соответствуют классике «цена × OI»; `pytest` зелёный; доступен через API и веб; описано в 10/14/17; статус в 12-roadmap обновлён.

### 8.13. Volume Profile: POC, Value Area (VAH/VAL), HVN, LVN

**Обоснование:** профиль объёма показывает распределение объёма торгов по ценовым уровням за период — где рынок «провёл больше всего времени» (зоны согласия) и где объёма почти не было (быстрые проходы). Даёт уровни поддержки/сопротивления, «справедливую цену» и фильтр пробоев. Строится по дневным свечам (high/low/close/volume) — внешние данные не нужны, работает и для акций, и для фьючерсов.

**Алгоритм (упрощённый, детерминированный):**
1. За период (`period` дней, по умолчанию 60) собрать дневные свечи (high, low, close, volume); окна строятся по фактическим датам (MOEX не торгует в праздники).
2. Разбить ценовой диапазон периода на бары: фиксированное число баров (`bins`, по умолчанию 60) либо шаг цены в % от средней цены периода — параметром `bins`/`price_step_pct`.
3. Объём каждого дня распределить по барам между `low` и `high` равномерно (объём / число баров в диапазоне дня) и накопить за период.
4. **POC (Point of Control)** — бар с максимальным накопленным объёмом: цена, по которой торговали больше всего за период.
5. **Value Area** — диапазон вокруг POC (расширяется от POC в обе стороны), содержащий `value_area_pct`% всего объёма (по умолчанию 70%); **VAH** — верхняя граница, **VAL** — нижняя.
6. **HVN (High Volume Node)** — бары с объёмом выше `hvn_factor` × средний объём бара (по умолчанию 2.0): зоны «согласия» (поддержка/сопротивление, «магнит» цены).
7. **LVN (Low Volume Node)** — бары с объёмом ниже `lvn_factor` × средний объём бара (по умолчанию 0.5): зоны «отсутствия торговли» (цена проходит быстро).

**Параметры:** `period` = 60 (дней), `bins` = 60 (ценовых баров), `value_area_pct` = 70, `hvn_factor` = 2.0, `lvn_factor` = 0.5.

**Результат (IndicatorResult):** values — объём по барам (kind `volume_profile`); `meta` — список узлов (цена бара, объём, метки: POC / VAH / VAL / HVN / LVN) для отображения профиля; сигналы — `poc` (контрольная точка), `value_area` (диапазон), `hvn`/`lvn` (узлы).

**Использование в аналитике бумаги (движок стратегий):**
- цена выше VAH → перекупленность (сдерживание BUY), цена ниже VAL → перепроданность (сдерживание SELL);
- возврат цены к POC → «магнит»/высокая волатильность (риск-фактор);
- пробой HVN с объёмом → подтверждение движения; проход LVN → быстрое движение без отката;
- POC/VAH/VAL добавляются в «Уровни» и «Сигналы» карточки бумаги.

**Отображение (веб):** на карточке бумаги — горизонтальный профиль объёма (ось Y — цена, ось X — объём; бары вправо, как на скриншоте пользователя), POC подсвечен, VAH/VAL — границы Value Area, HVN/LVN — выделенные узлы; **селектор периода** (пресеты 1M/3M/6M/1Y или диапазон дат) — пользователь указывает, за какой период считать.

**Сложность:** средне (алгоритм простой и детерминированный, но нет эталона в pandas-ta/ta-lib — проверка вручную на синтетике; новая визуализация профиля).

**Roadmap:** 1) модуль `app/market/indicators/volume_profile.py` + юнит-тесты на синтетике (эталон ручной) — **реализовано**; 2) валидация на данных MOEX — **реализовано**; 3) реестр/API `/v1/indicators/volume_profile` (параметры `period`/`bins`) — **реализовано**; 4) веб: профиль объёма на карточке бумаги с выбором периода (1M/2M/3M/6M/1Y) — **реализовано**; 5) интеграция в движок стратегий (сигнал POC/Value Area в «Сигналах», ослабление net_score при цене вне Value Area) — **реализовано**; 6) документация (10/14) и статус в 12-roadmap — **реализовано**.

### 8.14. OI по группам клиентов (физики/юрики)

**Статус:** **реализован** (после согласования ТЗ): миграция 017 `market_open_positions_client_groups`, синхронизация в `update_oi` (`fetch_open_positions_client_groups` → сервис `OpenOptionService`, кэш по (актив, дата)), API `client_groups=1`, веб-блок на вкладке OI — **COT-визуализация** (двухпанельный график: цена сверху + группированные столбцы нетто-позиций физ/юр вокруг нулевой оси; таблица с сортировкой по Дата/Физ нетто/Юр нетто, подсветкой противоположных ставок и строкой «Итого»).

**Обоснование:** расширение OI-индикатора (FR-03). Разделение открытых позиций по группам клиентов (физические/юридические лица) даёт дополнительный сигнал: какая группа набирала длинные/короткие позиции. Сопоставление с историей цен позволяет оценивать, какая группа чаще оказывается права («умные деньги» vs розничные инвесторы) и выявлять закономерности («кто когда был прав и что происходило с рынком»).

**Источник данных (исследовано 09.08.2026):**
- Публичный ISS-блок `openpositions`/`openposday` для этих данных **не отдаёт** (пустые ответы) — не подходит.
- Данные отдаёт сервис сайта MOEX: `GET https://www.moex.com/api/contract/OpenOptionService/{DD.MM.YYYY}/F/{ASSETCODE}/json` (обязателен Referer `https://www.moex.com/`). Пример для MIX на 07.08.2026:
  ```json
  [{"Date":"07.08.2026","JuridicalLong":"78 798","JuridicalShort":"77 082",
    "PhysicalLong":"83 304","PhysicalShort":"85 020","Summary":"324 204"},   // итоги, контракты
   {"Date":"07.08.2026","JuridicalLong":"5 031",...,"Summary":"4 498"},      // нетто (long−short)
   {"Date":"07.08.2026","JuridicalLong":"6,82",...,"Summary":"1,41"},         // %, доли групп
   {"Date":"07.08.2026","JuridicalLong":"77",...,"Summary":"7 752"}]          // число участников
  ```
- Агрегация — **по базовому активу** (`ASSETCODE`, например MIX, WHEAT, AFLT): все фьючерсы на актив суммарно — как вкладка «Открытые позиции по группам клиентов» на странице контракта (пример: moex.com/ru/contract.aspx?code=MIX-9.26).
- **История:** запрос на каждый торговый день (торговые даты берём из свечей фьючерса в `market_candles`); сервис отвечает и за давние даты (проверено на 01.07.2026).

**FR/UC:**
- **FR-3.3.1** — синхронизация OI по группам клиентов: скрипт `update_oi` дополнительно запрашивает `OpenOptionService` по `assetcode` фьючерса на каждую торговую дату и сохраняет ряды физиков/юриков (long/short/нетто/участники).
- **UC-14.1** — на `/indicators` (вкладка OI) пользователь видит: общий OI (как сейчас) + **две дополнительные линии OI физиков и юриков** (переключатель групп: физики/юрики/все — как на скриншоте MOEX) и **таблицу по датам с фильтрами дат ОТ/ДО** и переключателем групп.

**Модель данных:** новая таблица (миграция Liquibase `NNN_market_open_positions_client_groups.xml`):
- `market_open_positions_client_groups` — `id`, `security_id` (FK `securities`), `trading_date` (date), `client_group` (`physical`|`juridical`), `long_pos` (bigint), `short_pos` (bigint), `net_pos` (bigint), `participants` (int), `summary` (bigint); уникальность `(security_id, trading_date, client_group)`.
- SQLAlchemy-модель `MarketOpenPositionClientGroup` добавляется вместе с миграцией.

**API:** `/v1/indicators/oi` — расширение ответа: параметр `client_groups=1` добавляет `client_groups` — ряды `{date, physical_long, physical_short, juridical_long, juridical_short, net_physical, net_juridical, summary}` + итоговая точность групп. (Либо отдельный эндпоинт `/v1/indicators/oi/client-groups?ticker=...&from=...&to=...` — финальное решение при реализации.)

**Дополнительные аналитические метрики (добавлены по итогам согласования):**
- **Нетто-динамика групп**: изменение нетто (long−short) физиков и юриков за период (например, за 5 торговых дней) — признак **накопления/распределения** позиции группой;
- **Спред нетто «юр − физ»**: разность нетто-позиций групп как отдельный ряд — **смена знака** спреда показывает смену настроений (классический паттерн «институционалы против розницы»);
- **Доля физиков в суммарном OI, %**: рост доли розничных участников при сильном движении часто предшествует развороту (розница «догоняет»);
- **Пометка экспирации**: строки таблицы за 2 недели до `lastdeldate` помечаются (массовое закрытие позиций к экспирации искажает сигналы OI);
- **Противоположные ставки групп**: подсветка дат, когда нетто физиков и юриков имеют **разные знаки** (наибольший информационный сигнал).

**Ограничения источника (фиксируются в ТЗ):**
- данные агрегированы **по базовому активу** (все фьючерсы на актив), а не по отдельному контракту — для серий контрактов на один актив значения частично пересекаются с соседними экспирациями;
- MOEX разделяет только **физических и юридических лиц** (без выделения нерезидентов/брокеров/маркетмейкеров);
- сервис отдаёт данные **за завершённый торговый день** (задержка публикации — следующий день), внутри дня не обновляется.

**UI (`/indicators`, вкладка OI):**
- График «OI и цена»: три линии OI — общий, физики, юрики (по длинным позициям), переключатель групп (как на скриншоте MOEX);
- Таблица «Открытые позиции по группам клиентов»: дата, физ long/short/нетто, юр long/short/нетто, сумма, доля физиков %, спред нетто (юр−физ); фильтры **даты ОТ/ДО**; подсветка дат с противоположными ставками групп и дат вблизи экспирации.

**Roadmap:** 1) исследование источника данных ✅; 2) согласование ТЗ ✅; 3) миграция + модель ✅; 4) синхронизация (`update_oi` + `OpenOptionService`) ✅; 5) API (`client_groups=1`) ✅; 6) UI (график + таблица + фильтры ОТ/ДО, метрики нетто/спреда/доли физиков) ✅; 7) (опционально) техсигнал в движке ⏳.

**Критерии приёмки:** данные физ/юр по датам в БД; таблица с фильтрами ОТ/ДО и переключателем групп на вкладке OI; метрики (нетто-динамика, спред «юр−физ», доля физиков, пометка экспирации); `pytest` зелёный; документация (10/14) и статус в 12-roadmap обновлены.

### 8.14.1. Индикатор динамики OI (Δ OI) по группам клиентов — ТЗ

**Статус:** ТЗ согласовано; реализуется по [14-web-interface.md](./14-web-interface.md).

**Назначение:** в таблице «Открытые позиции по группам клиентов» показать, **насколько выросли/упали открытые позиции группы** по сравнению с предыдущим торговым днём.

**Метрика:** OI группы = `long_pos + short_pos` (все открытые позиции группы). Δ% = (OIₜ − OIₜ₋₁) / OIₜ₋₁ × 100, где OIₜ — значение за текущую дату, OIₜ₋₁ — за предыдущую (строки таблицы отсортированы по дате). Для первой даты (нет предыдущей) — состояние «−» (нет данных).

**Состояния (дефолтные пороги, калибруются):**

| Δ% (день-к-дню) | Состояние | Обозначение |
|---|---|---|
| ≥ +10% | стремительно возрастающая | ↑↑↑ |
| +5% … +10% | сильно возрастающая | ↑↑ |
| +2% … +5% | возрастающая | ↑ |
| −2% … +2% | инертная | − |
| −5% … −2% | падающая | ↓ |
| −10% … −5% | сильно падающая | ↓↓ |
| ≤ −10% | стремительно падающая | ↓↓↓ |

**UI:** в таблице — колонка **«Δ OI»** (после «Доля физ, %»; у заголовка — всплывающая подсказка «?» с объяснением индикатора и порогов, как принято в проекте); в каждой строке две подписи: **«Физ ↑↑ · L ↑ S ↓»** и **«Юр ↓ · L ↓ S ↑»** — общая динамика (long+short) и отдельно по длинным (L) и коротким (S) позициям группы; точные проценты (общ/long/short) — в браузерной подсказке (title) строки, например «Физики: общ +7,3% · long +2,1% · short +12,0% к пред. дню». Цвет: зелёный — рост, красный — падение, нейтральный — инертная/нет данных. Строка «Итого» — «—». Сортировка по колонке не требуется (первичная — Дата/Физ нетто/Юр нетто).

**Критерии приёмки:** в каждой строке таблицы у физ/юр показывается состояние Δ OI по порогам выше (общая динамика + отдельно long/short); первая дата — «−»; тултип «?» у заголовка и браузерная подсказка с точными %; «Итого» — «—»; `pytest` зелёный; документация (14) обновлена.

## 10. Риски и открытые вопросы

- **Поддержка/сопротивление** — главный риск: эвристика без эталона. Митигация: валидация на истории MOEX с метриками отскоков/пробоев, поэтапные итерации.
- **OI — внешние данные, а не расчёт:** зависят от публикации ISS (открытые позиции появляются после вечернего клиринга); пропуски в ряду — обрабатывать как пропуски (не ошибки), не интерполировать. Единицы — контракты (не лоты/рубли; `OPENPOSITIONVALUE` — рубли).
- **Фьючерсные серии:** тикер контракта живёт ~квартал (например, W4V6 → W4Z6), к экспирации OI обнуляется. В этом этапе работаем с конкретным контрактом по SECID; склейка серий по базовому активу (continuous) — отдельная задача.
- **OI существует только для срочного рынка** (фьючерсы): для акций/облигаций модуль возвращает пустые значения с пометкой в `meta`.
- **Точность формул:** сверка с эталонными реализациями (pandas-ta/ta-lib) на синтетических рядах — в тестах, но зависимостей в рантайм не добавляем.
- **Данные MOEX:** праздники/неликвидные дни — окна строятся по фактическим датам свечей; нулевые объёмы — OBV и %K деградируют без ошибок (None).
- **Производительность API:** on-the-fly расчёт при большом `limit` — ограничение `limit`, при необходимости кэш (отдельное решение).
- **Volume Profile:** нет эталона в pandas-ta/ta-lib (проверка вручную на синтетике); выбор числа баров/шага цены влияет на результат (POC/VAH/VAL) — параметры должны быть детерминированными и документированными; распределение объёма дня по барам — упрощённая модель (равномерное), при необходимости уточнить (HLC-метод).
- **Калибровка порогов сигналов** (ADX 25, |ROC|, bandwidth-процентиль) — через существующий механизм калибровки/весов, отдельная задача.
- Отложены (не в этом этапе): VWAP, Ichimoku, свечные паттерны, Williams %R, Supertrend, дивергенции MACD.

## 1. Обоснование

Требование FR-04-02 (приоритет P0) из [04-functional-requirements.md](./04-functional-requirements.md): система должна рассчитывать технические индикаторы — RSI, MACD, скользящие средние, уровни поддержки/сопротивления, волатильность.

Текущее состояние:

| Индикатор из FR-04-02 | Статус |
|---|---|
| RSI | ✅ есть (`app/market/indicators.py`, `rsi`) |
| Скользящие средние | ⚠️ только SMA; EMA нет |
| Волатильность | ✅ есть (упрощённо, `volatility`) |
| **MACD** | ❌ нет |
| **Поддержка/сопротивление** | ❌ нет |

**Зачем нужны отдельные модули:**
- индикаторы вызываются из разных мест: движок стратегий (техсигналы), веб-интерфейс (карточка бумаги, графики), REST API (внешние вызовы), бэктест и бумажная торговля (стопы, риск-параметры);
- единый контракт и реестр позволяют добавлять/тестировать/калибровать индикаторы независимо;
- реализация без тяжёлых внешних зависимостей (ta-lib/pandas-ta не подключаем): формулы стандартные, код свой.

**Утверждённый список (12 индикаторов):**

| № | Индикатор | Категория | Приоритет | Сложность |
|---|---|---|---|---|
| 1 | EMA | тренд | P1 | просто |
| 2 | MACD | тренд | P0 | просто |
| 3 | Полосы Боллинджера | тренд/волатильность | P1 | просто |
| 4 | Parabolic SAR | тренд | P2 | средне |
| 5 | Stochastic %K/%D | осциллятор | P2 | просто |
| 6 | CCI | осциллятор | P2 | просто |
| 7 | ROC | осциллятор | P2 | просто |
| 8 | ATR | волатильность | P1 | просто |
| 9 | OBV | объём | P2 | просто |
| 10 | ADX/DI | тренд (сила) | P1 | средне |
| 11 | Поддержка/сопротивление | уровни | P0 | сложно |
| 12 | OI (Открытый интерес) | позиции (срочный рынок) | P1 | средне |

Приоритеты: **P0** — закрывают невыполненные пункты FR-04-02 (MACD, поддержка/сопротивление); **P1** — базовые, риск-параметры и данные позиций (EMA, Боллинджер, ATR, ADX, OI); **P2** — остальные.

## 2. Цели и не-цели

**Цели:**
- пакет `app/market/indicators/` с единым контрактом и реестром;
- 11 индикаторов по утверждённому списку;
- REST API `/api/indicators/*` и веб-страница `/indicators`;
- интеграция в движок стратегий (новые техсигналы) и бэктест.

**Не-цели (в рамках этого ТЗ):**
- не заменяем существующие `sma/rsi/volatility` — они мигрируют в пакет с сохранением интерфейса (тонкая обёртка-реэкспорт остаётся);
- индикаторы не дают «советов»: выдают только расчётные значения и сигналы по порогам;
- историю расчётов в БД не храним — расчёт on-the-fly из свечей;
- индикаторы не являются инвестиционными рекомендациями (дисклеймер как у вердиктов);
- индикаторы VWAP, Ichimoku, свечные паттерны, Williams %R, Supertrend в этот этап **не входят** (могут быть добавлены отдельным ТЗ).

scripts/update_oi.py            # наполнение таблицы market_open_positions (регистрируется в админ-панели)

```

- Каждый модуль — чистая функция расчёта: вход — список свечей (объекты с атрибутами `date, open, high, low, close, volume` или dict-совместимые) + параметры; выход — `IndicatorResult`.
- Расчёт только по фактическим датам свечей (MOEX не торгует в праздники) — окна строятся по имеющимся свечам, без «пустых» дней.
- Детерминизм: одинаковый вход → одинаковый выход (требование для бэктеста «на момент T», см. [13-operations.md](./13-operations.md)).
- Модули не ходят в БД сами: данные загружает вызывающий слой (API/web/движок) через существующий `app/market/prices.py`.

## 4. Единый контракт индикатора

```python
@dataclass
class IndicatorValue:
    date: date
    value: float | None          # None — позиция «не прогрета» (недостаточно истории)

@dataclass
class IndicatorSignal:
    date: date
    kind: str                    # машинный ключ, например "cross_up", "overbought", "breakout"
    severity: str                # "info" | "warning" | "strong"
    note: str                    # человекопонятное описание на русском

@dataclass
class IndicatorResult:
    indicator: str               # имя индикатора (ключ реестра)
    params: dict                 # фактически применённые параметры
    values: list[IndicatorValue]
    signals: list[IndicatorSignal]
    meta: dict                   # число свечей, окно дат, ограничения (например, "мало данных")
```

Правила контракта:
- параметры валидируются (период > 0, разумные диапазоны); невалидные → исключение/ошибка 422 в API;
- недостаточно данных → пустые/частичные `values`, причина в `meta` (не ошибка);
- сигналы формируются по фиксированным порогам индикатора (см. ТЗ ниже), пороги калибруются отдельно (как веса факторов).

## 5. REST API (дизайн)

Эндпоинты (полная спецификация — в [10-api-specification.md](./10-api-specification.md) на этапе реализации):

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/v1/indicators` | Список индикаторов: имя, описание, параметры по умолчанию, сложность |
| GET | `/v1/indicators/{name}` | Расчёт индикатора |

Пути указаны с учётом префикса API проекта (`/v1`, см. [10-api-specification.md](./10-api-specification.md)).

Параметры `GET /v1/indicators/{name}`:
- `ticker` или `security_id` — бумага (обязательный);
- `from`, `to` — диапазон дат (опц., по умолчанию — доступная история);
- `limit` — ограничение числа свечей (опц., защита от тяжёлых запросов);
- параметры индикатора по именам из реестра (`period`, `fast`, `slow`, `k`, …).

Ответ: JSON-представление `IndicatorResult`:

```json
{
  "indicator": "macd",
  "params": {"fast": 12, "slow": 26, "signal": 9},
  "values": [{"date": "2026-05-14", "value": 12.4}, "..."],
  "signals": [{"date": "2026-05-14", "kind": "cross_up", "severity": "warning", "note": "MACD пересекла сигнальную линию снизу вверх"}],
  "meta": {"candles": 300, "from": "...", "to": "...", "limits": []}
}
```

Ошибки: `404` — неизвестный индикатор; `422` — невалидные параметры; `400` — нет данных по бумаге/периоду. Аутентификация — по текущим правилам API (уточняется на этапе реализации).

**Особенность OI:** значения для `oi` берутся не из `MarketCandle`, а из таблицы `market_open_positions` (см. §7); цена для сигналов — из `MarketCandle` по тем же датам. Контракт ответа (`values`/`signals`) — общий.

## 6. Веб-интерфейс (дизайн)

- Страница `/indicators`: выбор индикатора, бумаги, диапазона и параметров; график значений (тот же JS-график, что на карточке бумаги) + таблица сигналов.
- Опционально (фаза 6): компактный блок с ключевыми индикаторами на карточке бумаги.
- Дизайн страницы фиксируется на этапе реализации и описывается в [14-web-interface.md](./14-web-interface.md).

### 6.1. UI-требования: индикатор OI (страница `/indicators`, раздел «Открытый интерес»)

- Выбор фьючерсного тикера (SECID, например W4V6), диапазон дат, параметр `oi_change_threshold_pct`.
- **График 1 — OI и цена:** линия OI (ось слева, подпись «контракты») + линия close (ось справа) на общей временной шкале — для визуального поиска дивергенций «цена × OI».
- **График 2 — изменение OI:** `oi_change_pct` (столбцы/линия) с нулевой осью.
- **Таблица сигналов:** дата, тип (Strong Bull / Strong Bear / Long Liquidation / Short Covering), важность, трактовка.
- Пропуски в ряду OI (нет публикации/торгов) отображаются как пропуски, не как ноль.
- Страница общая для всех индикаторов; разделы других индикаторов добавляются по мере реализации (см. [14-web-interface.md](./14-web-interface.md)).

## 7. Модель данных

- Для 11 индикаторов, рассчитываемых из цен: on-the-fly из `MarketCandle` (daily, OHLCV) — новая таблица не требуется. Кэш не вводим: дневные свечи, расчёт быстрый.
- **Исключение — OI:** это внешние сырые данные (не расчёт), их нужно скачивать и хранить. Новая таблица `market_open_positions` (миграция Liquibase + модель SQLAlchemy):

  | Колонка | Тип | Назначение |
  |---|---|---|
  | id | int PK | |
  | security_id | FK → securities.id | фьючерсный контракт (по SECID) |
  | trading_date | date | дата торгов |
  | open_position | bigint | открытые позиции, контрактов (ISS `OPENPOSITION`) |
  | open_position_value | numeric | открытые позиции, руб. (ISS `OPENPOSITIONVALUE`, опц.) |
  | source | varchar | `iss` (для будущих источников) |

  Уникальный ключ (security_id, trading_date). Наполнение — `scripts/update_oi.py` (по аналогии с `update_prices`, с кэшем запросов ISS и повторными попытками).
- Параметры индикаторов передаются в вызове, в БД не хранятся.

## 8. ТЗ на индикаторы

Общие критерии приёмки для каждого индикатора:
- юнит-тесты на синтетических данных с известными эталонными значениями (ручной расчёт или сверка с pandas-ta/ta-lib в тестах-комментариях);
- детерминизм и обработка недостатка данных (None/пусто + `meta`);
- регистрация в реестре и доступность через API;
- описание и параметры в документации (10, 14, 17-quickstart) + статус в [12-roadmap.md](./12-roadmap.md).

### 8.1. EMA — экспоненциальная скользящая средняя

**Обоснование:** базовая СС с большим весом свежих цен; «кирпич» для MACD и Боллинджера; сейчас в проекте только SMA.

**Формула:** α = 2 / (N+1); seed: EMA первых N значений = SMA(N); далее EMAₜ = Cₜ·α + EMAₜ₋₁·(1−α).

**Параметры:** `period` = 20 (типовые 12/26/50/200).

**Сигналы:** пересечение двух EMA (`ema_fast`/`ema_slow`): `cross_up` / `cross_down` (golden/death cross).

**Сложность:** просто.

**Roadmap:** 1) модуль + тесты; 2) валидация на данных MOEX; 3) реестр/API; 4) веб; 5) интеграция в движок стратегий (EMA50/200 как техсигналы); 6) документация и статус.

### 8.2. MACD — схождение/расхождение скользящих средних

**Обоснование:** закрывает P0 FR-04-02; классический тренд-осциллятор, используется в стратегиях как фильтр направления.

**Формула:** MACD = EMA(fast) − EMA(slow); signal = EMA(signal) от MACD; hist = MACD − signal.

**Параметры:** `fast` = 12, `slow` = 26, `signal` = 9.

**Сигналы:** `cross_up` / `cross_down` (MACD × signal); `hist_positive` / `hist_negative` (знак гистограммы). Дивергенции MACD/цены — отдельная задача (не в этом этапе).

**Сложность:** просто.

**Roadmap:** 1) модуль + тесты (включая сверку с эталоном); 2) валидация; 3) реестр/API; 4) веб; 5) интеграция в движок (направление тренда в техсигналах); 6) документация и статус.

### 8.3. Полосы Боллинджера

**Обоснование:** волатильность вокруг среднего + зоны перекупленности/перепроданности по цене; входит в блок «волатильность» FR-04-02.

**Формула:** middle = SMA(N); σ — стандартное отклонение (популяционное) за окно; upper = middle + k·σ; lower = middle − k·σ; %B = (C − lower) / (upper − lower); bandwidth = (upper − lower) / middle.

**Параметры:** `period` = 20, `k` = 2.

**Сигналы:** `touch_upper` / `touch_lower` (C пересекает полосу), `revert_in` (возврат внутрь полос), `squeeze` (bandwidth ниже порога — сжатие, предвестник движения; порог = 10-й процентиль bandwidth за окно).

**Сложность:** просто.

**Roadmap:** 1) модуль + тесты; 2) валидация; 3) реестр/API; 4) веб; 5) движок (зоны перекупленности как сдерживающий фактор, аналогично RSI); 6) документация и статус.

### 8.4. Parabolic SAR

**Обоснование:** точки разворота тренда; удобен для стоп-уровней в бэктесте и бумажной торговле.

**Формула (итеративная):** SARₜ₊₁ = SARₜ + AF·(EP − SARₜ), где AF стартует с 0.02, растёт на 0.02 при каждом новом экстремуме EP до максимума 0.2; EP — экстремальная цена текущего тренда (максимум в аптренде, минимум в даунтренде); при пробое SAR ценой — разворот: SAR перепрыгивает на противоположную сторону, AF сбрасывается на 0.02.

**Параметры:** `af_step` = 0.02, `af_max` = 0.2.

**Сигналы:** `flip_up` / `flip_down` (разворот направления), `above` / `below` (SAR относительно цены — тренд).

**Сложность:** средне (аккуратная итеративная логика разворотов, edge-кейсы на старте).

**Roadmap:** 1) модуль + тесты (синтетика с известными разворотами); 2) валидация; 3) реестр/API; 4) веб; 5) движок/бэктест (стоп-уровни); 6) документация и статус.

### 8.5. Stochastic %K/%D

**Обоснование:** зоны перекупленности/перепроданности в боковике — дополняет RSI (RSI лучше работает в тренде).

**Формула:** %K = (C − Lₙ) / (Hₙ − Lₙ) · 100 (n = 14); %D = SMA(3) от %K.

**Параметры:** `k_period` = 14, `d_period` = 3, `smooth` = 1.

**Сигналы:** `overbought` (≥ 80), `oversold` (≤ 20), `cross_up` / `cross_down` (%K × %D).

**Сложность:** просто.

**Roadmap:** 1) модуль + тесты; 2) валидация; 3) реестр/API; 4) веб; 5) движок (осцилляторный сигнал); 6) документация и статус.

### 8.6. CCI — индекс товарного канала

**Обоснование:** циклические экстремумы и дивергенции; стандартные уровни ±100.

**Формула:** TP = (H + L + C) / 3; CCI = (TP − SMA(TP, n)) / (0.015 · MD), где MD — среднее абсолютное отклонение TP от SMA за окно.

**Параметры:** `period` = 20.

**Сигналы:** `overbought` (> +100), `oversold` (< −100), `revert` (возврат в коридор через ±100).

**Сложность:** просто.

**Roadmap:** 1) модуль + тесты; 2) валидация; 3) реестр/API; 4) веб; 5) движок (при необходимости); 6) документация и статус.

### 8.7. ROC — скорость изменения цены

**Обоснование:** простой моментум-фильтр (темп изменения за N периодов); полезен как ранний сигнал и в бэктесте.

**Формула:** ROCₜ = (Cₜ − Cₜ₋ₙ) / Cₜ₋ₙ · 100.

**Параметры:** `period` = 10.

**Сигналы:** `positive` / `negative` (знак моментума), `extreme` (выход за порог, напр. |ROC| > 10 — калибруется).

**Сложность:** просто.

**Roadmap:** 1) модуль + тесты; 2) валидация; 3) реестр/API; 4) веб; 5) движок (моментум-фильтр); 6) документация и статус.

### 8.8. ATR — средний истинный диапазон

**Обоснование:** мера волатильности; нужен для стопов/риск-параметров (paper trading, бэктест, размер позиции). Требует high/low — они есть в `MarketCandle`.

**Формула:** TRₜ = max(Hₜ − Lₜ, |Hₜ − Cₜ₋₁|, |Lₜ − Cₜ₋₁|); ATR — сглаживание Уайлдера (n = 14): ATRₜ = (ATRₜ₋₁·(n−1) + TRₜ) / n; seed — простое среднее первых n TR.

**Параметры:** `period` = 14.

**Сигналы:** сам по себе сигналов не даёт (уровень волатильности); нормализованное значение ATR/цена используется потребителями (движок, бэктест). Опционально `atr_pct` (ATR в % от цены) для сравнения между бумагами.

**Сложность:** просто.

**Roadmap:** 1) модуль + тесты; 2) валидация; 3) реестр/API; 4) веб; 5) интеграция в бэктест/бумажную торговлю (стопы по k·ATR) и движок; 6) документация и статус.

### 8.9. OBV — балансовый объём

**Обоснование:** подтверждение тренда объёмом; объём есть в `MarketCandle`.

**Формула:** OBVₜ = OBVₜ₋₁ + Vₜ при Cₜ > Cₜ₋₁; OBVₜ = OBVₜ₋₁ − Vₜ при Cₜ < Cₜ₋₁; без изменения при равенстве.

**Параметры:** нет (опц. `smooth_period` для сглаженного OBV, напр. 20).

**Сигналы:** `divergence_bullish` / `divergence_bearish` (цена обновляет экстремум, OBV — нет: расхождение цены и объёмного баланса).

**Сложность:** просто.

**Roadmap:** 1) модуль + тесты; 2) валидация; 3) реестр/API; 4) веб; 5) движок (подтверждение/ослабление сигнала); 6) документация и статус.

### 8.10. ADX/DI — средний направленный индекс

**Обоснование:** сила и направление тренда; фильтр сигналов движка (не выдаём BUY/SELL против сильного тренда).

**Формула:** +DM = Hₜ − Hₜ₋₁ (если > 0 и > −DM), −DM = Lₜ₋₁ − Lₜ (аналогично); сглаживание Уайлдера; +DI = 100·smooth(+DM)/TR_sum, −DI = 100·smooth(−DM)/TR_sum; DX = 100·|+DI − −DI| / (+DI + −DI); ADX = сглаженное DX (n = 14).

**Параметры:** `period` = 14.

**Сигналы:** `trend` (ADX ≥ 25 — выраженный тренд), `range` (ADX < 20 — флэт), `bullish` / `bearish` (+DI > −DI / наоборот).

**Сложность:** средне (аккуратное сглаживание Уайлдера, защита от деления на ноль).

**Roadmap:** 1) модуль + тесты; 2) валидация; 3) реестр/API; 4) веб; 5) движок (фильтр силы тренда); 6) документация и статус.

### 8.11. Поддержка/сопротивление

**Обоснование:** закрывает P0 FR-04-02. Эвристика, единого стандарта нет — открытых готовых решений мало, нужна своя реализация и валидация на истории MOEX.

**Алгоритм (предлагаемый, уточняется на этапе валидации):**
1. **Классические pivot points** от последней свечи окна: P = (H + L + C)/3; R1 = 2P − L; S1 = 2P − H; R2 = P + (H − L); S2 = P − (H − L).
2. **Локальные экстремумы (фракталы Уильямса):** свеча — максимум, если H выше k свечей слева и справа (k = 2); минимум — аналогично. Фильтр значимости: отклонение от соседних экстремумов ≥ k_atr·ATR (иначе уровень шума).
3. **Кластеризация:** близкие уровни (разница < 0.25·ATR) объединяются в средневзвешенный (вес = число касаний).
4. **Ранжирование:** по близости к текущей цене и числу касаний; сила уровня — weak/medium/strong.

**Выход:** список уровней: `{price, kind: support|resistance, strength, touches}`.

**Сигналы:** `bounce` (отскок от уровня — цена коснулась и развернулась), `breakout` (пробой уровня с подтверждением по закрытию за уровень).

**Параметры:** `window` = 20 (окно поиска экстремумов), `fractal_k` = 2, `min_touches` = 2, `cluster_tolerance_atr` = 0.25.

**Сложность:** сложно (эвристика, нет эталона; требует валидации и итераций).

**Roadmap:** 1) MVP алгоритма (pivot + фракталы + кластеризация) + юнит-тесты на синтетике; 2) валидация на истории: 5–10 бумаг × 2 года, метрики — доля отскоков и пробоев, сравнение с наивным бенчмарком (скользящие минимумы/максимумы); 3) итерации алгоритма по результатам валидации; 4) реестр/API; 5) веб; 6) движок (уровни в рисках/контраргументах, как «цена у сопротивления»); 7) документация и статус.

### 8.12. OI — открытый интерес (срочный рынок)

**Обоснование:** открытый интерес (число открытых контрактов) — ключевая метрика срочного рынка, недоступная из обычных свечей. Сигналы «цена × OI» показывают накопление/распределение позиций (классика анализа фьючерсов). Источник — **ISS API** (`engines/futures/markets/forts`), а не HTML-страница `moex.com/derivatives/open-positions` (она не API и парсить её не нужно).

**Данные (источник, подтверждено на 2026-08):**
- текущее значение: `securities/{SECID}.json` → блок `marketdata`: `OPENPOSITION` (контракты), `OICHANGE` (изменение к предыдущему дню); блок `securities`: `PREVOPENPOSITION`;
- история по датам: `forts/openpositions.json` (блок `history`: `TRADEDATE`, `SECID`, `CLOSE`, `VOLUME`, `OPENPOSITION`, `OPENPOSITIONVALUE`, `SETTLEPRICE`); точный способ запроса диапазона (`from`/`till`/`date`) уточняется на этапе реализации — задача «разведка ISS».

**Хранение:** таблица `market_open_positions` (см. §7) + `scripts/update_oi.py`. Скрипт из того же ответа ISS создаёт и дневные свечи фьючерса (`MarketCandle`) — без них сигналы «цена × OI» не рассчитываются.

**Расчёт (модуль `oi.py`):** вход — серия `(date, close, oi)` (цена из `MarketCandle`, OI из таблицы); выход: `values` — `oi`, `oi_change` (= oiₜ − oiₜ₋₁), `oi_change_pct` (= oi_change / oiₜ₋₁ · 100).

**Сигналы (по дневному изменению цены и OI):**

| Цена | OI | Сигнал | kind | severity | Трактовка |
|---|---|---|---|---|---|
| ↑ | ↑ | Strong Bull | `strong_bull` | strong | набор длинных позиций |
| ↓ | ↑ | Strong Bear | `strong_bear` | strong | открытие коротких позиций |
| ↓ | ↓ | Long Liquidation | `long_liquidation` | warning | закрытие длинных позиций |
| ↑ | ↓ | Short Covering | `short_covering` | warning | закрытие коротких позиций |

Сигнал считается только при `|ΔOI| ≥ oi_change_threshold_pct`% (иначе — без сигнала).

**Параметры:** `oi_change_threshold_pct` = 1.0 (мин. изменение OI для сигнала), `price_change_threshold_pct` = 0.0 (мин. изменение цены; при равенстве — нет сигнала).

**Сложность:** средне (не формула, а внешние данные: разведка эндпоинта истории, хранение, скрипт наполнения, специфика фьючерсов — тикеры и экспирации).

**Roadmap:** 1) разведка ISS: подтвердить эндпоинт истории OI, параметры диапазона и единицы; 2) миграция Liquibase `market_open_positions` + модель SQLAlchemy; 3) `scripts/update_oi.py` (загрузка с кэшем, повторными попытками; регистрация в админ-панели) + `app/market/oi_data.py`; 4) модуль `oi.py` (значения + сигналы) и юнит-тесты на синтетике; 5) валидация на реальном фьючерсе (сверка с сайтом MOEX); 6) реестр/API; 7) веб-страница; 8) движок стратегий (сигналы OI в контраргументах/рисках); 9) документация и статус.

**Критерии приёмки:** данные за указанный период скачиваются и строят график OI; сигналы соответствуют классике «цена × OI»; `pytest` зелёный; доступен через API и веб; описано в 10/14/17; статус в 12-roadmap обновлён.

## 10. Риски и открытые вопросы

- **Поддержка/сопротивление** — главный риск: эвристика без эталона. Митигация: валидация на истории MOEX с метриками отскоков/пробоев, поэтапные итерации.
- **OI — внешние данные, а не расчёт:** зависят от публикации ISS (открытые позиции появляются после вечернего клиринга); пропуски в ряду — обрабатывать как пропуски (не ошибки), не интерполировать. Единицы — контракты (не лоты/рубли; `OPENPOSITIONVALUE` — рубли).
- **Фьючерсные серии:** тикер контракта живёт ~квартал (например, W4V6 → W4Z6), к экспирации OI обнуляется. В этом этапе работаем с конкретным контрактом по SECID; склейка серий по базовому активу (continuous) — отдельная задача.
- **OI существует только для срочного рынка** (фьючерсы): для акций/облигаций модуль возвращает пустые значения с пометкой в `meta`.
- **Точность формул:** сверка с эталонными реализациями (pandas-ta/ta-lib) на синтетических рядах — в тестах, но зависимостей в рантайм не добавляем.
- **Данные MOEX:** праздники/неликвидные дни — окна строятся по фактическим датам свечей; нулевые объёмы — OBV и %K деградируют без ошибок (None).
- **Производительность API:** on-the-fly расчёт при большом `limit` — ограничение `limit`, при необходимости кэш (отдельное решение).
- **Калибровка порогов сигналов** (ADX 25, |ROC|, bandwidth-процентиль) — через существующий механизм калибровки/весов, отдельная задача.
- Отложены (не в этом этапе): VWAP, Ichimoku, свечные паттерны, Williams %R, Supertrend, дивергенции MACD.

# 16. Правила работы в проекте

**Статус:** утверждено v1.19 (сохранение согласованных макетов)
**Система:** NewsTrader Assistant

Свод правил для разработчиков и AI-агентов. Обязательны к выполнению при любой работе с репозиторием. Для AI-агентов краткая сводка продублирована в `AGENTS.md` (корень репозитория).

## 1. Обязательный цикл изменения

После согласований по §1.1 реализация проходит следующий цикл:

```
1. Изменить код
2. Проверить: compileall + pytest (+ smoke при изменении API/веба)
3. Обновить документацию, если затронуто описываемое поведение
4. Поднять версии затронутых документов
5. Закоммитить в git
6. Для стабильной рабочей версии — подготовить предложение аннотированного git-тега по §3.1
```

Пропуск шагов 2–5 недопустим.

### 1.1. Постановка, спецификация и реализация новых задач

Порядок обязателен для всех новых задач проекта, включая изменения процесса и документации. Исправления и уточнения уже начатой задачи продолжаются в её этапе, если согласованные цели и границы не изменились.

1. **Постановка:** описать цель, контекст, границы и проверяемые критерии готовности. Показать пользователю и спросить, устраивает ли постановка. После одобрения сохранить `tasks/<slug>.md` и создать коммит `tasks(scope): summary` в новой ветке от master по §3.2. До одобрения коммит постановки и реализация не разрешены.
2. **Спецификация и документация:** после фиксации и слияния постановки начать новую ветку от master. Задать необходимые уточняющие вопросы и подготовить конкретные документы: сценарии, ограничения, изменения и проверки; модель данных, API, UI и эксплуатацию — только если применимы. Получить одобрение документации и её коммита, затем создать `docs(scope): summary` или `spec(scope): summary`.
3. **Реализация:** только после одобрения, фиксации и слияния спецификации начать новую ветку от master. Выполнить согласованный объём и обязательные проверки, актуализировать применимые документы-дома. Уже полученные согласования повторно не запрашивать без изменения требований.
4. **Закрытие:** сопоставить результат с критериями. При полном выполнении перечислить выполненные критерии и проверки в описании завершающего коммита/PR, удалить файл задачи из Git и устранить действующие ссылки на него. Историю не переписывать, архив или копию задачи не создавать. При частичном выполнении оставить файл с выполненными пунктами, остатками, причинами и следующим шагом. Сокращение согласованного объёма требует решения пользователя.

Отсутствие ответа не означает одобрение. Согласование постановки не заменяет согласование спецификации. Существенные изменения целей или требований повторно согласуются в затронутой части. Одобрение коммита не является разрешением на push, PR или merge — эти действия требуют отдельного указания. Не обходить hooks ради фиксации этапа.

Спецификацию размещать в подходящем существующем документе либо зарегистрированном проектном документе. При завершении факты переносятся в документы-дома, спецификация проходит существующую архивацию; удаление относится к файлам задач в tasks/, а не ко всей документации. Владение файлами — [32](./32-docs-architecture.md). Для задач дорожной карты дополнительно обновить статус в [12](./12-roadmap.md). Порядок использования агентом — [проектный навык](../.agents/skills/task-spec-workflow/SKILL.md).

### 1.2. Регистрация скриптов в админ-панели

Любой новый скрипт в `scripts/` должен быть **зарегистрирован в админ-панели веб-интерфейса**: список `SCRIPTS` в `app/admin/runner.py` с полным описанием — назначение, что делает, параметры, **когда и с какой периодичностью запускать**. Без регистрации в админ-панели скрипт считается незавершённым.

### 1.3. Переменные окружения

При добавлении, переименовании или изменении способа заполнения переменной `.env` в той же задаче обязательно обновить `.env.example`. Для каждой новой переменной дать безопасное значение по умолчанию или пустой placeholder и пример допустимого формата; секреты заменять инструкцией по генерации/получению, не рабочим значением. Назначение и порядок настройки документировать в [13-operations.md](./13-operations.md), который остаётся источником полного перечня параметров. Перед коммитом проверить, что `.env.example` читается и не содержит реальных токенов, паролей или ключей.

## 2. Документация

- `docs/` ведётся **параллельно коду** — устаревшая документация считается дефектом.
- Каждый документ имеет шапку со статусом: `**Статус:** утверждено vX.Y`.
- Новый крупный раздел = новый файл `docs/NN-<slug>.md`, регистрируется в таблице `docs/README.md`.
- **Версионирование документов:** изменение содержания раздела поднимает его версию (v1.1 → v1.2). Некритичные правки (опечатки) — без смены версии.
- `docs/README.md` содержит актуальную общую версию комплекта и статус.
- К каким разделам обращаться при изменении:
  - поведение системы/функции → `04-functional-requirements.md`, `01-concept.md`;
  - архитектура/потоки → `06-architecture.md`;
  - модель данных/миграции → `07-data-model.md`;
  - команды запуска/скрипты → `13-operations.md`;
  - интерфейсы → `14-web-interface.md`, `15-telegram-bot.md`;
  - планы/статусы → `12-roadmap.md`.

### Согласованные макеты

Каждый явно согласованный пользователем макет сохранять в репозитории в `docs/design/`, а не только в чате или локальной папке визуализаций. Интерактивный макет сохранять как открываемый в браузере HTML; для других форматов сохранять исходник и доступное превью. В спецификации или документе-доме размещать относительную ссылку на макет, дату согласования и описание утверждённых решений. Использовать демонстрационные данные без секретов. Согласованную версию не заменять несогласованным вариантом; новый утверждённый вариант сохранять через историю Git с обновлением ссылки и описания при необходимости. При архивации спецификации сохранять доступность макета и исправлять относительные ссылки.

### 2.1. Правило единого источника истины (SSOT)

У каждого факта ровно один «дом»; остальные места — однострочное упоминание + ссылка. Карта владения и полный свод правил — [32-docs-architecture.md](./32-docs-architecture.md).

1. Копирование содержания другого документа запрещено: повторное изложение команд, таблиц `.env`, эндпоинтов API, маршрутов веба, полей модели данных заменяется ссылкой на документ-дом.
2. Версии пишутся только в шапке своего документа; версия комплекта — только в `docs/README.md`. Номера версий и счётчики документов не копируются в другие файлы (включая `AGENTS.md`).
3. **Жизненный цикл фича-ТЗ:** `проект → утверждено → реализовано → архив`. После реализации факты переносятся в базовые документы по карте владения, ТЗ сокращается до ADR-записи и перемещается в `docs/archive/`. Фича считается закрытой только после переноса и архивации.
4. Новый документ создаётся только для проектируемой фичи и регистрируется в README с пометкой «проект». Прежде чем создавать файл — проверить, нельзя ли добавить раздел в существующий документ-дом.
5. Если раздел базового документа разросся (~300+ строк) — он выносится в отдельный документ со ссылками, а не копируется.

## 3. Git

- **Коммит после каждой осмысленной группы изменений** (одна задача/фича — один коммит).
- Формат сообщения: `type(scope): summary` — `feat`, `fix`, `refactor`, `docs`, `spec`, `tasks`, `infra`, `test`, `chore`.
- **Секреты не коммитить**: `.env` и ключи остаются вне git.
- Не коммитить артефакты: `__pycache__`, `*.db`, `logs/`, `.venv/`.
- Стабильные, работоспособные версии отмечать **аннотированным тегом**: `git tag -a vX.Y.Z -m "..."`.
- Запрещён `force push` в основную ветку.

### 3.1. Обязательный выпуск стабильного тега

- После завершения и проверки значимой, работоспособной группы изменений исполнитель подготавливает рекомендуемый номер и текст аннотации, но **не создаёт тег самостоятельно**. Аннотация содержит понятную сводку разницы с предыдущим стабильным тегом: добавленные возможности, исправления, существенные изменения интерфейса/поведения и пройденные проверки. Для больших выпусков дополнительно готовятся развёрнутые release notes.
- Стабильный тег создаёт только пользователь после ручной проверки. Исполнитель создаёт тег лишь по явному запросу пользователя.
- Перед предложением тегирования рабочее дерево должно быть чистым, а обязательные для затронутых изменений проверки — пройдены. Тег должен указывать на последний коммит стабильного состояния.
- Формат — аннотированный семантический тег `vX.Y.Z`; сообщение кратко перечисляет главные изменения выпуска. Лёгкие исправления повышают `Z`, новая совместимая функциональность — `Y`, несовместимые изменения — `X`.
- При явном запросе пользователя новый тег сверяется с существующими тегами и не перезаписывает их; после создания проверяются его имя, аннотация и целевой коммит. Публикация в удалённый репозиторий выполняется только по явному запросу пользователя.
- При публикации нового стабильного тега в GitHub одновременно создаётся GitHub Release с тем же тегом. Его release notes содержат развёрнутую разницу с предыдущим стабильным тегом: добавленные возможности, исправления, существенные изменения интерфейса/поведения и пройденные проверки. Release создаётся только вместе с явно запрошенной пользователем публикацией тега.

### 3.2. Начало новой задачи и создание ветки

- Перед началом каждой новой задачи и каждого нового этапа по §1.1 проверить текущую ветку командой `git branch --show-current` и состояние рабочего дерева командой `git status --short`.
- Перед этапами спецификации и реализации убедиться, что предыдущий этап слит в master. Если нет — согласовать продолжение с пользователем; не создавать ветку от неслитой ветки предыдущего этапа.
- Новую рабочую ветку создавать только от `master`, находясь на `master`: `git switch -c codex/<имя-задачи> master`.
- Если текущая ветка отличается от `master` или HEAD отсоединён, до изменения файлов и создания ветки спросить пользователя, как действовать. Сообщить текущую ветку/состояние и предложить переход на `master` с созданием новой ветки либо продолжение текущей работы по явному указанию пользователя.
- Не переключаться автоматически на `master` и не создавать ветку от текущей рабочей ветки. Отступление от этого порядка допустимо только по явному указанию пользователя.
- Продолжение уже начатой задачи и исправления в её PR выполняются в существующей ветке этой задачи; это не начало новой задачи.

## 4. Версионирование

| Объект | Правило |
|---|---|
| Документация (docs/) | `v1.X` — при изменении разделов; общая версия в README |
| Релизы/теги | `v0.X.0`, `v1.X.0` — по значимости накопленных изменений |
| Приложение | `version` в `app/main.py` — поднимается при значимых фичах |
| Модели анализа/веса | `model_version` в движке стратегий |

## 5. Тестирование

- Юнит/интеграционные тесты: `pytest` (`tests/`, SQLite, асинхронные).
- Сквозная проверка API и веба: `scripts/smoke.py`.
- E2E-тесты веб-интерфейса (Playwright Test Runner, TypeScript): `tests/e2e/`, отдельный прогон `npx playwright test`; pytest запускает только Python-тесты (см. [21-web-e2e-tests.md](./21-web-e2e-tests.md)).
- **Изменение веб-интерфейса (шаблоны, роуты, поведение страниц) обязательно сопровождается актуализацией e2e-тестов:** для новой функциональности — добавляются тесты; для изменённой — правятся; для удалённой — удаляются. После любых UI-изменений — прогон `npx playwright test`.
- Перед коммитом изменений кода и связанных конфигураций: `compileall` + `pytest`; при изменении API/веба/бота — ещё и `smoke`; при изменении веб-интерфейса — обязателен `npx playwright test`. Для изменений только документации и прочих файлов вне области Python-проверки тяжёлый прогон hooks пропускается.
- Новый код, влияющий на поведение, должен покрываться тестом.

### 5.1. Автоматические проверки

- На каждом рабочем клоне устанавливаются `pre-commit` и `commit-msg` hooks; установка и ручной запуск — [13-operations.md](./13-operations.md) §7.
- Локальный hook проверяет изменённые файлы на ошибки корректности Python, синтаксис конфигураций, маркеры конфликтов, секреты и запрещённые артефакты; для кода и связанных конфигураций запускает полный `compileall` + `pytest`.
- Hook `commit-msg` проверяет формат из §3. История существующих коммитов не переписывается.
- В CI статические проверки выполняются на всех отслеживаемых файлах; полный pytest и Playwright запускаются отдельными заданиями. Автоматические проверки дополняют ручную проверку документации и smoke.
- Относительные Markdown-ссылки и якоря в заголовках проверяются hook; внешний HTTP(S) не проверяется при коммите. API-контракт `openapi/openapi.json` генерируется из FastAPI, должен обновляться вместе с API и проходит Redocly lint. Pull request дополнительно сравнивается с базовой веткой на ломающие изменения через oasdiff; команды — [13-operations.md](./13-operations.md) §7.4.
- Новое исключение в `.secrets.baseline` допустимо только после проверки, что это публичный пример, тестовое значение или ложное срабатывание. Добавлять настоящий секрет в baseline запрещено.
- Инструменты разработки размещаются в `tools/`; эксплуатационные скрипты в `scripts/` по-прежнему подчиняются §1.2.

## 6. База данных

- Схема управляется **только через Liquibase**: новый файл `liquibase/changelogs/NNN_*.xml`, включение в `changelog-master.xml`, применение `docker compose up --build migrations`.
- Приложение не пересоздаёт схему в окружениях с `AUTO_CREATE_SCHEMA=false`.
- Изменение SQLAlchemy-модели всегда сопровождается миграцией (и наоборот).
- Прекомишены прекондиции `onFail="MARK_RAN"` — менять схему без них не следует.

- [ ] `compileall` проходит
- [ ] `pytest` зелёный
- [ ] `smoke` пройден (если затронуты API/веб/бот)
- [ ] Документация актуальна, версии затронутых разделов подняты
- [ ] При изменении переменных `.env` обновлён и проверен `.env.example` с безопасными примерами

- [ ] `docs/README.md` обновлён (если менялась структура/версия комплекта)
- [ ] Сообщение коммита по формату `type(scope): summary`
- [ ] Секреты и артефакты не попали в коммит

## 8. Стандарт кнопок CRUD в веб-интерфейсе

Для всех списков и карточек сущностей в веб-интерфейсе используется **единый стандарт действий** (эталон — блок «Новости» `/news` и «Дополнение графа» `/admin/graph`). Новые функции обязаны следовать этому стандарту.

| Действие | Кнопка | Поведение |
|---|---|---|
| **Редактировать** | `✎` (класс `.feed-edit`, `data-id=...`) | Переводит строку/карточку в режим редактирования (поля становятся изменяемыми) |
| **Сохранить** | `✓` (тот же элемент после клика по `✎`) | Сохраняет изменения (`POST {route}/update`) и выводит карточку из режима редактирования |
| **Удалить** | `✕` (класс `.feed-remove`, внутри `<form method="post" action="{route}/remove">`) | `POST {route}/remove` удаляет запись |

**Обязательные требования:**
- Кнопка изменения/удаления кладётся в строку справа, раздельно; клики не должны совпадать с переходом по ссылке на карточку.
- Удаление — через `<form method="post">` (не `GET`), с кнопкой `type="submit"`. При необходимости — подтверждение через `onsubmit="return confirm(...)"`.
- Для авторизованных действий (удаление/изменение) сервер проверяет аутентификацию и перенаправляет на `/login`, если пользователь не вошёл.
- Стили переиспользуются: `.feed-edit` / `.feed-remove` (уже в `app/web/static/style.css`). Новый набор кнопок не дублирует цвета/размеры.
- Роуты действий — `POST /{entity}/{id}/delete`, `POST /{entity}/{id}/update` (или `/{entity}/{id}` аналогично `/news`), редирект после действия — на ту страницу, с которой пришёл запрос.

**Использование в проекте:** блоки «Новости» (`/news`), «Дополнение графа» (`/admin/graph`) и карточки «Теханализ в LLM» (`/securities/{ticker}`, кнопка удаления `✕`).

### 8.1. Стиль обычных кнопок действий

Для **кнопок действий** (запуск, переход, отправка формы) используется единый класс `.btn` из `app/web/static/style.css`. Эталон — кнопки **«Сделать скриншот»** и **«Теханализ в LLM»** на карточке бумаги (`/securities/{ticker}`).

- Кнопка: `padding: 8px 14px`, `border-radius: 8px`, фон `--panel-2`, текст `--text`, рамка `--border`, при наведении (`:hover`) — акцентная рамка и цвет текста (`--accent`). Никаких собственных переопределений цвета/фона.
- Обычная кнопка — `<button class="btn" type="button">`; отправка формы — `<button class="btn" type="submit">` внутри `<form ... class="btn-form">` (стиль `display:flex;gap:10px;flex-wrap:wrap`, чтобы кнопка оставалась чистым `.btn`).

**Запрещено:** переопределять вид `.btn` через обёрточные селекторы наподобие `.inline-add button` (задают фон `--accent`/белый текст и «съедают» hover — текст кнопки становится цвета фона и пропадает при наведении). Если нужен отступ/раскладка — используй собственный flex-класс на **форме**, не на кнопке.

Если кнопка должна быть «первичной» (акцентной) — используй `class="btn active"` (заголовочный акцентный фон), а не дублирующий стиль.

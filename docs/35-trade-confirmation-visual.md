# 35. Свечная схема подтверждения сделки и оглавление теханализа — ТЗ

**Статус:** проект v1.0 (ожидает согласования)
**Система:** NewsTrader Assistant

## 1. Цель и границы

В полном ответе «Теханализ в LLM» пользователь должен видеть порядок событий перед входом: подход к уровню, пробой или отбой, закрытие свечи, закрепление, возможный ретест и допустимый вход. Длительность ожидания, условия подтверждения и отмены берутся из конкретного ответа, а не вычисляются по общему шаблону. Справа нужно оглавление глав длинного ответа по образцу страницы «Индикаторы».

Схема иллюстрирует **ожидаемый сценарий**, а не рисует прогнозные рыночные цены и не подменяет реальные свечи. Исторические свечи на этой схеме не показываются: они описывают уже случившееся и могли бы создать ложное впечатление, что будущие условия уже выполнены. Реальные свечи остаются на карточке бумаги и странице индикаторов.

## 2. Сценарии использования и требования

- **UC-35-01.** Пользователь открывает `/tech_analysis/{id}`, переходит через «На этой странице» к главе 10 и видит под её заголовком схему подтверждения основного сценария A.
- **UC-35-02.** Если в анализе есть осмысленные планы подтверждения для B или C, пользователь переключает сценарий; схема, условия входа и отмены меняются вместе. Сценарий без плана не получает пустой вкладки.
- **UC-35-03.** Пользователь последовательно читает отмеченные этапы на свечной схеме и видит требуемый таймфрейм, число закрытых свечей и/или время закрепления. Неуказанное условие обозначается «не указано», без догадки приложения.
- **UC-35-04.** Пользователь сравнивает подтверждающие сигналы (например, объём, OI) и условия отмены; эти признаки показываются только когда они есть в анализе.
- **UC-35-05.** Старый или неполный ответ остаётся читаемым. Оглавление строится из фактических заголовков; при отсутствии пригодного структурированного плана под главой 10 остаётся её текст и компактное сообщение, что схема для этого ответа недоступна.

- **FR-35-01.** Схема показывает от 2 до 8 указанных в ответе ценовых этапов и отметки «ожидать»/«вход»; направление SELL зеркально BUY. Числовую ось цены не строить, если ответ не даёт сопоставимые уровни. Подпись «Схема условий, не реальные и не прогнозные свечи» видна постоянно.
- **FR-35-02.** Для каждого этапа доступны его название и объяснение текстом, а не только цветом. Запрещено изображать уже выполненное подтверждение, если статус в анализе — ожидание (`await_confirmation=true`); этапы помечаются как условия, а не текущие сигналы.
- **FR-35-03.** `WAIT` без конкретного плана входа не получает кнопку/метку «Покупать» или «Продавать». Для BUY/SELL метка входа означает «только после перечисленных подтверждений», не приказ к немедленной сделке.
- **FR-35-04.** Оглавление включает фактические заголовки глав ответа уровня H2 (включая главу 10), ссылку на «Сценарии» при наличии карточек, переход по якорю и выделение текущей главы. Дублирующиеся заголовки получают уникальные ID. На широком экране блок закреплён справа; на узком доступен сворачиваемый блок над ответом, без горизонтальной прокрутки. Навигация работает с клавиатуры.
- **FR-35-05.** Оригинальный Markdown-ответ и скачиваемый `response.md` остаются полными. При повреждённом или отсутствующем JSON страница не падает и не строит выдуманную схему.

## 3. Структура данных и правила извлечения

Промпт [promt_tech_analize.md](./promt_tech_analize.md) должен попросить LLM согласовать текст главы 10 и завершающий JSON. В корень существующего JSON добавляется необязательный объект `confirmation_plans` с ключами `a`, `b`, `c`. Каждый план содержит:

| Поле | Тип | Назначение |
|---|---|---|
| `direction` | `buy` / `sell` / `wait` | Направление сценария |
| `timeframe` | строка или `null` | Таймфрейм из текста ответа |
| `level_label` | строка или `null` | Название ключевого уровня/зоны, если указан |
| `steps` | список из 2–8 объектов | Упорядоченные ценовые события: `approach`, `breakout`, `close`, `retest`, `hold`, `entry`, `invalidation`; у каждого `label` и `detail` |
| `closed_candles` | положительное целое или `null` | Сколько закрытых свечей нужно для закрепления |
| `wait_minutes` | положительное целое или `null` | Время ожидания, только когда оно явно задано |
| `confirmations` / `cancellations` | списки строк | Дополнительные подтверждения и условия отмены |

Пример одного плана (синтетический, для формата):

```json
{
  "direction": "buy",
  "timeframe": "1ч",
  "level_label": "зона 100–102",
  "steps": [
    {"kind": "approach", "label": "Подход к зоне", "detail": "Дождаться касания зоны"},
    {"kind": "close", "label": "Закрытие выше", "detail": "Часовая свеча закрывается выше зоны"},
    {"kind": "retest", "label": "Ретест", "detail": "Зона удерживается при возврате"},
    {"kind": "entry", "label": "Вход", "detail": "Только после удержания зоны"}
  ],
  "closed_candles": 1,
  "wait_minutes": null,
  "confirmations": ["объём выше среднего"],
  "cancellations": ["закрытие ниже зоны"]
}
```

Сервер разбирает и ограничивает допустимые типы, длины строк, число этапов и значения длительности; неизвестные типы и некорректные планы пропускает. `scenario_json` сохраняет планы вместе с существующими `scenario_a/b/c`; новая таблица и миграция не нужны. Данные схемы не извлекаются регулярными выражениями из старого свободного текста, чтобы не приписывать ему отсутствующие сроки или уровни.

Свечи схемы строятся детерминированно из последовательности типов событий и направления, в относительных координатах без оси реальной цены. Их форма служит визуальной метафорой порядка этапов; числовые уровни, длительность и подписи берутся только из валидированного плана. Цвет и штриховка различают ожидание, подтверждение, отмену и вход, но текстовые подписи всегда сохраняются.

## 4. UI, API и совместимость

Страница `/tech_analysis/{id}` получает валидированные планы и список фактических заголовков Markdown. Схема вставляется непосредственно после заголовка главы 10; если заголовок отсутствует, отдельный блок схемы выводится перед ответом с явной подписью. Переключатель сценариев показывается только при двух и более валидных планах. Ни навигация, ни схема не меняют вердикт и не инициируют торговое действие.

Внешние API и формат скачивания Markdown не меняются. Существующие `/v1/tech-analysis/{id}/status` и `/response.md` продолжают работать без новых полей. Структура `confirmation_plans` остаётся внутренней частью `scenario_json` модели `TechAnalysis`; при будущем публичном экспорте планов понадобится отдельная версия API-контракта. Новых переменных `.env`, скриптов и внешних библиотек не требуется.

## 5. Приёмка

Проверить BUY и SELL, переключение A/B/C, наличие и отсутствие числа свечей/времени, план с дополнительными подтверждениями и отменой, `WAIT`, неполный и старый ответ, дубли заголовков, отсутствие главы 10, клавиатуру и экран 375 px. Отдельно проверить, что скачанный Markdown не изменился, а некорректный JSON не ломает страницу. Добавить unit-тесты разбора и построения схемы, обновить Playwright-сценарии; после реализации выполнить pytest, compileall, smoke, `npx playwright test` и проверки OpenAPI.

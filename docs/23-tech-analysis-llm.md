## 1. Обоснование

Пользователь, разбирающий бумагу (акцию или фьючерс) на странице анализа (`/securities/{ticker}`), хочет **отправить полный технический анализ выбранной бумаги во внешнюю LLM (ChatGPT)** и получить практический торговый разбор по промту `docs/promt_tech_analize.md` (уровни входа, стоп, цели, сценарии, итоговая оценка).

Сейчас такой возможности нет: промт и данные собираются вручную, результат не сохраняется, процесс непрозрачен. Требуется:

- запуск анализа **одной кнопкой** прямо со страницы бумаги;
- **видимые этапы** обработки (актуализация данных → формирование запроса → отправка в LLM → ожидание ответа), чтобы не было подозрений, что запрос «упал и не выполнится»;
- **история результатов** в виде карточек на странице бумаги (не более 4 на страницу + пагинация): дата анализа, вердикт **Купить/Продать/Выжидать**, точка входа, цена TP, цена SL;
- **страница полного ответа** LLM в исходном форматировании;
- **скачивание** запроса и ответа в Markdown;
- **повтор** неудачного запроса с тем же запросом;
- видимость неудачных запросов наравне с другими неудачными операциями (SystemNotice в шапке на всех страницах + карточка со статусом `failed` и кнопкой «Повторить»).

## 2. Термины

| Термин | Определение |
|---|---|
| Теханализ в LLM | Фоновый процесс: дособор актуальных данных по бумаге → формирование Markdown-запроса (данные + промт) → отправка в ChatGPT → сохранение полного ответа и разбор вердикта |
| Карточка результата | Краткая сводка одного выполненного анализа: дата, вердикт, точка входа, TP, SL |
| Запрос (request) | Markdown-текст: данные по бумаге (свечи, объём, уровни, индикаторы, OI/клиентские группы/базис для фьючерсов) + полный текст промта `promt_tech_analize.md` |
| Ответ (response) | Полный ответ LLM ChatGPT в исходном форматировании (Markdown) |
| Вердикт | `BUY` (Купить) / `SELL` (Продать) / `WAIT` (Выжидать) из итоговой оценки LLM |

## 3. Сценарии использования (UC)

- **UC-1. Запуск теханализа.** Пользователь на странице `/securities/{ticker}` (акция или фьючерс) нажимает кнопку **«Теханализ в LLM»**. Система создаёт запись анализа и запускает фоновый процесс.
- **UC-2. Отслеживание этапов.** Пока процесс идёт, на странице показывается панель этапов: **1) Актуализация данных → 2) Формирование запроса → 3) Отправка в LLM → 4) Ожидание ответа**. Текущий этап подсвечивается; страница автоматически обновляется (поллинг), пока процесс не завершится.
- **UC-3. Карточки результатов.** Внизу страницы — карточки выполненных анализов по этой бумаге: **не более 4 на страницу + пагинация**. Карточка: дата анализа, вердикт (Купить — зелёный / Продать — красный / Выжидать — жёлтый), **Точка входа**, **TP**, **SL**. Клик по карточке открывает страницу полного ответа.
- **UC-4. Страница полного ответа.** `GET /tech_analysis/{id}` — полный ответ LLM в исходном форматировании (заголовки, таблицы, эмодзи). Рендер Markdown → HTML на клиенте (`marked.js` + `DOMPurify`), как в проекте принято подключать библиотеки локально.
- **UC-5. Скачивание запроса.** Кнопка **«Скачать запрос (MD)»** активна сразу после формирования запроса (этап 2 завершён) — ещё до отправки в LLM. Скачивается ровно тот Markdown, который ушёл (или уйдёт) в LLM.
- **UC-6. Скачивание ответа.** Кнопка **«Скачать ответ (MD)»** — ровно тот Markdown, который прислала LLM.
- **UC-7. Повтор неудачного запроса.** Если запрос в LLM упал (ошибка сети, таймаут, ошибка API), карточка получает статус `failed` и кнопку **«Повторить»**. Повтор отправляет **тот же сохранённый запрос** (без повторного дособора данных).
- **UC-8. Видимость неудачных запросов.** При падении создаётся `SystemNotice` (источник `tech_analysis_llm`, уровень `critical`) — отображается в шапке на всех страницах, как неудачные скрипты. На странице бумаги запись видна как карточка `failed` с текстом ошибки и кнопкой «Повторить».

## 5. Модель данных

Миграция **`liquibase/changelogs/021_tech_analysis.xml`** (включить в `changelog-master.xml`), таблица **`tech_analyses`**:

| Колонка | Тип | Описание |
|---|---|---|
| `id` | SERIAL PK | Идентификатор |
| `user_id` | INT NULL (FK → users.id) | Инициатор (если авторизован) |
| `ticker` | VARCHAR(32) NOT NULL | Тикер бумаги (акция или фьючерс) |
| `is_future` | BOOLEAN NOT NULL DEFAULT false | Фьючерс ли это (влияет на дособор OI и разделы запроса) |
| `status` | VARCHAR(20) NOT NULL DEFAULT 'running' | `running` \| `success` \| `failed` |
| `stage` | VARCHAR(30) NULL | `refreshing_data` \| `forming_request` \| `awaiting_llm` \| `done` |
| `request_md` | TEXT NULL | Сформированный запрос (до отправки в LLM) |
| `response_md` | TEXT NULL | Полный ответ LLM |
| `verdict` | VARCHAR(10) NULL | `BUY` \| `SELL` \| `WAIT` |
| `entry` | VARCHAR(64) NULL | Точка входа (число или диапазон «3200–3250») |
| `tp` | VARCHAR(64) NULL | Цель (TP) |
| `sl` | VARCHAR(64) NULL | Стоп (SL) |
| `model` | VARCHAR(64) NULL | Модель ChatGPT, которой отправлен запрос |
| `error` | TEXT NULL | Текст ошибки (при `failed`) |
| `created_at` | TIMESTAMP NOT NULL DEFAULT now() | Дата создания |
| `finished_at` | TIMESTAMP NULL | Дата завершения |

Индексы: `(ticker, id)` для пагинации карточек; `(status)` для stale-маркировки.

Значения `entry/tp/sl` хранятся строкой (LLM может вернуть диапазон); для карточки допускается одно число или диапазон. Если LLM не вернула JSON-блок и fallback-регэксп не сработал — карточка сохраняется без вердикта (полный ответ доступен), это **не ошибка**.

## 7. Формирование запроса (Markdown)

Запрос собирается из данных по тику и полного текста промта. Состав данных зависит от типа бумаги:

**Общее (акция и фьючерс):**
- шапка: тикер, тип бумаги, дата формирования, текущая цена, изменение за день;
- свечи (Daily) в **трёх окнах** — старший/средний/младший таймфрейм: 1Y, 3M, 1M (последние ~30 свечей каждого окна таблицей `дата | open | high | low | close | volume`);
- объём (последние свечи);
- уровни поддержки/сопротивления (модуль `support_resistance`);
- Volume Profile (POC, VAH, VAL, HVN/LVN, метка «в/вне Value Area») — модуль `volume_profile`;
- индикаторы: RSI(14), ATR(14) и `atr_pct`, ADX/DI, EMA fast/slow, MACD, полосы Боллинджера (верх/низ, %B) — значения/сигналы на последней свече.

**Дополнительно для фьючерсов:**
- OI: серия, сигнал «цена × OI» (`oi_data.latest_oi_signal`);
- клиентские группы физ/юр (нетто long−short, доля физиков, Δ OI) — таблица за последние дни;
- базис «фьючерс против спота»: разница (и/или отношение) цены ближайшего фьючерса и спотовой цены базового актива.

**Промт:** после блока данных — полный текст `promt_tech_analize.md` + постскриптум о формате ответа:

```
В самом конце ответа добавь блок ```json``` с полями:
{"direction": "BUY|SELL|WAIT", "entry": "...", "tp": "...", "sl": "...", "risk_reward": "..."}
entry/tp/sl — число или диапазон "3200-3250"; если рекомендация WAIT — entry/tp/sl пустые строки.
```

Первая версия — **текстовый формат** (без скриншотов). Скриншоты графиков (vision, `gpt-4o`) — отдельная задача (см. §11).

## 8. API (REST, версия `/v1`) и веб-роуты

| Метод и путь | Назначение |
|---|---|
| `POST /v1/tech-analysis` `{ticker}` | Запуск теханализа → `202 {id}` |
| `GET /v1/tech-analysis?ticker=SBER&page=1&per_page=4` | Карточки (пагинация ≤4) |
| `GET /v1/tech-analysis/{id}` | Полная запись (статус/этап/запрос/ответ/вердикт) — используется поллингом |
| `POST /v1/tech-analysis/{id}/retry` | Повтор с тем же `request_md` (только `failed`) → `202 {id}` |
| `GET /v1/tech-analysis/{id}/request.md` | Скачивание запроса (`text/markdown`, `Content-Disposition: attachment`) |
| `GET /v1/tech-analysis/{id}/response.md` | Скачивание ответа (`text/markdown`, `Content-Disposition: attachment`) |
| `POST /securities/{ticker}/tech-analysis` (веб-форма) | Запуск со страницы бумаги → redirect на карточку |
| `GET /tech_analysis/{id}` (веб) | Страница полного ответа |
| `GET /tech_analysis/{id}/request.md` / `response.md` (веб) | То же скачивание для браузера |

Документация API — в `10-api-specification.md` (обновляется при реализации).

## 9. UI

### 9.1. Страница бумаги `/securities/{ticker}`

- Кнопка **«Теханализ в LLM»** (в шапке карточки; если `CHATGPT_API_KEY` пуст — недоступна с подсказкой).
- **Панель этапов** (видна, пока есть активный запуск): шаги «Актуализация данных → Формирование запроса → Отправка в LLM → Ожидание ответа», текущий подсвечен, поллинг раз в ~3 с.
- **Список карточек** внизу страницы: не более **4 на страницу + пагинация** (по тикеру). Карточка — ссылка на `/tech_analysis/{id}`:
  - дата анализа (дд.мм.гггг чч:мм);
  - вердикт: **Купить** (зелёный) / **Продать** (красный) / **Выжидать** (жёлтый);
  - **Точка входа**, **TP**, **SL**;
  - для `failed` — статус «Ошибка» + кнопка «Повторить» (без перехода на страницу ответа).

### 9.2. Страница ответа `/tech_analysis/{id}`

- Полный ответ LLM в исходном форматировании (Markdown → HTML: `marked.js` + `DOMPurify`, локальные копии в `app/web/static/`);
- кнопки **«Скачать запрос (MD)»** (доступна, если `request_md` есть — в т.ч. во время выполнения) и **«Скачать ответ (MD)»**;
- при `failed` — текст ошибки и кнопка **«Повторить»**.

## 10. Обработка ошибок и повтор

- Ошибки LLM (сеть, таймаут, 4xx/5xx, пустой ответ) → `status=failed`, `error`, `add_notice(level="critical", source="tech_analysis_llm")` (поповер в шапке, как у скриптов), `finished_at`.
- Ошибка на этапе дособора данных (MOEX недоступен и т.п.) → то же, `error` с описанием этапа.
- **Повтор**: `POST .../retry` переводит запись в `running`, этап `awaiting_llm`, повторно отправляет сохранённый `request_md` (данные не пересобираются).
- При старте приложения записи `running` помечаются `failed` (stale), текст ошибки — «Прервано перезапуском приложения».
- Конкурентный запуск: если для тикера уже есть активный (`running`) анализ — второй запрос отклоняется (`409`), панель показывает существующий.

## 11. Недостающие данные/графики (отдельный план)

Промт `promt_tech_analize.md` требует сигналы, часть которых ещё не имеет вкладок на `/indicators`. Отдельный план — [19-market-indicators.md](./19-market-indicators.md) §8.15–8.16:

1. **RSI** — полноценный индикатор в реестре (сейчас — функция `rsi()` в `app/market/indicators/rsi.py` без вкладки/API); в запрос LLM значение попадает уже с первой версии.
2. **Бары объёма** на графике цены (карточка бумаги и вкладки `/indicators`); данные есть (`MarketCandle.volume`).
3. **Базис «фьючерс против спота»** — новый индикатор (для фьючерсов): разница цены ближайшего фьючерса и спота.
4. **Мультитаймфрейм** (внутридневные 60-мин свечи, MOEX `interval=60`) — отдельная задача roadmap (требует хранения внутридневных свечей). В первой версии запроса — три окна дневных свечей (1Y/3M/1M) как старший/средний/младший таймфреймы.
5. **Скриншоты графиков в запросе** (vision, `gpt-4o`) — последующий шаг после появления вкладок; формат запроса остаётся Markdown (данные + промт), изображения добавляются как блок.

## 12. Тестирование

- **Unit:** сборщик запроса (акция/фьючерс, наличие всех разделов), парсер вердикта (JSON-блок, fallback-регэксп, пустой ответ), сервис (стадии, ошибка → `failed` + нотис, повтор, конфликт дублей), конфиг (значения по умолчанию).
- **pytest** (SQLite) + `compileall`; `smoke` — при изменении API/веба.
- **E2E** (Playwright, `tests/e2e/`): кнопка «Теханализ в LLM», панель этапов, карточки и пагинация, страница ответа, скачивание `request.md`/`response.md`, повтор при `failed`. E2E использует мок-ответ ChatGPT (в тестовом окружении LLM не вызывается) — см. `21-web-e2e-tests.md`.

## 13. Критерии приёмки

- Кнопка «Теханализ в LLM» на карточке акции и фьючерса; при пустом `CHATGPT_API_KEY` — недоступна с пояснением.
- Процесс проходит этапы (UC-2); `request_md` сохраняется до отправки; «Скачать запрос» активна сразу после этапа 2.
- После завершения — карточка с датой, вердиктом Купить/Продать/Выжидать, точкой входа, TP, SL; на странице не более 4 карточек + пагинация.
- Страница `/tech_analysis/{id}` показывает полный ответ в исходном форматировании; оба MD-скачивания работают.
- Неудачный запрос: карточка `failed` + нотис в шапке + «Повторить» (повтор с тем же запросом).
- `compileall` + `pytest` + `smoke` + `pytest -m e2e` зелёные; документация (10/13/14/17/12/19/README) актуальна.

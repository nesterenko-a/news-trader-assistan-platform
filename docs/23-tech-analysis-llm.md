# 23. Теханализ в LLM — отправка технического анализа бумаги в ChatGPT

**Статус:** реализовано v1.0
**Система:** NewsTrader Assistant
**Приоритет задачи:** P0 (этап 2 дорожной карты, «Углубление аналитики»)

## 1. Обоснование и цели

Пользователь, разбирающий ценную бумагу (акцию или фьючерс) на странице `/securities/{ticker}`, хочет получить **внешний независимый технический разбор** от LLM ChatGPT на основе всех данных, которые накопила система: цена, объём, уровни поддержки/сопротивления, Volume Profile, RSI, индикаторы, а для фьючерсов — OI, клиентские позиции Long/Short, базис.

Цель — ускорить принятие торгового решения: вместо самостоятельного чтения множества индикаторов пользователь получает структурированный вердикт с точкой входа, ценой TP и SL.

**Не-цели:**
- Не является заменой движка стратегий (`app/strategy/engine.py`) — это дополнительный, внешний по отношению к внутреннему вердикту разбор.
- Не выполняет автоматических сделок (см. «Дальний TODO» в `12-roadmap.md`).
- В MVP — текстовый (Markdown) запрос; передача скриншотов графиков — отдельная задача.

## 2. Термины

| Термин | Значение |
|---|---|
| **Теханализ** | Отправка полного набора данных по бумаге в LLM ChatGPT для технического разбора |
| **Карточка-результат** | Краткий итог одного анализа: дата, вердикт, точка входа, TP, SL |
| **Сценарий A/B/C** | Сценарии из раздела «9. Моя стратегия» ответа LLM (основной/альтернативный/негативный) |
| **Этап** | Стадия исполнения анализа: `refreshing_data` → `forming_request` → `awaiting_llm` |
| **JSON-блок** | Обязательный машинно-читаемый блок в конце ответа LLM для парсинга |

## 3. Пользовательские сценарии (UC)

- **UC-01. Запуск теханализа.** На странице бумаги (`/securities/{ticker}`, доступно для акций и фьючерсов) пользователь нажимает кнопку **«Теханализ в LLM»**. Система запускает фоновый анализ и сразу показывает признак обработки — чтобы не было подозрений, что запрос «упал».
- **UC-02. Наблюдение за этапами.** Пользователь видит текущий этап: «актуализация данных», «формирование запроса», «отправка в LLM / ожидание результата».
- **UC-03. Просмотр результата.** После завершения внизу страницы появляется карточка-результат: дата, Купить/Продать/Выжидать, точка входа, цена TP, цена SL.
- **UC-04. Пагинация.** Если анализов больше четырёх — на странице не более **4 карточек** + пагинация для остальных.
- **UC-05. Полный ответ.** По клику на карточку пользователь попадает на страницу `/tech_analysis/{id}` с полным ответом LLM в исходном форматировании (Markdown → HTML).
- **UC-06. Скачать запрос.** На странице ответа доступна кнопка **«Скачать запрос для LLM в MD»** — скачивание сформированного запроса в формате Markdown. Кнопка активна **сразу после формирования запроса** (до отправки в LLM).
- **UC-07. Скачать ответ.** Кнопка **«Скачать ответ от LLM в MD»** скачивает точный ответ, который прислала ChatGPT.
- **UC-08. Повтор при сбое.** Если запрос в LLM упал, пользователь может отправить запрос **повторно с тем же запросом**. Информация о неудачном запросе появляется в общих уведомлениях (шапка, на всех страницах) — как и другие неудачные операции.

## 5. Модель данных (миграция)

Схема управляется через Liquibase (по правилу 6 working-process). Новый ченджлог `liquibase/changelogs/021_tech_analysis.xml`, включается в `changelog-master.xml`.

**Таблица `tech_analyses`:**

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | INTEGER PK autoincrement | Идентификатор |
| `user_id` | INTEGER nullable FK → users | Кто запустил (если авторизован) |
| `ticker` | VARCHAR(50) | Тикер бумаги |
| `is_future` | BOOLEAN | Признак фьючерса (для сборки данных и названия) |
| `status` | VARCHAR(20) | `running` / `success` / `failed` |
| `stage` | VARCHAR(30) | Текущий этап: `refreshing_data` / `forming_request` / `awaiting_llm` / `done` |
| `request_md` | TEXT | Сформированный Markdown-запрос |
| `response_md` | TEXT nullable | Полный Markdown-ответ LLM |
| `verdict` | VARCHAR(20) nullable | Итоговая оценка: `buy` / `sell` / `wait` |
| `entry` | VARCHAR(50) nullable | Точка входа (из Сценария A) |
| `tp` | VARCHAR(100) nullable | Цена/цены TP |
| `sl` | VARCHAR(50) nullable | Цена SL |
| `scenario_json` | TEXT nullable | JSON всех сценариев A/B/C (для карточек на странице ответа) |
| `model` | VARCHAR(100) nullable | Модель LLM, которая выполнила анализ |
| `error` | TEXT nullable | Описание сбоя |
| `created_at` | TIMESTAMP | Создание |
| `finished_at` | TIMESTAMP nullable | Завершение (успех/сбой) |

SQLAlchemy-модель `TechAnalysis` в `app/db/models.py` меняется вместе с миграцией.

## 7. Формат запроса в LLM

- Запрос — **Markdown-текст** (MVP; скриншоты графиков — отдельная задача).
- Текстовая часть промта берётся из файла `docs/promt_tech_analize.md` (путь — в конфиге, при отсутствии файла — встроенный fallback-промт в коде).
- Файл промта дополняется **обязательным JSON-блоком** в конце ответа (структура ниже) — чтобы ответ было легко парсить.
- Промт читается с диска при старте/при формировании запроса; изменения файла применяются к новым анализам без перезапуска приложения.

**Структура JSON-блока:**

```json
{
  "verdict": "BUY|SELL|WAIT",
  "entry": "ч-ч или число",
  "tp": "ч / ч / ч",
  "sl": "число",
  "scenario_a": {"title": "...", "entry": "...", "stop": "...", "targets": "...", "why": "..."},
  "scenario_b": {"title": "...", "entry": "...", "stop": "...", "targets": "...", "why": "..."},
  "scenario_c": {"title": "...", "entry": "...", "stop": "...", "targets": "...", "why": "..."}
}
```

Карточка-результат (FR-23-03/08) заполняется из блока `Сценария A` (вердикт, вход, TP, SL). На странице ответа в шапке — карточки всех сценариев A/B/C (FR-23-08). Если JSON-блок отсутствует/непарсится — карточка создаётся без вердикта/уровней, но анализ считается успешным (не ошибка); данные запроса и ответа сохраняются и скачиваются.

## 8. Состав данных запроса (request_builder)

Запрос собирается из данных БД, которые предварительно актуализируются (этап `refreshing_data`).

Общие (акция и фьючерс):
- Тикер, тип инструмента, последняя цена, валюта.
- **3 окна дневных свечей** как три таймфрейма для анализа (старший/средний/младший): 1 год / 3 месяца / 1 месяц.
- Объём (последние свечи).
- **Уровни поддержки/сопротивления** (`support_resistance`).
- **Volume Profile** (POC, VAH, VAL, HVN/LVN) (`volume_profile`).
- **RSI** (серия значений + сигналы перекупленности/перепроданности).
- **Bollinger / ATR / ADX / EMA / MACD** (значения и сигналы).

Дополнительно для **фьючерсов**:
- **OI** (открытый интерес) и сигнал «цена × OI».
- **Клиентские позиции Long/Short** (физики/юрики, нетто) — из `client_groups_series`.
- **Базис «фьючерс против спота»** (разница фьючерс − спот, в пунктах и %).

Объём запроса ограничивается (например, окна свечей усекаются до актуального числа последних дней), чтобы уложиться в контекст LLM.

## 9. Этапы исполнения анализа

Фоновый asyncio-таск (по образцу запуска скриптов в `app/admin/runner.py`, поллинг страницы как `/admin/runs/{id}?partial=1`):

1. **`refreshing_data`** — актуализация данных: для акции — `sync_security_prices`; для фьючерса — `sync_security_prices` + `sync_security_oi` (и клиентских групп, если необходимо).
2. **`forming_request`** — сборка Markdown-запроса (`request_builder`); запись `request_md` в БД. **С этого момента кнопка «Скачать запрос (MD)» активна** (FR-23-06) — даже если отправка в LLM ещё не выполнена.
3. **`awaiting_llm`** — отправка запроса в ChatGPT (`app/tech_analysis/llm.py`), ожидание ответа.
4. **`done`** — парсинг ответа (JSON-блок → verdict/entry/tp/sl/scenario_json), сохранение `response_md`, статус `success`.

При ошибке на любом этапе: статус `failed`, `error`, `finished_at`; `add_notice(..., source="tech_analysis_llm")` — уведомление в шапке на всех страницах (как неудачные скрипты).

**Повтор (FR-23-07):** кнопка «Повторить» на failed-карточке → переходит к этапу `awaiting_llm` и повторно отправляет **тот же `request_md`** (данные не пересобираем, `refreshing_data`/`forming_request` не повторяются).

**Единовременность (FR-23-10):** при активной `running`-записи на тикер повторный запуск отклоняется с ошибкой 409.

**Stale-записи:** при старте приложения `running`-записи без завершения помечаются `failed` (по аналогии с `mark_stale_runs`).

## 10. Конфигурация (`.env`)

Добавляются поля в `app/config.py` (pydantic-settings) и `.env.example`:

```
# ChatGPT (тех. анализ в LLM). Отдельный токен, по аналогии с DeepSeek LLM_*.
CHATGPT_BASE_URL=https://api.openai.com/v1
CHATGPT_API_KEY=
CHATGPT_MODEL=gpt-4o
CHATGPT_REQUEST_TIMEOUT=120
# Путь к промту теханализа (Markdown); при отсутствии файла — встроенный fallback
TECH_ANALYSIS_PROMPT_FILE=docs/promt_tech_analize.md
```

Перед отправкой в LLM приложение проверяет: если `CHATGPT_API_KEY` пуст — анализ не запускается с понятной ошибкой.

## 11. Безопасность и правовые аспекты

- `CHATGPT_API_KEY` — секрет, живёт только в `.env` (не в репозитории, как `LLM_API_KEY`).
- Ответ LLM рендерится на странице как HTML из Markdown через санитизацию (`DOMPurify`) — защита от инъекций из ответа модели.
- «Теханализ в LLM» — **аналитическая справка, не торговая рекомендация**; на странице ответа присутствует дисклеймер (см. `11-security-compliance.md`).
- Пользователи видят результаты анализов всех (как стратегии), но запуск и повтор доступны авторизованным пользователям (как прочие функции).

## 12. Недостающие графики (входит в фазу 2 — отдельный план)

Промт требует данные, которых сейчас нет в реестре индикаторов / на графиках. Отдельный план в `docs/19-market-indicators.md`:

| Данные | Статус | Действие |
|---|---|---|
| **RSI** | Функция есть (`app/market/indicators/rsi.py`), но нет в реестре/API/вкладке | Добавить индикатор `rsi` в реестр: модуль (серия + сигналы overbought/oversold), API `/v1/indicators/rsi`, вкладка на `/indicators`, интеграция в движок |
| **Объём** | Есть `MarketCandle.volume`, баров нет | Бары объёма на SVG-графике цены (карточка и `/indicators`) |
| **Базис «фьючерс против спота»** | Нет | Блок/индикатор для фьючерсов через `nearest_future` + спотовая цена |
| **Клиентские группы Long/Short** | **Реализовано** на вкладке OI (`/indicators`, график нетто + таблица) | Использовать уже имеющиеся данные в запросе |
| **Мультитаймфрейм** | Только дневные свечи | Отдельная задача (внутридневные 60-мин свечи, MOEX `interval=60`); в MVP — 3 окна дневных свечей |

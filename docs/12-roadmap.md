**Цель:** проверить ключевую гипотезу — система умеет давать обоснованный вердикт по бумаге.

**Фокус среза:** рынок Мосбиржи; сектора авиация + нефть (AFLT, LKOH, GAZP и связанные бумаги). Стек: Python + FastAPI + PostgreSQL, граф в таблицах, NLP через LLM API (DeepSeek → OpenAI).

| Задача | Результат | Статус |

| Конвейер сбора новостей: RSS российских агентств + Telegram-каналы | Работающий сбор, нормализация, дедупликация; автоматический запуск по расписанию | RSS ✅ / Telegram (источник) ✅ |

**Ограничение бэкфилла новостей:** RSS-ленты отдают только последние элементы (глубина — обычно от нескольких дней до недель), поэтому «полная» историческая загрузка через RSS невозможна. Глубокая история (месяцы/годы) доступна через архивы Telegram-каналов и поисковые API источников. Уже сейчас скрипты `collect_news` и `daily_pipeline` поддерживают окно сбора `--days N` / `--from YYYY-MM-DD`, а `collect_news --entity <имя>` — точечный сбор по сущностям (см. [13-operations.md](./13-operations.md)).

Первый срез: получение счетов, позиций, остатков, поиск инструментов и рыночные данные для аналитики; определить пользовательские сценарии и связь с существующим подключением Т-Инвестиций. При проектировании проверить доступные инструменты через `tools/list`, поддержку выбранной LLM, сертификаты TLS, хранение токенов и изоляцию пользователей; ограничить вызовы разрешёнными инструментами чтения. До реализации согласовать FR/UC, модель данных, API и UI по [правилам работы](./16-working-process.md) §1.1.

Источники: [официальная документация T-Invest MCP](https://developer.tbank.ru/invest/mcp), [статья команды Т-Банка с примерами Telegram-ассистента и робота](https://habr.com/ru/companies/tbank/articles/1086714/). ### Графический редактор графа влияний + актуальность графа

**Обоснование (as-is):** текущий способ ведения графа — карточки связей в админке «Дополнение графа» (`/admin/graph`). Карточки не визуальны, разрозненны и фрагментарны: одна карточка = одна связь («Нефть → X5», «Ставка ЦБ → X5», «Долги → X5»), по ним сложно ориентироваться и видеть целостную картину влияний на компанию/сектор. Дополнительно граф не актуализируется оперативно: рёбра не меняются под влиянием новостей, новых отчётностей и геополитики.

**Цель (to-be):** графический редактор графа влияний, в котором пользователь визуально строит связи бизнеса с миром. **Один граф = одна история про компанию или сектор** (полностью описывает его связность с миром/сущностями); если граф для компании/сектора уже существует, второй создать нельзя. Граф должен быть **актуальным**: новости, новые отчётности, геополитика оперативно меняют рёбра (знак, силу, наличие).

**Сценарии (FR/UC):**

- **UC-1. Создание сущности вручную.** Пользователь создаёт сущность (например «Нефть»). Сущности — переиспользуемые «кирпичики» ценообразования, часто входят в построение графов к секторам и компаниям.
- **UC-2. Связывание сущности с компанией или сектором.** Например, «Нефть» → X5 (компания) или «Нефть» → «Ритейл» (сектор).
- **UC-3. Графическое добавление связи.** Связь добавляется стрелкой (графически), выставляется влияние на компанию/сектор и направление: положительное (синий) / отрицательное (красное).
- **UC-4. Опциональная ссылка.** Ссылка на статью/источник, подтверждающая связь, не обязательна.
- **UC-5. Выбор бизнеса и сущностей.** Пользователь добавляет конкретный бизнес (выбор из акций МосБиржи) и ведёт от него связи к сущностям — готовым или созданным вручную (ставка ЦБ, Нефть, Пшеница, Долг, капекс, Спрос, драгметаллы, другие экономические показатели).
- **UC-6. Влияние и обоснования вручную или через RAG LLM.** Значение влияния и обоснование можно задать вручную, либо RAG LLM выделяет их из отчётности компании, которую пользователь подгружает или которая уже есть в библиотеке (документы, БД, API, Wiki, корпоративные знания).
- **UC-7. Описание на рёбрах.** На ребре — краткое описание «что произошло» + ссылка на место в документе отчётности компании или иной источник (например, красное ребро «Нефть → X5» с пометкой «Резкое подорожание цен на бензин» и ссылкой).
- **UC-8. Актуальность графа.** Новости, новые отчётности, геополитика оперативно меняют рёбра графа: смена знака (например, «Цена на нефть высокая» — отрицательное влияние → «Цена упала» — положительное), изменение силы, добавление/удаление рёбер.
- **UC-9. Алерты при сильных изменениях графа.** Пользователь оперативно информируется алертами (веб/Telegram/API) при значимом изменении: смена знака влияния, резкое изменение силы, добавление/удаление важной связи.

**Механизм сверки актуальности (открытый вопрос, механизм разработать):** желаемый режим — «в реальном времени», но конкретный механизм не определён; варианты для проектирования: периодическая сверка по расписанию, слежка за RSS-лентами по сущностям графа, ручная сверка, RAG LLM по отчётности (новые отчётности меняют рёбра). Выбор механизма и периодичности — на этапе проектирования.

**Правило приоритета:** при разногласиях по связи приоритет у связи **компании** над связью **сектора**; если у компании связи нет — используются данные сектора (общие связи сектора, к которому относится компания).

**Статус:** запланировано (дальняя перспектива).

## Критерии перехода между этапами

- Каждый этап завершается замером метрик NFR-04 и демонстрацией ключевых сценариев.
- Гейт на выходе из этапа: отсутствие критических дефектов, метрики качества не хуже целевых, документация актуальна.

Выполнено: портфель обоих контуров и управление тестовыми счетами встроены плашками в настройки брокеров; доступность зависит от сохранённого подключения. Поведение — [14](./14-web-interface.md#отдельная-страница-настроек-брокеров).

Выполнено: управление рабочими счетами при production-подключении (список, баланс, выбор и обновление портфеля). Использование — [14](./14-web-interface.md#управление-рабочими-счетами).

Выполнено: согласованный вариант карточек брокеров с независимыми рабочим/Sandbox-подключениями, раскрытием настроек и портфеля, персональным цветом/фоном и заглушкой своего брокера. Миграция 038; использование — [14](./14-web-interface.md#отдельная-страница-настроек-брокеров), обновление — [13](./13-operations.md#карточки-брокеров-и-оформление).

Реализован процесс task → spec → implementation: проектный навык, согласования этапов, префиксы tasks/spec и закрытие без накопления файлов завершённых задач. Правила — [16](./16-working-process.md#11-постановка-спецификация-и-реализация-новых-задач), решение — [ADR 39](./archive/39-task-spec-workflow.md).

Выполнено: выбор счёта и ручное обновление брокерского портфеля без перезагрузки, независимые состояния загрузки контуров, сохранение снимка при ошибке и защита от неподходящих/поздних ответов. История операций и периодическое автообновление в срез не входят. Использование — [14](./14-web-interface.md#обновление-портфеля-без-перезагрузки), проверки — [21](./21-web-e2e-tests.md#обновление-брокерского-портфеля-без-навигации).

## Отложенные задачи

### История операций брокерского счёта

**Статус:** отложено по решению пользователя. Срок и приоритет не назначены; постановка, спецификация и реализация не начаты.

Предлагаемый объём: покупки, продажи, комиссии, дивиденды и купоны по выбранному счёту с выбором периода. Рабочий контур и Sandbox используют одинаковое представление. Историю разместить отдельной вкладкой рядом с «Портфелем», чтобы не увеличивать длину страницы. Детали и доступность данных уточнить при возвращении к задаче по регламенту согласования.

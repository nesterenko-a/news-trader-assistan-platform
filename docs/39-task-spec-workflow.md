# 39. Процесс task → spec → implementation

**Статус:** утверждено v1.0 — документация и её коммит одобрены пользователем.
**Основание:** утверждённая [постановка задачи](../tasks/task-spec-workflow.md), PR #7.

## 1. Назначение и границы

Ввести обязательный порядок для новых задач проекта: постановка, согласование, спецификация и документация, согласование их коммита, затем реализация. Отсутствие ответа не считается одобрением. Уточнения и исправления текущей задачи не запускают процесс заново, если не меняют согласованные цели или границы.

Это организационный процесс: БД, продуктовый API, веб-интерфейс и переменные окружения не изменяются. Навык не разрешает самостоятельные push, создание PR или merge: для этих действий сохраняются отдельные указания пользователя.

## 2. Этапы и согласования

| Этап | Результат | Условие перехода |
|---|---|---|
| Постановка | Цель, контекст, границы, критерии готовности | Пользователь утверждает постановку |
| Фиксация постановки | Файл `tasks/<slug>.md`, коммит `tasks(scope): summary` | Постановка зафиксирована и слита в master |
| Спецификация | Уточнения, согласованные сценарии, ограничения, изменения и проверки | Пользователь одобряет документацию и её коммит |
| Фиксация спецификации | Коммит `docs(scope): summary` либо `spec(scope): summary` | Спецификация зафиксирована и слита в master |
| Реализация | Код, проверки и актуальная документация | Выполнены критерии либо явно зафиксированы остатки |
| Закрытие | Полное или частичное выполнение | Результат сопоставлен с критериями задачи |

Утверждение постановки разрешает её фиксацию, но не реализацию. Одобрение документации и её коммита разрешает следующий этап после слияния; это согласование не следует запрашивать повторно без изменений требований. Существенное изменение постановки или спецификации требует нового согласования затронутой части.

## 3. Ветки

Перед каждым новым этапом проверить ветку, рабочее дерево и наличие предыдущего этапа в master. Создавать отдельную ветку от master только находясь на master, по [регламенту §3.2](./16-working-process.md#32-начало-новой-задачи-и-создание-ветки). Примеры имён: `codex/<slug>-task`, `codex/<slug>-spec`, `codex/<slug>-implementation`.

Если текущая ветка другая, HEAD отсоединён, есть мешающие изменения или предыдущий этап ещё не слит, остановить зависимые действия и согласовать продолжение с пользователем. Не переносить чужие изменения, не выполнять stash/reset и не сливать PR автоматически. Работа внутри уже открытого этапа продолжается в его ветке.

## 4. Файлы и единый источник истины

- `tasks/<slug>.md` — цель, контекст, границы, критерии, статус этапа, ссылки на спецификацию и оставшиеся пункты. Содержимое требований не дублируется в нескольких файлах задач.
- Спецификация — существующий подходящий документ в `docs/` либо отдельный зарегистрированный проектный документ. Состав зависит от задачи: сценарии, ошибки, модель данных, API, UI, эксплуатация и проверки описываются только там, где применимы.
- `.agents/skills/task-spec-workflow/SKILL.md` — проектный навык с областью применения, переходами между этапами, обязательными согласованиями и ссылкой на регламент. AGENTS.md явно направляет агента к навыку для новых задач проекта.
- `docs/16-working-process.md` — постоянный источник правил. Навык содержит краткую последовательность исполнения и ссылки, а не копию всего регламента.
- `docs/32-docs-architecture.md` — разграничение временных файлов задач и спецификаций. Требование удаления относится к полностью закрытым файлам `tasks/`; проектные спецификации проходят существующий перенос фактов и архивацию.

Навык не устанавливается глобально для других проектов и не навязывает им этот процесс.

## 5. Изменения при реализации

1. Добавить проектный навык с корректными YAML-полями name/description и русскими инструкциями.
2. Связать его с AGENTS.md; обновить регламент: процесс действует для всех новых задач, а не только задач дорожной карты.
3. Добавить типы `tasks` и `spec` в регулярное выражение и диагностическое сообщение `tools/git_checks.py`. Сохранить остальные типы и обязательный формат `type(scope): summary`.
4. Согласовать правила закрытия и владения документами; актуализировать реестр и версии изменённых документов.
5. Выполнить проверки и сопоставить результат с критериями постановки.

Первый коммит постановки уже выполнен с `docs(process)` по отдельному разрешению пользователя, поскольку действующий валидатор пока не поддерживает tasks. Спецификация может быть зафиксирована с разрешённым типом docs; обход hooks и преждевременное изменение валидатора не требуются.

## 6. Закрытие

При полном выполнении перечислить результат по критериям в описании завершающего коммита/PR и удалить `tasks/<slug>.md` обычным Git-коммитом. Историю не переписывать, копию завершённой задачи и архив задач не создавать. До удаления устранить действующие ссылки на удаляемый файл.

При частичном выполнении сохранить файл задачи: отметить выполненные критерии, остатки, причины и следующий шаг. Недостаток времени или завершение текущего сеанса не считается полным закрытием. Отказ от согласованного объёма требует решения пользователя.

## 7. Проверки и критерии приёмки

- Валидатор принимает `tasks(process): define workflow`, `spec(process): document workflow` и существующие типы.
- Валидатор отклоняет неизвестные типы, отсутствие scope, пустой summary и неверные разделители. Тестируется реальная проверка сообщения и её код возврата.
- Проверены сценарии: новая задача на master; новая задача в другой ветке; отсутствие одобрения; одобренная постановка без одобренной спецификации; исправление текущего этапа; полное и частичное закрытие.
- SKILL.md проходит доступный валидатор skill-creator; ссылки Markdown и git hooks проходят.
- После изменения Python выполнить pytest и compileall по регламенту. E2E не требуются, поскольку продуктовый интерфейс не затрагивается.
- Навык и код валидатора появляются только на этапе реализации. В этой ветке находятся исключительно проект спецификации, реестр и статус задачи.

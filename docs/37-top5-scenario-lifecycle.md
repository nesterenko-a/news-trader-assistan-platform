# 37. Проверка исходов, актуальность и уведомления Top-5

**Статус:** проект v0.1 (ожидает согласования)
**Система:** NewsTrader Assistant

## 1. Цель и порядок

Связать опубликованный сценарий Теханализ LLM с последующим движением рынка: понять, был ли вход и чем закончился сценарий, показать его актуальность, затем уведомлять о событиях. Порядок реализации: №1 «Исходы» → №3 «Актуальность» → №2 «Алерты». Существующий бэктест Strategy Engine и виртуальный портфель решают другие задачи; новая функция оценивает модельные сценарии, а не фактические сделки пользователя.

Это отдельная проектируемая фича: в базовые справочники её контракты переносятся после реализации по [карте владения](./32-docs-architecture.md). Настоящий документ задаёт предлагаемый дизайн; разрешение начать реализацию — после его согласования по [правилам работы](./16-working-process.md) §1.1.

## 2. Срез №1: проверка исходов

### 2.1. Сценарии пользователя

- UC-37-01: запустить Top-5 и позднее увидеть состояние каждого оцениваемого сценария и историю событий.
- UC-37-02: открыть отчёт за период и сравнить результаты по инструменту, сценарию, модели и версии правил.
- UC-37-03: увидеть причину отсутствия оценки: WAIT, нет числовых уровней, неподдерживаемое подтверждение, недостаточные или неоднозначные данные.

### 2.2. Требования

| ID | Требование |
|---|---|
| FR-37-01 | При завершении нового успешного анализа из Top-5 автоматически фиксировать неизменные снимки A/B/C, автора запуска, направление, исходный JSON, уровни и версии. Для повторно использованного анализа снимки не дублировать. |
| FR-37-02 | Учитывать всех кандидатов запуска, а не только оставшиеся пять строк; отчёт явно называется статистикой сценариев кандидатов Top-5. Отбор пяти строк и браузерные фильтры не восстанавливать задним числом. |
| FR-37-03 | Добавить в JSON ответа необязательный машинный план исполнения для каждого сценария: направление, тип входа, числовые уровни, стоп, первая цель, срок действия и формальное условие подтверждения. Текст и числовой план должны согласовываться; конфликт делает сценарий неоцениваемым. |
| FR-37-04 | Первый срез поддерживает вход по касанию фиксированной цены и вход на следующем открытии после закрытия часовой свечи выше/ниже уровня. Условие применяется только при его явном наличии в плане; сложные текстовые ретесты, объёмы и сочетания индикаторов помечаются как неподдерживаемые. |
| FR-37-05 | BUY/SELL определять из плана конкретного сценария, не наследовать автоматически общий вердикт анализа. WAIT, противоречивые или неполные планы не включать в автоматическую оценку. |
| FR-37-06 | Использовать только завершённые часовые свечи MOEX, целиком начинающиеся после публикации анализа. Сохранять их время и источник. Для фьючерса фиксировать конкретный контракт без склейки при экспирации. |
| FR-37-07 | Отслеживать состояния: ожидание входа, позиция открыта, первая цель, стоп, истёк до входа, истёк после входа, неоднозначно. При недостатке данных сохранять последнее подтверждённое состояние и отдельный признак неполноты. Не превращать сетевой сбой в исход сделки. |
| FR-37-08 | Начальная точка наблюдения — время завершения анализа. Срок из валидного плана, а при отсутствии явного срока — 7 календарных дней от публикации с маркировкой «системный горизонт оценки». Это не срок, обещанный LLM. |
| FR-37-09 | Для касания фиксированного входа использовать заданную цену; если свеча открылась за входом, не предполагать исполнение по выгодной цене: пометить неоднозначность. Для входа после подтверждения использовать следующее доступное открытие без пересечения стопа или цели на этом открытии; иначе — неоднозначно. |
| FR-37-10 | После входа фиксировать первую цель или стоп. Гэп через стоп исполнять по открытию, через цель — консервативно по цели. Если порядок входа/выхода либо цели/стопа внутри свечи неизвестен, фиксировать неоднозначность. |
| FR-37-11 | При истечении срока открытый сценарий оценивать по последнему доступному закрытию не позднее срока только при подтверждённом покрытии данных; иначе результат не определён. Пропуски не заполнять искусственными ценами. |
| FR-37-12 | Повторная проверка идемпотентна: уникальность снимков и событий, курсор свечей и защита от параллельного обновления. Обновление анализа или его повторный запуск не переписывает историю снимка. |
| FR-37-13 | Старые анализы автоматически не оценивать задним числом. История нового модуля начинается после внедрения; импорт истории — отдельная задача. |

### 2.3. Метрики

Отчёт показывает число снимков и причины исключения, долю входов, число открытых и завершённых сценариев, цели/стопы/истечение, неоднозначность и полноту данных. Доля входов считается среди валидных сценариев с полным окном наблюдения. Доля достижения первой цели считается среди завершённых сценариев с входом и определённым исходом, включая истёкшие после входа; знаменатель показывается рядом.

Результат в R = направленная разница выхода и фактического модельного входа / расстояние от этого входа до стопа. Для SHORT знак разницы обратный. Нулевой риск запрещён. Показывать средний R и число наблюдений; явно указывать, что комиссия и проскальзывание не моделируются. Достижение цели до входа не является успехом. Неоднозначные исходы исключаются из агрегатов результата и видны отдельным числом. A/B/C одного анализа — зависимые альтернативы, их нельзя представлять как три независимые сделки или доходность портфеля.

### 2.4. Модель данных (проект)

- `ScenarioSnapshot`: владелец, исходный analysis_id, ticker, тип инструмента и идентификатор контракта, ключ A/B/C, published_at, expires_at, модель/провайдер, версия правил, исходный JSON и нормализованный машинный план, eligibility и причина отказа. Уникальность по analysis_id + scenario_key; снимок неизменен.
- `ScenarioEvaluation`: ссылка на снимок, текущее состояние, признак полноты, checked_at, время последней проверенной свечи, вход/выход с временем и ценой, причина исхода, результат R. Одна строка на снимок.
- `ScenarioEvent`: ссылка на снимок, тип события, время рыночного события, время регистрации, данные события и уникальный ключ для дедупликации.
- `ScenarioCandle`: инструмент/контракт, интервал, begin_at/end_at в UTC, OHLCV, источник и fetched_at; уникальность по инструменту, интервалу и begin_at. Кэш для воспроизводимости, отдельно от дневных `MarketCandle`.

Изменения SQLAlchemy сопровождаются Liquibase. Отображение времени — Europe/Moscow, хранение — UTC; границы свечей MOEX преобразуются явно. Видимость истории ограничена владельцем запуска, включая повторное использование общих расчётов: чужое владение не наследовать; при необходимости создавать принадлежащую пользователю связь наблюдения со снимком.

### 2.5. API, UI и запуск (проект)

- `GET /v1/top5/outcomes`: собственные сценарии с фильтрами по периоду публикации, тикеру, состоянию, модели и пагинацией.
- `GET /v1/top5/outcomes/summary`: агрегаты той же выборки с явными знаменателями и версией правил.
- `GET /v1/top5/outcomes/{snapshot_id}`: снимок и история событий; чужие записи недоступны.
- На `/top5` — вкладка «Исходы»: таблица сценариев, фильтры, сводные метрики и раскрытие истории; в рейтинге — краткий статус выбранного сценария. Запросы GET не запускают расчёты и не изменяют историю.
- `scripts/evaluate_top5.py`: пакетная идемпотентная проверка, режим однократного запуска и режим цикла с интервалом 5 минут; регистрация в админке с назначением и периодичностью. Запуск отдельным процессом по существующему эксплуатационному регламенту, без неявного запуска второго цикла в каждом веб-воркере. После простоя — восстановление с курсора с ограничением числа обрабатываемых снимков за проход.

## 3. Срез №3: актуальность сценария

UC-37-04: пользователь открывает старый Top-5 и видит, пригоден ли план для дальнейшего наблюдения и насколько свежи данные.

Добавить в выдачу и карточку независимые признаки: возраст анализа, время рыночных данных, последнее успешное наблюдение, срок сценария, вход уже состоялся, цель/стоп достигнуты, срок истёк, данных недостаточно. Состояния исхода берутся из общего оценщика. Признак «данные свежие» не означает «условие входа подтверждено».

Формальное подтверждение и отмена проверяются только по поддерживаемым правилам; текстовые условия показываются как требующие ручной проверки. В первом срезе этой задачи «отмена» — только явное числовое правило до входа из машинного плана, с направлением сравнения; отсутствие правила не восполняется догадкой. Возраст анализа выводится числом, срок — по снимку; универсального обещания свежести по возрасту нет. Для рыночных данных показывать торговый статус и отличать закрытый рынок от технического отставания; при неизвестном расписании не объявлять данные свежими.

Предложить переключатель «Скрыть завершённые и истёкшие» и действие пересчёта через существующий запуск анализа. Пересчёт создаёт новую версию, старая остаётся в истории. API рейтинга расширить полями актуальности без удаления существующих полей. Модель расширяется результатом проверки актуальности и причиной; TTL кэша актуальности — 5 минут, при ошибке явно показывается время последней удачной проверки. Для рыночной сессии использовать расписание MOEX, техническое отставание оценивать относительно ожидаемой последней закрытой часовой свечи.

## 4. Срез №2: алерты по сценариям

UC-37-05: пользователь подписывается на конкретный сценарий и получает уведомления о его переходах состояния, затем может отключить подписку.

Добавить `ScenarioSubscription` (владелец, снимок, включённые типы событий, каналы, active) и очередь доставки `ScenarioDelivery` с уникальностью подписка + событие + канал. Подписки выключены по умолчанию; доступны веб и привязанный Telegram. Подписка начинает доставку с момента создания, без рассылки старых событий.

События: формальное подтверждение входа, модельный вход, отмена до входа, первая цель, стоп, истечение срока. Вход в диапазон можно уведомлять только при наличии явного диапазона в плане, отдельно от подтверждения. Неподдерживаемые текстовые условия автоматических алертов не создают. Каждое событие сохраняется один раз; повторные проверки не создают новых уведомлений. Доставка допускает повторы при неопределённом ответе Telegram, поэтому не обещает exactly-once. Ошибки доставки повторяются с ограничением и паузой, текст формируется общим слоем презентации.

Проект API: `POST /v1/top5/outcomes/{snapshot_id}/subscription`, `DELETE /v1/top5/outcomes/{snapshot_id}/subscription`; включение и выбор каналов в карточке сценария. Права проверяются на каждом запросе; изменения веб-форм защищены существующим механизмом CSRF. Существующие новостные алерты сохраняют свою семантику. Уведомления означают наблюдение за модельным планом; брокерские заявки не отправляются.

## 5. Проверки и критерии завершения

Для каждого среза: meaningful pytest на переходы и границы правил, compileall; для API — контракт OpenAPI, lint и smoke; для веба — актуализация и полный прогон Playwright. Проверить LONG/SHORT/WAIT, неподдерживаемые планы, противоречивые уровни, оба уровня внутри одной свечи, гэпы, публикацию внутри свечи, часовые пояса, истечение до/после входа, выходные, пропуски, сетевые ошибки, повторный и параллельный запуск, перезапуск процесса, повторное использование анализа и изоляцию пользователей. Для алертов — подписки, дедупликацию, повторную доставку и отсутствие ретроспективной рассылки.

Срез №1 завершён, когда новые анализы имеют воспроизводимые снимки и проверяемые исходы с честными ограничениями, а пользователь видит отчёт и историю. №3 — когда карточка различает состояние сценария и свежесть наблюдений. №2 — когда подписчик получает соответствующие события без повторного создания уведомлений. После каждого среза обновить применимые базовые документы, инструкции использования и статус roadmap; проект остаётся активным до завершения всех трёх срезов, затем архивируется.

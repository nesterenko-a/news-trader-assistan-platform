# 18. Монитор здоровья (Health Monitor) — техническое задание

**Статус:** утверждено v1.0  
**Система:** NewsTrader Assistant

## 1. Назначение и обоснование

Фоновый монитор здоровья следит за доступностью ключевых внешних и внутренних зависимостей системы и сообщает о проблемах через сущность «Внимание» (`SystemNotice`, значок «!» в шапке веб-интерфейса, см. [14-web-interface.md](./14-web-interface.md)).

**Проблемы, которые решает:**
- сбой подключения к Telegram-боту не должен ронять приложение (уже исправлено);
- администратор/пользователь видит ошибки работы программы сразу, без чтения логов;
- различаются критичные (ядро не работает) и некритичные (частичная деградация) проблемы;
- после восстановления зависимостей уведомления автоматически снимаются.

## 2. Термины

- **Проверка (check)** — периодическая проверка одной зависимости, возвращает ошибку или «ок».
- **Уровень уведомления** — три уровня:
  - `critical` — блокирует основную функциональность или грозит потерей данных (красный);
  - `warning` — частичная деградация, второстепенный компонент (янтарный);
  - `info` — информационное сообщение: не ошибка, но требует внимания (например, периодический скрипт давно не запускался) (синий).
- **Источник уведомления (source)** — ключ проверки в `SystemNotice`, позволяет обновлять/снимать уведомление по состоянию и определяет иконку в попапе.

## 3. Функциональные требования

| ID | Требование |
|---|---|
| FR-HM-01 | Монитор периодически проверяет доступность БД; при недоступности создаёт уведомление `critical`, при восстановлении — снимает (и записывает факт простоя) |
| FR-HM-02 | Монитор проверяет доступность ИИ-анализа (LLM): нет `LLM_API_KEY` или нет ответа → уведомление `critical`, восстановление снимает |
| FR-HM-03 | Монитор проверяет доступность Telegram-бота (только если задан `TELEGRAM_BOT_TOKEN`); сбой → `warning`, восстановление снимает |
| FR-HM-04 | Монитор проверяет доступность MOEX ISS (котировки/свечи); сбой → `critical` |
| FR-HM-05 | Монитор проверяет источники новостей: RSS-ленты и (если настроены) Telegram-каналы; сбой → `warning` |
| FR-HM-06 | Монитор проверяет файловую систему/логи: каталог `logs/` доступен на запись, свободное место выше порога; проблемы → `warning` |
| FR-HM-07 | Монитор проверяет «свежесть» данных: если стратегии/новости не обновлялись дольше порога (например, 3 дня) — `warning` |
| FR-HM-08 | Монитор проверяет латентность LLM/MOEX: ответ дольше порога (например, 60 с для LLM) — `warning` |
| FR-HM-09 | Каждое уведомление обновляется по состоянию проверки (одно активное уведомление на источник), не дублируется |
| FR-HM-10 | Сбой самого монитора не влияет на работу приложения (проверки изолированы) |
| FR-HM-11 | Уведомления отображаются в «Внимании»: критичные — красные, некритичные — янтарные, информационные — синие (см. 14) |
| FR-HM-12 | Уведомления имеют третий уровень `info`: информационные сообщения (не ошибки), например «периодический скрипт давно не запускался» |
| FR-HM-13 | Каждая провалившаяся проверка в попапе сопровождается коротким значком, характеризующим проверку (иконка по `source`): БД, LLM (чат GPT), RSS-лента, MOEX, Telegram и т.д. |
| FR-HM-14 | Монитор контролирует **регулярность запуска периодических скриптов** из меню администрирования: если скрипт (или его результат) устарел больше допустимого срока — информационное уведомление `info` |

## 4. Объекты мониторинга и критичность

| Проверка (source) | Что проверяется | Критичность | Периодичность | Комментарий |
|---|---|---|---|---|
| `db` | `SELECT 1` | **critical** | 120 с | Вся работа зависит от БД |
| `llm` | `LLM_API_KEY` + лёгкий вызов `models.list` | **critical** | 120 с | Анализ новостей невозможен |
| `telegram` | `get_me` (только если токен задан) | warning | 120 с | Канал алертов/бота |
| `moex` | лёгкий запрос к MOEX ISS (статус 200, короткий таймаут) | **critical** | 300 с | Котировки, графики, портфель, paper trading |
| `rss` | выборка 1–2 RSS-лент через HTTP (200) | warning | 3600 с | Сбор новостей деградирует |
| `telegram_channels` | Telethon: сессия авторизована, каналы доступны (только если настроены) | warning | 3600 с | Источник новостей |
| `disk` | `logs/` доступен на запись; свободное место > 500 МБ | warning | 600 с | Потеря логов/диагностики |
| `pipeline_stale` | последняя `Strategy`/новость не старше 3 дней | warning | 3600 с | Данные устаревают (планировщик не работает) |
| `llm_latency` | время ответа LLM ≤ 60 с | warning | 3600 с | Медленный анализ (NFR-01-01) |
| `moex_latency` | время ответа MOEX ≤ 15 с | warning | 3600 с | Медленные котировки |
| `stale_daily_pipeline` | стратегии не генерировались дольше 2 дней | **info** | 3600 с | «Ежедневный конвейер» давно не запускался |
| `stale_prices` | нет свечей за последние 3 дня | **info** | 3600 с | «Обновить цены» давно не запускался |
| `stale_alerts` | алерты не генерировались дольше 7 дней | **info** | 3600 с | «Сгенерировать алерты» давно не запускался |
| `stale_macro` | нет макрособытий на ближайшие 30 дней | **info** | 3600 с | «Наполнить макрокалендарь» давно не запускался |

**Правило уровней:** `critical` — блокирует основную функциональность (БД, ИИ-анализ, рыночные данные) или грозит потерей данных; `warning` — частичная деградация (источники новостей, бот, диск, латентность, устаревание); `info` — информационные напоминания (давно не запускавшиеся периодические скрипты, см. FR-HM-14). Информационные проверки оценивают **свежесть результата** периодического скрипта (стратегии/свечи/алерты/макрокалендарь), а не факт его запуска в админ-панели — чтобы учитывать и запуски по расписанию извне.

## 5. Алгоритм работы

```
запуск приложения (lifespan)
   │
   ▼
старт фоновой задачи монитора (run_monitor)
   │  каждые N секунд (по расписанию каждой проверки)
   ▼
для каждой проверки: выполнить → {ошибка | ок}
   │
   ├─ ошибка  → создать/обновить активное уведомление source=проверка
   │            (для db: запомнить время простоя; уведомление не сохранить)
   │
   └─ ок      → снять активное уведомление source=проверка
                (для db: если был простой — создать запись «БД была недоступна …»)
```

- Проверки выполняются **независимо**; сбой одной не влияет на другие (FR-HM-10).
- Уведомление на источник одно: создаётся при ошибке, обновляется текст, снимается при восстановлении (FR-HM-09).
- Не настроенные компоненты (Telegram-бот/каналы без токена, LLM без ключа — кроме случая «ключ не задан» как ошибки) не проверяются и не порождают уведомлений.

## 6. Модель данных

Используется существующая таблица `system_notices` (см. [07-data-model.md](./07-data-model.md) §2.12.7):

| Поле | Использование в мониторе |
|---|---|
| `level` | `info` / `warning` / `critical` по таблице §4 |
| `text` | «Нет подключения к <компонент>: <ошибка>» (для БД — запись о простое) или информационное «Давно не запускался <скрипт>» |
| `source` | ключ проверки: `db`, `llm`, `telegram`, `moex`, `rss`, `telegram_channels`, `disk`, `pipeline_stale`, `llm_latency`, `moex_latency`, `stale_daily_pipeline`, `stale_prices`, `stale_alerts`, `stale_macro`, `script_run`, `db_outage` |
| `is_active` | `true` пока проблема актуальна; `false` после восстановления |
| `created_at` | время создания |

Значение `level` хранится строкой (`varchar(10)`), новых миграций для уровня `info` не требуется.

## 7. Отображение (UI)

- Значок «Внимание» (!) с четырьмя состояниями: серый (нет уведомлений) / синий (есть `info`) / янтарный (есть `warning`) / красный с пульсацией (есть `critical`) — см. [14-web-interface.md](./14-web-interface.md).
- Попап: список активных уведомлений (`GET /api/notices`), каждое выделено цветом и левой полосой по уровню (синий — info, янтарный — warning, красный — critical) с датой.
- **Иконка проверки:** у каждого уведомления в попапе слева от текста отображается короткий значок по `source` (поле `source` возвращается в API). Таблица иконок:

| source | Иконка |
|---|---|
| `db` / `db_outage` | 🗄 (база данных) |
| `llm` / `llm_latency` | 🤖 (чат GPT / ИИ) |
| `telegram` / `telegram_channels` | 📡 (Telegram) |
| `moex` / `moex_latency` | 📈 (MOEX) |
| `rss` | 📰 (RSS-лента) |
| `disk` | 💾 (диск) |
| `pipeline_stale` / `stale_*` | ⏰ (устаревание) |
| `script_run` | ⚙️ (скрипт) |

Иконки задаются на фронтенде по ключу `source` (дефолт — ⚙️). Изменений модели/API не требуется, кроме возврата поля `source` в ответе `GET /api/notices`.

## 8. Нефункциональные требования

| NFR | Значение |
|---|---|
| NFR-HM-01 | Нагрузка: суммарные проверки не должны заметно нагружать систему (лёгкие запросы, короткие таймауты) |
| NFR-HM-02 | Самоизоляция: ошибка в любой проверке не роняет монитор и приложение |
| NFR-HM-03 | Таймауты проверок ограничены (БД — 3 с, LLM — 10 с, MOEX — 10 с, HTTP-ленты — 5 с) |
| NFR-HM-04 | Время до появления уведомления: ≤ 2 × периодичность проверки |
| NFR-HM-05 | Кэширование/дедупликация: одно активное уведомление на источник |

## 9. Критерии приёмки

- [ ] При недоступности БД/LLM/MOEX в «Внимании» появляется красное уведомление, при восстановлении — снимается (для БД — запись о простое).
- [ ] При недоступности БД приложение не падает: стартует, страницы с данными отдают дружелюбную страницу «База данных недоступна» (503); критическое уведомление о простое появляется после восстановления БД (запись хранится в БД, поэтому при полной недоступности показать её невозможно).
- [ ] При недоступности Telegram-бота / RSS / каналов / диска / устаревании данных — янтарное уведомление, снимается при восстановлении.
- [ ] При «протухании» результата периодических скриптов (ежедневный конвейер, цены, алерты, макрокалендарь) — синее информационное уведомление.
- [ ] Каждое уведомление в попапе сопровождается иконкой по `source` (🗄 🤖 📰 …).
- [ ] Сбой старта бота не роняет приложение (уже реализовано).
- [ ] Отсутствуют дубли уведомлений по одному источнику.
- [ ] Монитор не влияет на скорость ответов веб-интерфейса.

## 10. План внедрения

1. **Уже реализовано:** `db`, `llm`, `telegram` (монитор в `app/notices/monitor.py`, некритичный старт бота).
2. **Этап А:** `moex`, `rss`, `disk`, `pipeline_stale` — лёгкие проверки, минимум новых зависимостей; уровень `info` и `stale_*` проверки периодических скриптов; иконки в попапе.
3. **Этап Б:** `telegram_channels` (Telethon), `llm_latency`, `moex_latency` — замеры латентности и тяжёлые проверки.

# 20. News Sources Manager — управление источниками новостей

**Статус:** утверждено v1.0  
**Система:** NewsTrader Assistant

Дизайн-документ функции управления источниками новостей из веб-интерфейса. Реализовано: страница `/news` (вкладка RSS), персональные списки `user_sources`, стандартные ленты при регистрации и кнопка «Вернуть стандартные ленты», API `/v1/sources`, SSRF-защита, автопроверка лент при старте, чтение лент коллектором и монитором из БД.

## 1. Обоснование

- Сейчас RSS-ленты **захардкожены** в `app/collectors/rss.py` (`DEFAULT_FEEDS`, 10 лент) — пользователи не могут управлять источниками.
- Одна из лент (РБК, `https://rssexport.rbc.ru/exports/full/rbc/news.rss`) **устарела и не отдаёт новости (404)**.
- Коллектор читает хардкод, а не БД: правка источников не влияет на сбор.
- **Перспектива (по решению пользователя):** страница станет единой точкой управления **всеми видами источников новостей** — RSS, Telegram-каналы, сайты компаний. RSS реализуется первым, структура закладывается сразу под все `kind`.

## 2. Термины

- **Источник новостей (source)** — запись в таблице `sources` (глобальный каталог); вид задаётся `kind`: `rss` (сейчас), `telegram` (план), `site` (план).
- **Персональный список источников** — связка `user_sources` (user_id ↔ source_id): «отслеживаемые» ленты конкретного пользователя; у каждого пользователя свой список.
- **Стандартные ленты** — `DEFAULT_FEEDS` (захардкожены в `app/collectors/rss.py`, с исправленным URL РБК): автоматически добавляются в персональный список **каждого нового пользователя** при регистрации; кнопкой «Вернуть стандартные ленты» их можно восстановить после удаления.
- **Проверка источника (health check)** — по типу: `rss` — HTTP GET + парсинг `feedparser`; результат: `ok` / `error` (+ текст ошибки). Для будущих `kind` — свои проверки (telegram: авторизация сессии; site: HTTP 200).
- **Категория** — метка для сортировки/фильтрации: фиксированный список `финансы`, `геополитика`, `погода`, `другое` (пусто).

## 3. Структура страницы `/news` (единая точка управления)

- Главная страница **`/news`** — управление источниками новостей, вкладки по типу источника:
  - **RSS** — реализуется в этой задаче (полный менеджер лент);
  - **Telegram** — заглушка «в планах» (источник уже есть: `TELEGRAM_CHANNELS`, Telethon; управление каналами — отдельная задача);
  - **Сайты** — заглушка «в планах» (парсеры сайтов компаний — этап 1 roadmap);
  - (дальше — любые новые `kind` добавляются вкладкой автоматически по наличию источников/реестру видов).
- Внутри вкладки RSS — весь функционал RSS Feed Manager (см. FR ниже).
- Маршруты: `/news` (главная, вкладки), `/news/rss` (можно открыть напрямую) — реализуется как одна страница с параметром вкладки.

| FR-20-15 | **Персональный список**: CRUD-операции пользователя работают над его списком `user_sources`; удаление убирает ленту из списка пользователя, **не удаляя** её из глобального каталога. |

## 5. Сценарии использования (UC)

- **UC-20-01** — Пользователь открывает `/news` → вкладка RSS, видит ленты со статусами, фильтрует по категории.
- **UC-20-02** — Добавляет ленту вручную → мгновенная проверка → ✓ или ✗ с причиной.
- **UC-20-03** — Ищет ленты по теме через LLM → кандидаты с проверкой → добавляет выбранные.
- **UC-20-04** — Редактирует/деактивирует/удаляет ленту.
- **UC-20-05** — При старте приложения активные ленты проверяются автоматически; статусы актуальны.
- **UC-20-06** — Пользователь видит вкладки Telegram/Сайты с пометкой «в планах» (структура готова для будущих видов источников).
- **UC-20-07** — Новый пользователь регистрируется → в его список автоматически попадают стандартные ленты.
- **UC-20-08** — Пользователь удалил стандартную ленту → нажал «Вернуть стандартные ленты» → лента снова в его списке.

## 6. Модель данных (миграция)

Таблица `sources` — новые колонки (применимы ко всем `kind`):

| Колонка | Тип | Назначение |
|---|---|---|
| `category` | `String(50)`, default `""` | Категория из фиксированного списка |
| `last_checked_at` | `DateTime(timezone=True)`, nullable | Время последней проверки |
| `last_status` | `String(10)`, nullable | `ok` / `error` |
| `last_error` | `String(500)`, nullable | Текст ошибки проверки |

Новая таблица `user_sources` (персональные списки):

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | PK | |
| `user_id` | FK → `users.id` | Владелец списка |
| `source_id` | FK → `sources.id` | Источник в списке |
| `created_at` | `DateTime(timezone=True)`, default now | Время добавления |

- Уникальность: `unique(user_id, source_id)` — один источник не дублируется в списке пользователя.
- **Регистрация пользователя**: после создания `User` в его `user_sources` добавляются все стандартные ленты (`DEFAULT_FEEDS`; сверка по URL, недостающие записи каталога создаются в `sources`).
- Миграция: `liquibase/changelogs/NNN_news_sources_manager.xml` (+ включение в `changelog-master.xml`), `ADD COLUMN` + `CREATE TABLE` с precondition `columnExists`/`tableExists` / `onFail="MARK_RAN"` (правила [16-working-process.md](./16-working-process.md) §6).
- SQLAlchemy-модель `Source` меняется вместе с миграцией.

## 7. API (REST, версия `/v1`)

Обобщённые эндпоинты над таблицей `sources` (будущие `kind` используют те же маршруты):

| Метод | Путь | Описание |
|---|---|---|
| GET | `/v1/sources` | Список **источников пользователя** (из `user_sources`), фильтр `?kind=rss` и `?category=` |
| POST | `/v1/sources` | Добавить источник **в список пользователя** (kind, name, url/config, category, reputation) + проверка; новая запись создаётся в каталоге `sources` |
| PUT | `/v1/sources/{id}` | Обновить метаданные источника в каталоге |
| DELETE | `/v1/sources/{id}` | Убрать источник **из списка пользователя** (из каталога не удаляется) |
| POST | `/v1/sources/check` | Проверить источники (`{ids: [...]}`, пусто = все активные) → статусы |
| POST | `/v1/sources/search` | LLM-поиск (`{query, kind: "rss"}`) → кандидаты с проверкой |
| POST | `/v1/sources/restore-defaults` | Вернуть стандартные ленты (`DEFAULT_FEEDS`) в список текущего пользователя |

- Авторизация: сессия (Bearer или cookie `nt_token`), любая роль `user`/`admin`.
- Валидация Pydantic; URL — SSRF-валидатор на всех входящих/исходящих запросах.
- Ошибки: 400 (невалидный URL/SSRF), 401, 404, 422.

## 8. UI (страница `/news`, вкладка RSS)

- **Таблица лент** (персональный список пользователя): имя, URL, категория, репутация, активность, статус (✓/✗), кнопки «Изменить», «Убрать», чекбоксы + «Проверить выбранные», «Проверить все».
- **Кнопка «Вернуть стандартные ленты»** — добавляет в список недостающие `DEFAULT_FEEDS`.
- **Фильтр** по категории (выпадающий список) и поиск по имени.
- **Форма ручного добавления**: имя, URL, категория, репутация, кнопка «Добавить и проверить».
- **Форма LLM-поиска**: поле запроса, «Найти» → кандидаты (название, URL, категория, статус) с чекбоксами и «Добавить выбранные».
- **Пункт меню «Новости»** в троеточии (⋮) для авторизованных.

## 9. Коллектор, монитор, стартовая проверка

- `app/collectors/rss.py`:
  - `DEFAULT_FEEDS` — bootstrap-список (первичное наполнение/fallback), в нём исправляется URL РБК;
  - новый `async def get_rss_feeds(session) -> list[dict]` — активные ленты из `sources` (`kind='rss'`, `is_active=true`).
- `scripts/collect_news.py`: `RSSCollector(await get_rss_feeds(session) or DEFAULT_FEEDS)`.
- `app/notices/monitor.py`: `check_rss` — активные ленты из БД (fallback `RSS_SAMPLE`); `RSS_SAMPLE` обновляется.
- `app/main.py` (`lifespan`): после инициализации БД — фоновая задача проверки активных лент (не блокирует старт).
- Общий модуль проверки `app/news/feed_check.py`: `async check_feed(url) -> (ok, error)` — SSRF-валидация + HTTP GET (httpx, 10 с, 2 МБ) + `feedparser.parse`.

## 10. Безопасность

- **SSRF-валидатор**: схема `http`/`https`; резолв хоста → запрет private/loopback/link-local (IPv4+IPv6); применяется при создании/редактировании и перед каждым фетчем/проверкой.
- Таймауты и лимиты: 10 с, 2 МБ.
- CRUD доступен всем авторизованным (решение пользователя); при необходимости аудит — отдельная задача.

## 11. Тестирование

- **pytest (unit)**: SSRF-валидатор (localhost/10.x/192.168.x/::1 — запрет; публичные — разрешение); `get_rss_feeds`; парсинг LLM-ответа; `check_feed` (мок httpx).

## 13. Объём работ (этапы)

1. Миграция: колонки `sources` (`category`, `last_checked_at`, `last_status`, `last_error`) + таблица `user_sources` + модель `Source`/`UserSource`.
2. Регистрация: добавление стандартных лент в список нового пользователя.
3. SSRF-валидатор + `check_feed` + `get_rss_feeds` + фикс URL РБК.
4. API `/v1/sources` (список пользователя, add/remove, check, search, restore-defaults) с LLM-интеграцией.
5. Веб-страница `/news` (вкладки, таблица, формы, кнопка «Вернуть стандартные ленты», меню).
6. Автопроверка при старте (lifespan) + обновление `check_rss` монитора и `collect_news`.
7. Тесты, документация, коммиты (по задачам).

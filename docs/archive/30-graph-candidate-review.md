# 30. Автоматические кандидаты связей графа и кураторское подтверждение

**Статус:** реализовано v1.0 (очередь кандидатных связей с кураторским подтверждением)  
**Система:** NewsTrader Assistant

## 1. Назначение и границы

Система должна находить в уже проанализированных новостях возможные новые связи вида «сущность → сущность» и передавать их куратору на проверку. Цель — расширять knowledge graph доказуемо и без автоматического внесения недостоверных рёбер в стратегии.

Первая версия работает только с кандидатами на **новую связь между существующими сущностями**. Кандидаты на создание новой сущности, изменение уже утверждённого ребра и автоматическое удаление связи не входят в объём версии 1: они требуют отдельного дизайна актуализации графа.

Кандидат никогда не участвует в поиске путей, расчёте стратегии, карте зависимостей или API публичной аналитики, пока куратор явно не примет его.

## 2. Обоснование

В графе уже есть курируемые связи и ручное дополнение через `/admin/graph`, включая ссылки на исследования. Однако расширение покрытия требует от куратора вручную обнаруживать связи в большом потоке статей. Анализ новостей уже извлекает сущности, тональность и факты, поэтому может подготовить структурированные предложения с первоисточниками, оставляя человеку решение о достоверности и экономическом смысле.

## 3. Пользовательские сценарии

### UC-30-01. Просмотр очереди

Администратор открывает `/admin/graph/candidates`, видит новые и отложенные предложения, их приоритет, сущности, предполагаемый знак, силу, объяснение и статьи-доказательства. По умолчанию отображаются кандидаты со статусом `pending`.

### UC-30-02. Подтверждение кандидата

Администратор проверяет минимум одну статью и объяснение, при необходимости исправляет знак, силу, характер связи, уверенность и обоснование. После «Принять» создаётся обычное утверждённое `Influence` с `created_by="curator"`; кандидат получает статус `approved` и ссылку на созданное ребро.

### UC-30-03. Отклонение

Администратор отклоняет ложное или нерелевантное предложение, при необходимости оставляя короткую причину. Кандидат сохраняется со статусом `rejected` для аудита и не предлагается повторно по тем же доказательствам.

### UC-30-04. Отложенная проверка

Администратор выбирает «Нужно больше данных». Кандидат получает статус `needs_evidence`; при появлении новой независимой статьи система добавляет её в те же доказательства и возвращает кандидат в `pending`, когда пройдены пороги отбора.

### UC-30-05. Пакетный просмотр

Администратор фильтрует очередь по сущности, типу, направлению, силе, уровню уверенности, статусу и дате. Пакетное подтверждение намеренно не поддерживается в первой версии: решение по каждой экономической связи требует просмотра доказательств.

## 5. Правила извлечения и отбора

1. Входом является статья с завершённым LLM-анализом и минимум двумя распознанными сущностями из `entities`.
2. LLM получает нормализованный список сущностей статьи и возвращает не более трёх причинно-следственных предложений строго в JSON: `from_entity`, `to_entity`, `direction`, `strength`, `kind`, `confidence`, `rationale`, `quote`.
3. Допускаются `direction`: `positive`/`negative`; `strength`: `weak`/`medium`/`strong`; `kind`: `direct`/`indirect`. Некорректный ответ отбрасывается и логируется.
4. Связь с одинаковой исходной и целевой сущностью, а также пара, уже утверждённая в `influences`, отбрасывается.
5. Ключ агрегации: `from_entity_id`, `to_entity_id`, `direction`, `kind`. Сила кандидата равна наиболее часто подтверждённой силе; при равенстве выбирается более осторожная. Итоговая уверенность — взвешенная средняя по источникам с ограничением 0.95.
6. Независимыми считаются статьи с разными каноническими `cluster_id` (или разными `id`, если кластер отсутствует) и разными URL. Перепечатки не повышают число доказательств.
7. Если один из факторов качества не достигнут, кандидат хранится как `needs_evidence`; при достижении порогов автоматически возвращается в `pending`.
8. Отклонённый кандидат не возобновляется автоматически. Новая очередь может быть создана только при новом наборе доказательств, который не пересекается с отклонённым; это защищает куратора от повторного шума.

## 6. Модель данных

### 6.1. `graph_candidates`

| Поле | Тип | Назначение |
|---|---|---|
| id | PK | Идентификатор кандидата |
| from_entity_id | FK → entities | Сущность-источник |
| to_entity_id | FK → entities | Сущность-приёмник |
| direction | varchar(10) | `positive` / `negative` |
| strength | varchar(10) | `weak` / `medium` / `strong` |
| kind | varchar(10) | `direct` / `indirect` |
| confidence | float | Агрегированная уверенность 0..1 |
| rationale | text | Сводное объяснение кандидата |
| status | varchar(20) | `needs_evidence` / `pending` / `approved` / `rejected` |
| evidence_count | integer | Число независимых доказательств |
| approved_influence_id | FK → influences, nullable | Созданная связь после принятия |
| reviewed_by | FK → users, nullable | Куратор, принявший решение |
| reviewed_at | datetime, nullable | Время решения |
| review_comment | text, nullable | Причина отклонения или заметка куратора |
| created_at / updated_at | datetime | Время создания и обновления |

Уникальность активного кандидата: `(from_entity_id, to_entity_id, direction, kind)` для статусов `needs_evidence` и `pending`. В PostgreSQL это обеспечивается частичным уникальным индексом; для SQLite-тестов — проверкой в сервисе.

### 6.2. `graph_candidate_evidence`

| Поле | Тип | Назначение |
|---|---|---|
| id | PK | Идентификатор доказательства |
| candidate_id | FK → graph_candidates | Кандидат |
| article_id | FK → articles | Исходная статья |
| quote | text | Цитата, подтверждающая причинную связь |
| rationale | text | Объяснение LLM для этой статьи |
| confidence | float | Уверенность отдельного извлечения |
| created_at | datetime | Время добавления |

Уникальность: `(candidate_id, article_id)`. URL и кластер берутся из `articles`; отдельное копирование не требуется.

### 6.3. Миграция

Нужен новый Liquibase-чейнджлог с преcondition `onFail="MARK_RAN"`, добавленный в `changelog-master.xml`. Новые SQLAlchemy-модели и миграция поставляются одним изменением. Существующие `entities`, `influences` и `articles` не меняются.

## 7. API

Все маршруты раздела доступны только администратору и используют текущую сессионную аутентификацию.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/v1/admin/graph/candidates` | Список кандидатов: `status`, `entity`, `direction`, `min_confidence`, `page`, `per_page` |
| GET | `/v1/admin/graph/candidates/{id}` | Детали кандидата и все evidence со ссылками на статьи |
| POST | `/v1/admin/graph/candidates/{id}/approve` | Принять с редактируемыми полями связи и необязательным комментарием |
| POST | `/v1/admin/graph/candidates/{id}/reject` | Отклонить: `{comment}` |
| POST | `/v1/admin/graph/candidates/{id}/need-evidence` | Вернуть в ожидание дополнительных независимых доказательств |

`approve` принимает `direction`, `strength`, `kind`, `confidence`, `rationale`, `source_ref` и `comment`. Сервер повторно проверяет, что связь ещё не создана другим куратором; при конфликте возвращает `409` и показывает существующее ребро.

## 8. Веб-интерфейс

Текущая страница `/admin/graph` сохраняет назначение ручного дополнения и управления утверждёнными связями. В её шапке появляется ссылка **«Кандидаты (N)»**, где `N` — число `pending`.

Новая страница `/admin/graph/candidates`:

- вверху — счётчики «Новые», «Нужно больше данных», «Принято сегодня», фильтры и поиск по сущностям;
- каждая карточка показывает пару сущностей, знак, силу, характер, уверенность, число независимых источников и агрегированное объяснение;
- блок доказательств содержит заголовок, дату, источник, цитату и внешнюю ссылку на статью;
- действия: **«Принять»**, **«Отклонить»**, **«Нужно больше данных»**; перед принятием карточка раскрывает редактируемые поля будущего `Influence`;
- для действий используются существующие стандартные кнопки: `✎`/`✓` для правки, `✕` не применяется, поскольку отклонение не удаляет данные.

При принятии или отклонении страница сохраняет выбранный фильтр и возвращает пользователя в очередь. Страница должна иметь отдельные Playwright-сценарии: доступ только админу, фильтрация, просмотр evidence, принятие с редактированием и отклонение.

## 9. Интеграция с конвейером и Strategy Engine

Извлечение запускается после успешного текстового анализа статьи. Ошибки извлечения изолированы: статья сохраняется и продолжает участвовать в обычном анализе. Для ограничения стоимости LLM извлечение выполняется только для статей с `impact_score >= 0.50` и не чаще одного раза на статью и версию извлекателя.

Утверждённая связь сохраняется как обычный `Influence` с `is_approved=true`, `created_by="curator"` и объединёнными URL доказательств в `source_ref`. После этого существующий поиск путей автоматически сможет использовать её без изменения алгоритма Strategy Engine. Кандидаты и evidence не участвуют в бэктестах до принятия.

## 10. Проверки и критерии приёмки

- Из двух независимых статей создаётся один агрегированный кандидат, а не два.
- Перепечатка той же статьи не увеличивает `evidence_count`.
- Кандидат с низкой уверенностью остаётся в `needs_evidence`.
- Принятие создаёт одно утверждённое ребро и делает его доступным в `find_influence_paths`.
- Отклонение сохраняет аудит и не влияет на граф или стратегии.
- Обычный анализ новости и ежедневный конвейер завершаются успешно при недоступности LLM-извлекателя кандидатов.
- Юнит-тесты покрывают агрегацию, пороги, идемпотентность и принятие; E2E — права доступа и все кураторские действия.

## 11. Этапы реализации

1. Liquibase, модели, сервис агрегации и юнит-тесты.
2. Вызов извлекателя из конвейера и безопасное журналирование ошибок.
3. REST API и серверная страница очереди куратора.
4. Playwright E2E, документация эксплуатации/API/UI, smoke и полный набор проверок.

Реализация завершена: модели и Liquibase-миграция `031`, извлечение после анализа новости, admin API, веб-очередь и unit-тесты добавлены. Изменения существующих связей и автоматическое создание сущностей остаются вне текущей версии.

## 12. Принятые решения

1. Используются пороги: `0.70 + 2 независимых источника` или `0.90 + 1 источник`.
2. Отклонённые кандидаты сохраняются без автоматического удаления для аудита.
3. Первая версия не создаёт новые сущности автоматически; новые сущности добавляются текущим ручным инструментом.
4. Изменение существующих связей и уведомления об изменении графа относятся к отдельному последующему проекту «актуальность графа».

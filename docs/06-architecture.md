# 06. Архитектура системы

**Статус:** утверждено v1.0  
**Система:** NewsTrader Assistant

Документ описывает архитектуру на уровне компонентов и потоков данных, **без привязки к конкретным технологиям**. Выбор конкретных языков, СУБД и библиотек — отдельное решение (см. раздел «Требования к технологиям»).

## 1. Принципы архитектуры

1. **Слоистость** — данные, аналитика, приложение разделены.
2. **Слабая связанность** — компоненты общаются через очереди и чёткие интерфейсы.
3. **Асинхронность приёма данных** — поступление новостей не блокирует запросы пользователей.
4. **Горизонтальное масштабирование** — самые «тяжёлые» компоненты (анализ, стратегия) масштабируются независимо.
5. **Прозрачность принятия решений** — каждый компонент сохраняет артефакты (версии моделей, цепочки влияния), чтобы решение можно было объяснить.

## 3. Компоненты

### 3.1. Слой сбора (Ingestion)

**Назначение:** получение, очистка и нормализация контента.

| Компонент | Ответственность |
|---|---|
| **Коннекторы** | Один коннектор на источник/тип источника: RSS-ленты, API агентств, парсеры сайтов, Telegram-каналы, вебхуки. Работают по расписанию или по подписке |
| **Нормализатор** | Приводит данные к единой схеме: текст, дата, язык, источник, автор. Убирает HTML-мусор, рекламу, дублирующие блоки |
| **Дедупликатор** | Кластеризует перепечатки одной новости (по хешам и семантической близости), выбирает «канонический» текст и собирает список источников |

### 3.2. Аналитическое ядро

| Компонент | Ответственность |
|---|---|
| **NLP-анализ** | Определение тематики, тональности по сущностям, извлечение сущностей и фактов, расчёт impact score. Каждый результат привязан к версии модели |
| **Knowledge Graph** | Хранение сущностей и связей; алгоритмы вывода цепочек влияния; объяснение рёбер (почему связь существует) |
| **Market Data** | Котировки, технические индикаторы, макрокалендарь. Данные кэшируются и снабжаются меткой времени |
| **Strategy Engine** | Синтез вердикта из сигналов: новости + граф + индикаторы. Формирует обоснование и контраргументы |

### 3.3. Слой приложения

| Компонент | Ответственность |
|---|---|
| **API Gateway** | Единая точка входа: авторизация, rate limiting, маршрутизация, версионирование API |
| **Web UI** | Интерфейс пользователя: запрос аналитики, карточки бумаг, watchlist, портфель, история |
| **Admin Console** | Управление источниками, скорингом, связями графа; просмотр статистики |
| **Alerting** | Генерация и доставка уведомлений по настройкам пользователя |
| **Bot** | Канал взаимодействия через мессенджер (опционально) |

### 3.4. Служебные сервисы

| Компонент | Ответственность |
|---|---|
| **Сервис пользователей** | Регистрация, профили, watchlist, портфели, настройки |
| **Сервис обратной связи** | Сбор оценок, статистика качества, пересчёт весов моделей (с версионированием) |
| **Бэктестинг** | Воспроизведение вердиктов «на момент T», отчёты о качестве |
| **Планировщик** | Периодические задачи: обновление макрокалендаря, пересчёт индикаторов, прогон вердиктов по watchlist |

## 4. Потоки данных

### 4.1. Поток обработки новости (асинхронный)

```
Источник → Коннектор → Очередь сырых событий
         → Нормализатор → Дедупликатор
         → NLP-анализ (тематика, тональность, сущности, факты)
         → Обогащение: связи сущностей из графа, привязка к бумагам
         → Сохранение в хранилище + индекс
         → (если значимость высокая) → Алертинг → Уведомление
```

### 4.2. Поток запроса пользователя (синхронный)

```
Пользователь (UI/API) → API Gateway → Проверка доступа
  → Запрос аналитики по бумаге [ticker]
  → Strategy Engine:
     1. Собрать свежие новости по бумаге (прямые + отраслевые + связанные сущности)
     2. Построить цепочки влияния через Knowledge Graph
     3. Подтянуть индикаторы и события макрокалендаря
     4. Агрегировать сигналы → вердикт + уверенность
     5. Собрать обоснование: цитаты, ссылки, цепочки, контраргументы
  → Кэширование ответа
  → Ответ пользователю
```

### 4.3. Поток обучения (периодический)

```
Фактические движения цен → Сервис обратной связи
  → Сопоставление с прошлыми вердиктами → Метрики качества
  → Корректировка весов факторов → Новая версия весов (A/B сравнение)
```

## 5. Хранилища данных

| Хранилище | Содержимое | Примечания |
|---|---|---|
| **Документное/поисковое** | Новости, статьи, обогащённые метаданными (сущности, тональность, тематика) | Поддерживает полнотекстовый поиск и фильтры |
| **Графовое** | Сущности и связи influence с атрибутами | Для вывода цепочек влияния |
| **Временные ряды** | Котировки, индикаторы, исторические данные | Высокая частота записи, агрегации по периодам |
| **Реляционное** | Пользователи, watchlist, портфели, вердикты, оценки | Транзакционная целостность |
| **Кэш** | Частые ответы, индикаторы на коротком горизонте | Снижение нагрузки, быстрое чтение |

## 6. Требования к технологиям (ориентир)

- **Язык**: допускается любой язык экосистемы; предпочтительно использование одного основного языка для аналитического ядра.
- **ML/NLP**: современные библиотеки обработки текста, поддержка русского и английского языков; возможность запуска больших языковых моделей как отдельного сервиса.
- **Очереди**: надёжный брокер сообщений с гарантией доставки.
- **Граф**: хранилище, поддерживающее обход графа и атрибуты рёбер.
- **Контейнеризация**: компоненты разворачиваются в контейнерах; оркестрация — по потребности.

## 7. Развёртывание

- Каждый сервис — независимо разворачиваемый модуль.
- Аналитическое ядро масштабируется горизонтально (несколько воркеров очереди).
- Прод/стейдж/тест среды изолированы.
- Данные аналитики пересоздаются повторным прогоном конвейера (воспроизводимость).

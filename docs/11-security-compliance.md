# 11. Безопасность и комплаенс

**Статус:** утверждено v1.6 (границы доступа аналитики MCP)
**Система:** NewsTrader Assistant

## Аналитика MCP Т-Инвестиций

Доступ к аналитике требует пользовательской сессии; cookie-POST проверяет Origin. Подключение выбирается по владельцу и контуру, счёт — только из его подключения; подстановка другого accountId моделью запрещена. Ключи брокера/LLM, MCP session id и заголовки не входят в контекст модели. При отражении токена/сессии в результате MCP данные отклоняются. Подтверждение проверки LLM привязано к владельцу, провайдеру, модели, сроку и конфигурации.

Внешние новости, описания и результаты — недоверенные данные. Они не расширяют разрешения: модель видит только локальные адаптеры, манифест проверяет полное совпадение схемы, аргументы проходят отдельную валидацию, счёт подставляет сервер. Заявки, переводы, управление Sandbox, избранным и история операций в аналитическом наборе отсутствуют. Даже предложенный моделью изменяющий вызов отклоняется сервером. Ответы выводятся как текст, ссылки источников не исполняются автоматически; схемы и их документация не считаются инструкциями.

При отправке вопроса пользователь видит предупреждение о передаче необходимых данных выбранному внешнему LLM-провайдеру. Токен брокера не передаётся. У приложения нет постоянной истории диалога; успех проверки схемы не подтверждает достоверность/свежесть данных, а лимиты и предупреждения остаются частью результата. Контракт — [API](./10-api-specification.md#аналитический-вопрос).

## 1. Безопасность данных

| Область | Требования |
|---|---|
| Аутентификация | Пароли — только в хешированном виде; API-ключи — в зашифрованном виде |
| Транспорт | TLS для всех соединений с системой |
| Доступ | Ролевая модель: user / admin; изоляция данных пользователей |
| Хранение | Шифрование чувствительных данных; резервное копирование с ограничением доступа |
| Аудит | Журналирование действий администраторов (кто, что, когда) |
| Защита | Защита от OWASP-типовых уязвимостей: инъекции, XSS, CSRF, подбор ключей |
| Данные пользователей | Удаление аккаунта и связанных данных по запросу |

### 1.1. Роли и административный доступ

- Пользователи имеют роль `user` (по умолчанию) или `admin`.
- Администраторы задаются переменной `ADMIN_USERNAMES` в `.env` (через запятую); при старте приложения эти пользователи идемпотентно получают роль `admin`.
- Администратор получает доступ к странице `/admin`: запуск основных скриптов проекта (`daily_pipeline`, `collect_news`, `update_prices`, `process_alerts`, `seed_macro`, `seed_db`, `calibrate`, `backtest`, `backtest_asof`) из веб-интерфейса и просмотр истории запусков с выводом.
- Запуск выполняется подпроцессом с **whitelist-аргументами** (допустим только один числовой параметр); произвольные команды/аргументы не принимаются. Одновременно выполняется один скрипт (глобальная блокировка).
- История запусков хранится в таблице `script_runs` (кто запустил, какой скрипт, статус, код выхода, вывод, время) — это журнал действий администратора.

## 2. Правовые аспекты и комплаенс

### 2.1. Не является инвестиционной рекомендацией

- Все вердикты системы носят **информационный характер** и не являются индивидуальной инвестиционной рекомендацией (ИИР) в терминах законодательства о финансовых рынках.
- Каждый ответ содержит дисклеймер (см. пример в [09-strategy-engine.md](./09-strategy-engine.md), раздел 5).
- Система не учитывает полный профиль риска пользователя; при необходимости пользователь должен обращаться к лицензированным консультантам.

### 2.2. Работа с открытыми данными

- Источники — только публичные и легально доступные.
- Использование контента (цитаты, ссылки) — с указанием авторства и первоисточника.
- Не используются инсайдерские данные; система не стимулирует их получение.

### 2.3. Ответственность за решения

- Решения о сделках принимает исключительно пользователь.
- Система обязана показывать риски и неопределённость (уверенность, контраргументы), а не только вердикт.
- Верификация результатов на исторических данных публикуется как метрики качества, без гарантий будущей доходности.

## 3. Этические принципы

1. **Прозрачность** — путь рассуждения системы доступен пользователю.
2. **Независимость от источника** — скоринг источников не зависит от платы или связей; потенциальные конфликты интересов исключаются.
3. **Отказ от манипуляций** — система не создаёт шумовых сообщений, не «подкручивает» вердикты.
4. **Ограничение вреда** — при высокой неопределённости система выбирает HOLD / INSUFFICIENT_DATA, а не рискованный вердикт.

## 4. Процедуры

| Процедура | Описание |
|---|---|
| Ревью новых моделей | Каждая модель проходит валидацию и A/B-прогон перед продом |
| Ревью связей графа | Авто-предложенные связи графа вводятся только после подтверждения куратором |
| Инцидент-процесс | Фиксация, разбор, уведомление пользователей при утечках/сбоях |
| Обновление дисклеймеров | Юридическая вычитка текстов перед релизами и при изменении регулирования |
| Отказ пользователю | Возможность полного отказа от данных и сервиса |
## Токен Т-Инвестиций

Для рабочего контура принимается только токен с правами чтения. Для каждого пользователя токен шифруется AES-256-GCM с отдельным случайным nonce и привязкой к пользователю через AAD. В БД находятся только шифротекст, nonce и идентификатор ключа; ключ задаётся отдельно через конфигурацию окружения. При отсутствии ключа подключение недоступно. Ответы и логи не включают токен; отключение удаляет сохранённый шифротекст и снимки, отзыв токена пользователь выполняет в Т-Инвестициях.

## Контуры Т-Инвестиций

Рабочий контур по-прежнему принимает только readonly-токены. Песочница допускает тестовый токен с полными правами. После отдельного согласования реализованы только три изменяющих RPC SandboxService: OpenSandboxAccount, SandboxPayIn и CloseSandboxAccount. Они закреплены за sandbox-хостом, проверяют сохранённый контур и владельца; заявки и торговля не реализованы. Приложение проверяет принадлежность счёта актуальному списку, Origin/CSRF и обязательное подтверждение закрытия. Ключ операции и журнал защищают от повторов, изменяющие RPC не используют автоматические retries; неопределённый ответ отмечается unknown. GET страницы ничего не создаёт и не пополняет. Контур выбирается явно, адреса закреплены в клиенте; автоматической попытки того же токена в другом контуре нет. AAD шифрования токена песочницы привязана к владельцу и sandbox; формат рабочего AAD сохранён для совместимости существующих подключений. Переключение контура без повторного шифрования не позволяет прочитать токен. Календарь использует только подключение владельца исходного анализа, не токен другого наблюдателя. В снимки расписания и сообщения об ошибках токены не включаются.

## Приватное оформление карточек брокеров

Цвет проверяется как #RRGGBB; фон читается не более 3 МБ и принимается только после декодирования PNG/JPEG/WebP. Изображения свыше 20 мегапикселей отклоняются, остальные нормализуются до WebP не более 1024×512 с удалением метаданных. Байты хранятся в БД, не публикуются в uploads и JSON API. Выдача требует текущего владельца, не принимает чужой user_id и имеет private/no-store и nosniff. POST оформления проверяет Origin. У обоих контуров отдельные токены, состояния и снимки; отключение одного не удаляет другой, оформление сохраняется отдельно.
